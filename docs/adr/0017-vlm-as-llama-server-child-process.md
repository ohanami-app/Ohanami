# 0017. VLM は、アプリが起動する別プロセスの llama-server で動かす

状態: 採用

## 背景

VLM(画像と文章を扱える AI モデル。ここでは、画像から、写っている文字・説明文・タグを作る)を使って、画像ごとに、写っている文字の書き起こし(OCR)・説明文・タグを作る(モデルの選択は 0018)。使う人から見た問題は、次のとおり。ゲームを始めるときに処理を止めたら、GPU のメモリがすぐに空いてほしい。AI の実行サービスを、先に別にインストールしてほしい、とは頼みたくない。AI の処理が失敗しても、アプリの画面ごと落ちてほしくない。これらから、動かし方には、次の制約がある。

- 外部サービスのインストールが要らないこと(out of the box)。外部の API・クラウドへの通信もしない。
- ゲームをしている間は GPU を空けたい。VLM は VRAM を約 6GiB(0019)握るので、止めたら確実に戻る必要がある(0027)。
- 推論側のクラッシュや異常が、画面(UI)を巻き込まないこと。
- ビルドとモデルのファイルを固定して、結果が勝手に変わらないこと(0020)。
- マルチモーダルの入力(画像)に対応していること。

## 決定

llama.cpp の `llama-server.exe` を、アプリの exe の隣に(その DLL と一緒に平らに)同梱し(0042)、アプリの子プロセスとして起動・停止する。通信は `127.0.0.1` のループバックの HTTP(OpenAI 互換の `/v1/chat/completions`)で行う。

- 固定するビルドは b12110(`llama-server --version` の出力は `build 12110, commit cd959bae9`)。起動前に、`llama-server.exe` の SHA-256 と、`--version` の出力が定数(`src/Ohanami.Core/Models/VlmCatalog.cs`)と一致することを確かめる。不一致なら起動を止める。
- 起動の引数は、文字列の連結ではなく、明示的に組み立てる(構成は 0019)。`--host 127.0.0.1` を明示する。ポートは OS に決めさせた空きポートを使う。
- 起動待ちは `GET /health` を 0.5 秒おきに叩く。503 は読み込み中として待ち、200 で完了とする。それ以外の状態や、プロセスの終了は、即失敗にする。失敗したときは、標準出力・標準エラーの末尾 40 行をメッセージに入れ、ログの全体は最新 3 回分を残す。
- 停止は、プロセスツリーごとの kill である。llama-server は状態を持たない使い捨てなので、穏やかな終了は要らない。
- 自前で書く部品は、ポートの確保、起動待ち、孤児プロセス(親のアプリが終わったあとも残る子プロセス)の掃除(0026)、ファイルとビルドの検証(0020)である(`src/Ohanami.Core/Vlm/`)。
- VLM は起動時には検証も起動もしない。最初に VLM のジョブが必要になったときに行う(検索だけのとき、約 6GB を読まない)。

## 検討した案

- **Ollama を使う**: 外部サービスのインストールが要る。ビルドとモデルの固定も、アプリの側から制御しにくい。採らない。
- **LLamaSharp で、アプリのプロセス内で動かす**: マルチモーダル対応が llama.cpp 本体に遅れて入りやすく、対応状況が地雷になりやすい。プロセス内のクラッシュが UI ごと巻き込む。VRAM を確実に空けるには、プロセスを終わらせるのが最も確実である。採らない。
- **llama.cpp の最新ビルドに追随する**: 挙動が勝手に変わる。結果を「モデル・ビルド・設定だけ」で決める方針(0006・0024)に反する。ビルドを固定して、上げるときは評価をやり直す。

## 根拠

- b12110 のマルチモーダル(画像を読む部分。mtmd)が対応する Qwen 系は、Qwen2-VL・Qwen2.5-VL・Qwen3-VL・Qwen3.5。Qwen3.6 以降は 27B(パラメータ 270 億)以上か、MoE(一部の専門家だけを動かす構造のモデル)しかなく、対象環境(0018)に載らない。
- b12110 の `llama-server` は、評価に必要なオプションをすべて持つ。`--image-min-tokens`・`--image-max-tokens`・`--no-mmproj-offload`・`-cram`・`-lm none`・`-np`・`--no-webui`・`--timeout`・`--chat-template-kwargs`。リクエストごとの `repeat_penalty` と `dry_multiplier` が、temperature 0 でも効く(0023)。
- 子プロセスを kill すれば、VRAM が起動前の水準に戻る。1030 枚を流す途中で一時停止して再開したとき、VRAM は起動前 + 147MiB まで戻り、再開後も正常に動いた。
- 起動の時間は、実際のライブラリでの確認で 2.6〜9 秒(モデルが OS のキャッシュにあるとき)。電源を入れた直後のコールドスタートは測っていない。
- `llama-server --version` は、標準出力でなく標準エラーに出る。両方を取って解析する。
- 同梱物: `llama.cpp/b12110/` は 56 ファイル(約 735.5MiB。大きいものは `cublasLt64_13.dll` 469.9MiB・`ggml-cuda.dll` 151.6MiB)。`llama-server.exe` の静的 import の閉包は、本体を含む 8 ファイル(約 25.2MiB)。

## 結果

- 外部サービスなしで、VLM がアプリと一緒に配布できる。止めれば VRAM が戻るので、ゲーム中の一時停止(0027)が成り立つ。
- llama-server の異常(クラッシュ・応答しない・GPU が取られた)は、UI と切り離される。扱いは 0023(出力のループ)・0026(寿命管理)・0028(長時間の処理)で決める。
- ビルドの更新は、評価のやり直しを伴う。ポート確保・孤児の掃除・ヘルスチェックなどを自前で保守する。
- `ggml-cuda.dll` などのビルドの同梱物は、実行時には個別にハッシュしない(`llama-server.exe` の SHA-256 と `--version` で確かめる)。配布物を作るときに、許可の表の SHA-256 と突き合わせる(0042)。
- llama-server が実行時に読む DLL は、静的 import の閉包以外は確かめていない。

## 見直す合図

- llama.cpp を更新するとき。同じ評価(0018)で、出力が同じか(または許容できるか)を確かめる。
- 使いたいモデルが、b12110 の mtmd で対応していないとき。
- 子プロセスを使う形で、利用者の環境(セキュリティ製品・ファイアウォールの警告など)に問題が出たとき。
