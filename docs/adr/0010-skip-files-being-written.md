# 0010. 書き込みの途中のファイルは登録しない

状態: 採用

## 背景

利用者がスクリーンショットを撮った直後に、アプリがまだファイルを書いている途中かもしれない。スクリーンショットのアプリは、ファイルを一度に書くとは限らない。開いたまま少しずつ書くもの、少しずつ(チャンクごとに)開いて閉じるもの、一時ファイルに書いて名前を変えるものがある。ほかのプログラムが書き込み中のファイルを開こうとすると、共有違反(使用中で開けないエラー)になる。途中の内容を画像として登録すると、壊れた画像のハッシュで結果が作られ、書き終わったあとに別のハッシュで登録し直すことになる。

走査は、ディレクトリの列挙で得た更新日時とサイズを DB に記録し、ファイルを読んだ内容からハッシュを取る(0003)。確かめたこと(NTFS)を示す。

| 事実 | 内容 |
|---|---|
| 列挙の値が古い | 書き手が開いたまま `Flush` せずに書く間、列挙で得る更新日時とサイズは、書き手が閉じるまで古いままだった(2MB を 1 秒おきに 8 回書いて、長さ 0 のまま 8 秒)。パスを直接引いた値と、開いたハンドルの値は、書くたびに進む。`Flush` する書き手・チャンクごとに閉じる書き手では、列挙の値も書くたびに進む |
| 公式の記述 | 最後に書いた時刻は、書き込みに使った全ハンドルが閉じるまで完全には更新されない(Microsoft Learn の File Times) |
| 共有違反 | 書き手が書き込みのために開いている間は、読み取りの共有で開こうとすると共有違反になる。共有の検査は開くときに双方向に行われるので、こちらが読んでいる間に書き手が Write で開くことも、書き手の側が共有違反になる |
| 閉じたあと | 書き手が閉じたあとの列挙の値は新しい |

## 決定

次の 4 つで、途中の内容を登録しない(`src/Ohanami.Core/Scanning/Scanner.cs`)。

1. **開き方は `FileShare.Read | FileShare.Delete` のままにする。** 書き手が書き込みのために開いている間は共有違反になり、そのファイルは今回の走査では登録しない(記録せず、次回に回す)。「書き手が開いている間の途中の内容を決して読まない」保証を取る。
2. **共有違反など一時的に読めなかったファイルがあれば、監視がきっかけの走査のとき、そのフォルダを 5 秒後にもう一度走査する。** 書き手が閉じても、イベントが来ない書き方があるため。同じフォルダで「一時的に読めない」が 3 回続けて 1 件以上なら、再走査は予約せず、定期の走査(0009)に任せる。0 件になれば回数を戻す。
3. **読んだあと、ハンドルの値と列挙の値を比べる。** ハンドルのサイズが列挙のサイズと違う、またはハンドルの更新時刻と列挙の更新時刻の差が 2 秒を超えるファイルは、今回は登録せず、5 秒後の走査に回す。列挙してから開くまでの間に書き足された場合を拾う。更新時刻に 2 秒の許容を入れるのは、ファイルシステムによって更新時刻の刻みや表し方が違い、完全一致を求めると、そのボリュームのファイルが永久に登録されなくなるため。サイズは完全一致である。一致したときだけ登録するので、DB に入る更新日時とサイズは列挙の値のままで、ハッシュの内容と対応する。
4. **更新時刻が「0 ≤ 今 − 更新時刻 < 2 秒」のファイルは、今回は登録しない。** チャンクの間が 2 秒より短い書き手を拾う。更新時刻が未来のファイルは、普通に登録する(NAS の時計のずれなどで、「2 秒以内」を絶対値で判定すると、未来のファイルが永久に登録されないため)。2 秒は、測って決めた値ではなく、推測の初期値である。

## 検討した案

| 案 | 採らなかった理由 |
|---|---|
| `FileShare.ReadWrite` で開く | 書き手を弾かないが、書き込み途中の内容を読みうる |

## 根拠

「書き手が開いている間の途中の内容を決して読まない」を取る代わりに、走査がハッシュを取る短い間(0.8MB で約 1 ミリ秒、48MB で数十ミリ秒)は、チャンクごとに開く書き手の次の `open` が共有違反になる。再試行しない書き手は、そのチャンクを失う。どのスクリーンショットのアプリも詰まらないことは、実際に使って確かめた(Snipping Tool。開発者の手元の実データで確かめた。データは公開していない)。ほかのアプリ(Steam・Xbox Game Bar・NVIDIA のオーバーレイ)は確かめていない。

読んでいる最中の書き足しは、ローカルのファイルシステムでは起きない。共有の検査は開くときに行われ、読み取りで開いている間は Write で開く要求が共有違反になる(NTFS・ReFS・FAT・exFAT で共通)。変わりうるのは、メモリマップして閉じた書き手と、共有を守らないネットワークのサーバだけで、スクリーンショットの用途の外である。

## 結果

- それでも、間を空けて追記する書き手の途中の内容は、1 度登録されることがありうる。書き終わったあとのサイズと更新日時の変化で、次の走査が新しいハッシュとして登録し直す。途中の内容のハッシュは、現存するパスの無い画像として残り、待ちに数えず、検索に出ない。結果を作る段階が途中の内容を読んでも、読んだバイト列のハッシュを DB の識別子と照合する(0003)ので、別の内容は弾かれる。害は、使われない画像の行が 1 つ残ることだけで、「インデックスの状態」の窓から消せる(0007)。
- 復帰と定期の走査は、「一時的に読めない」ファイルの 5 秒後の再走査を予約しない。次の監視のきっかけか、15 分ごとの定期の走査で拾われる。
- FAT・exFAT(更新時刻が 2 秒刻み)での確認は、していない。許容があるので、ずれても取りこぼしにはならない見込みである。
