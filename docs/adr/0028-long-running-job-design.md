# 0028. 長時間の処理は、画像 1 枚ずつ確定し、どこで止まっても続きから再開できるようにする

状態: 採用

## 背景

インデックス(検索のための下準備)の作成は、長時間かかる。特徴ベクトル(埋め込み。0011)は 1030 枚で約 83 秒だが、VLM(画像と文章を扱える AI モデル。ここでは、画像から、写っている文字・説明文・タグを作る。0018)は 1 万枚で約 36 時間である。使う人から見た問題は、数十時間かかる処理の途中でアプリを閉じたり PC を再起動したりしても、最初からやり直しにならないでほしいことである。その間に、次のことが起きる。

- 利用者が、ゲームの前に一時停止する、アプリを閉じる、PC をスリープさせる。
- アプリが強制終了される。
- GPU のセッションや llama-server が異常になる(0023・0026)。
- 新しい画像が、走査(0009)で入ってくる(0027)。
- 一部の画像が、開けない・壊れている・消える。

どの時点で止まっても、それまでの結果が失われず、続きから再開でき、状態が食い違わないことが要る。

## 決定

### 結果の確定と、待ち行列

- 画像 1 枚の結果は、1 つのトランザクションで確定する。埋め込みは、ベクトル・段階の状態(`stage_status`)・画像の幅と高さ。VLM は、書き起こし・説明文・タグ・段階の状態 2 行・検索用のテキスト・全文検索の文書。止めても、失うのは処理中の 1 枚だけである。確定は、キャンセルされない(`CancellationToken.None`)ので、始めた 1 枚は必ず確定する。
- 待ち行列は、メモリに持たず、毎回 DB から組み立てる。待ちとは、現存するパス(`missing_since` が無い)があり、その段階の `stage_status` に行が無い画像である。実行ごとに、飛ばした画像の hash の集合を持ち、次の問い合わせから除く(開けない画像は記録しないので、除かないと、同じ画像を取り直し続けて止まらない)。
  - 埋め込み: `images` の rowid 順に 256 件ずつ。CPU のワーカーが先読みする(有界のキューの容量は 8)。止まるときは、先読みした分を捨てる。
  - VLM: 新しい順(現存するパスの更新時刻の最大の降順、同じなら hash)に、8 枚ずつ(0027)。

### ジョブと段階

- 「段階」(`stage_status` の `stage` 列。どの結果を埋めたか)と、「ジョブ」(実行の単位。どのランナーを動かすか)を分ける。埋め込みのジョブは埋め込みの段階を、VLM のジョブは書き起こしと説明文の 2 つの段階を埋める。
- ランナー(`JobRunner`)は、`RunAsync(記録, 合図, キャンセル)` を実装し、次のどれかで戻る。例外にはしない。
  - `Drained`: 待ちが無くなった。
  - `Yielded`: 切り替えの合図(`shouldYield`)が立った。今の 1 枚を確定してから戻る。資源は握ったままで、`Indexer` が次のジョブを選ぶ。
  - `Cancelled`: キャンセル(停止・一時停止・終了)。境目が長いランナー(VLM は 1 枚約 12 秒)は、処理中の 1 枚を中断して、やり直す(`stage_status` を書かない=未処理のまま)。
- `Yielded` のたびに、「待ちが無くなった」の印を消して、ランナーを選び直す。ランナーが `Drained` で戻るまでの間に合図が立った場合も、合図を下ろして、印を消す(優先のランナーの新着を見落とさないため)。
- 一時停止は、ランナーに渡すキャンセルを切る → 止まるのを待つ → 資源を解放する、の順で行う。待ち行列は DB にあるので、失うものは無い。再開は、新しい実行(`runs` の行)として始まる。
- 実行の記録(`runs`)は、資源を作ってから空けるまでの 1 回ごとに作る。「どのビルドで作ったか」を残す(0006)。
- ジョブの致命的な失敗は、実行の `Task` を失敗させず、状態を `Failed` にして、理由(`LastError`)で伝える。一時停止または失敗のあとの再開・開始で、続きから動く。
- 失敗した画像のやり直しと、要再作成の画像の再処理は、`stage_status` の該当する行を消すだけである(待ち行列は「行が無い画像」なので、次の実行で処理される)。古いモデルの結果は消さない。

### 画像ごとの失敗の扱い(埋め込み)

- ファイルを開けない画像(消えた・取り外した・アクセス拒否)は、記録しない。`stage_status` の行を作らないので、失敗に固定されず、その実行では飛ばし、次の実行で再試行する。警告をログに出す。
- 読んだバイト列の SHA-256 が DB のハッシュ(0003)と違う画像は、そのパスを使わない(次のパスを試す)。
- 読めたがデコード・前処理できない画像、出力が NaN や無限大の画像は、失敗として記録して、先へ進む。
- GPU のセッションの作り直し(Run の例外のとき。次の節)に失敗したとき、ネイティブ環境の例外、次元の不一致は、致命的として、ジョブを止める(実行は `Failed`)。

### GPU のセッション

- ONNX Runtime の Run が例外になったら、セッションを破棄して作り直し、その 1 枚を 1 回だけ再試行する。作り直すたびに、自己検査(0015)も行う。再試行も失敗なら、その画像は失敗にする。作り直しそのものが失敗したら、致命的として伝え、以後のエンコーダは使えない。この責任は、ランナーでなく、エンコーダが持つ。

### スリープの抑止と復帰

- 実行中は、システムのスリープを抑止する(`SetThreadExecutionState` の `ES_CONTINUOUS | ES_SYSTEM_REQUIRED` だけ。画面は消えてよい)。この API はスレッド単位なので、専用のスレッドで持つ。ジョブが動いている間だけ持ち、一時停止・待機・失敗で解除する。始められなくても、警告だけでジョブは動かす。
- スリープからの復帰は、`PowerRegisterSuspendResumeNotification` で検知する。NuGet のパッケージは足さない(0026)。

### 進捗の通知

- 進捗(現在のパス・完了数・走査の進捗)は、100ms 以上の間隔に間引き、間引いた末尾の 1 回は必ず送る。実行の状態の切り替え(動作中・停止中・一時停止・待機・失敗)は、間引かずに即時に送る。
- 残り時間は、今のジョブの待ちだけで見積もる(別のジョブの待ちを足すと、桁が違う)。ジョブが切り替わるとき、速さの計算の窓をクリアする。

## 検討した案

- **待ち行列をメモリに持つ**: 再起動で消え、DB と食い違う。毎回 DB から組む。
- **結果をまとめてコミットする**: 中断で、まとめた分を失う。
- **処理中の 1 枚の確定まで、キャンセルを待つ(VLM でも)**: VLM は 1 枚 12 秒、大きい画像で約 100 秒(0025)かかるので、一時停止がすぐに効かない。VLM は中断してやり直す。埋め込みは、Run が約 66ms なので、境目で止める(これは契約でなく、埋め込みの実装の選択)。
- **ONNX Runtime の Run の例外を、そのまま画像の失敗にする**: セッションが壊れていると、以後の画像が全部失敗する。作り直して 1 回だけ再試行する。
- **開けない画像を、失敗として記録する**: 一時的な共有違反や取り外しで、失敗に固定される。記録せずに、次の実行で再試行する。
- **スリープの抑止を、UI のスレッドで持つ**: `SetThreadExecutionState` はスレッド単位で、スレッドが終わると効かなくなる。専用のスレッドで持つ。
- **復帰の検知に、NuGet のライブラリを使う**: 依存が増える(0026)。

## 根拠

- 1030 枚の通し(開発者の手元の約 1,000 枚。データは公開していない)で、VLM の実行は 3.34 時間で完走し(1 時間を超える背景の実行でも止まらなかった)、失敗 0 だった。途中の一時停止と再開(+100 枚で停止 → llama-server の終了、VRAM は起動前 + 147MiB → 再開、実行の記録は 2 行)も確かめた。
- 偽の llama-server(別プロセス。落ちる・止まる・遅い・不正な応答)に対するテストで、画像ごとの確定、境目での切り替えと中断(処理中の 1 枚は `stage_status` を書かない)、一時停止での llama-server の停止、再開は新しい実行、起動し直しとやり直し、開けない・書き換えられた画像を 64 件を超える量で飛ばしても `Drained` で終わること、を確かめた。
- スリープ・強制終了・サーバの異常の実機での確認は 0026。スリープの抑止は、実行中に `powercfg /requests` で確かめた(実行中だけ、システムの要求にアプリが出る)。
- 実行の終わり際(合図が `Drained` の直前に立つ場合)に新着を見落とさないことを、テストで固定している。

## 結果

- どの時点で止まっても、確定した結果は残る。再開は、DB の状態だけで、続きから動く。
- 一時停止は、埋め込みでは画像 1 枚(Run は約 66ms)の境目で効き、VLM では処理中のリクエストを中断してやり直す。
- 失敗した画像と、一時的に開けない画像を区別できる。
- 確定の途中でプロセスが殺されたときの、トランザクションの原子性は、SQLite に任せる。
- 実行の記録(`runs`)が、強制終了のときに閉じない(`ended_at` が空のまま)ことがある。製品の挙動に害は無い。

## 見直す合図

- 長時間の処理が、実際のライブラリで、想定外の止まり方をしたとき(休止状態、300 秒を超えるスリープなど。0026)。
- 一時停止が、VLM でなかなか効かないとき。リクエストの中断の仕方を見直す。
- 件数が設計上の上限(約 10 万枚)に近づいて、待ち行列の取り方が性能の問題になったとき。
