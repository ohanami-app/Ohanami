# 0007. 見つからなくなった画像は消さず、印を付けて残す

状態: 採用

## 背景

たとえば、外付けドライブに入れたスクリーンショットを検索するために、ドライブをつないだまま使っていて、ある日、ドライブを抜いたとする。このとき画像の結果を全部消すと、ドライブを挿し直したときに、数十時間かけて作った結果を作り直すことになる。ファイルは、移動・削除・外付けドライブの取り外し・ネットワークの切断で、走査(フォルダの中を調べ直して、画像の追加・変更・消失を DB に反映する処理)から見えなくなる。見えなくなった画像の結果(OCR・説明文・ベクトル・手動タグ)を消すと、同じ内容のファイルが戻ったとき(移動・復元・ドライブの再接続)に、数十時間分の結果を作り直すことになる(0006)。一方、見えない画像が検索に出続けると、ドラッグしても渡せない画像が結果に並ぶ。

## 決定

**見えなくなったパスは、`image_paths.missing_since` に時刻を入れて残す。** 行も、画像の結果も消さない。再び現れたら `missing_since` を空に戻す。検索の結果には、`missing_since` の無いパスを持つ画像だけを出す。同じ内容のファイルが別のパスに現れれば、`image_paths` に行を足すだけで、処理をやり直さずにすぐ検索できる。同じパスの内容が変わったら、その行のハッシュを更新する。古いハッシュの画像は、ほかにパスが無くても残す。

**到達できない場所には印を付けない。** 登録したフォルダの根が存在しない・列挙に失敗した(外付けドライブを抜いた、ネットワークが落ちた、アクセス拒否)ときは、その根またはサブディレクトリを、今回の走査の対象外にする。走査中に、列挙しようとして失敗したディレクトリの集合を作り、そのどれかの配下にあるパスは、見つからなくても `missing_since` を付けない。親の一覧に出てこなかった(削除された)ディレクトリは、この集合に入れない。根が存在しない場合は、削除と取り外しを区別できないので、根を集合に入れる。登録を解除するかどうかは、利用者が決める。記録は、走査の結果の `Unreachable` と `folders.last_error`(件数と先頭の最大 20 件のパスと理由。次の走査が成功したら消す)に残す。

**明示的に消す操作を別に持つ。** 見つからない画像の記録を、利用者が「インデックスの状態」の窓から消せる(0039)。対象は、現存するパスが 1 つも無い画像で、フォルダを外したために `image_paths` の行が無くなった画像も含む(外すと、パスの行だけが連鎖して消え、画像と結果は残る)。根に到達できないフォルダの配下は、印が付かないので対象にならない。消すものは、画像の行と、そこにつながる結果(パス・状態・ベクトル・説明文・手動タグ・全文検索の行)で、1 つのトランザクションで消す。

- 画像のハッシュを参照する表には `ON DELETE` が無い(連鎖するのはフォルダの識別子だけ)。外部キーは接続ごとに有効なので、子の表から順に明示的に消してから `images` を消す。
- 対象は、消すトランザクションの中で決める。数えてから消すまでの間に走査が戻した画像を消さないため。
- メモリ上の特徴ベクトルの表(0008)からも外す。外さないと、検索には出なくても、ベクトルの件数が次の起動まで合わない。
- インデックス作成の実行中(ジョブの実行中)は押せない。処理を進める部品が、取った待ちの画像のハッシュをメモリに持ち、消されたあとに結果を書くと、外部キーで失敗して実行全体が止まるため。
- サムネイルのディスクキャッシュ(ハッシュが鍵)は、残しても害が無いので消さない。

**走査の細部。**

- サブディレクトリを辿る。シンボリックリンク・ジャンクションのディレクトリは、循環を避けるため辿らない。ただし黙ってスキップせず、辿らなかった件数を `SkippedLinks` に数えて画面に出せるようにする(ジャンクションでフォルダをまとめている人に、画像が入らない理由が見えなくなるため)。登録した根そのものがリンクなら、根は辿る。
- 画像の形式は、拡張子ではなくファイルの先頭のバイト列(PNG・JPEG・WebP)で判定する。どれでもなければ `file_issues` に `unsupported` として記録する。拡張子が `.png` でも中身が JPEG なら、中身を信じる。
- 差分は、パスごとに更新日時とサイズを DB の値と比べ、違う・新しいときだけハッシュを取る(0003)。
- パスの比較は ASCII の大文字小文字だけを畳む。SQLite の `NOCASE`(ASCII だけ)と一致させ、メモリ上の突き合わせと DB の一意制約をずらさないため。ASCII 以外の大文字小文字の違いは別のパスになる。
- 検索の結果に載せるパスは、検索の時点では DB の印だけで決める。ファイルの実在は、検索では確認しない(ネットワークのフォルダや抜かれた外付けドライブで、検索が止まらないように)。実在の確認は、ドラッグ・コピー・エクスプローラーで表示を実行する時点で、App が `File.Exists` で行う。

## 検討した案

| 案 | 採らなかった理由 |
|---|---|
| 見えなくなった画像の行と結果をすぐ消す | 外付けドライブを抜いただけで全件が消えた扱いになる。戻ったとき、数十時間分を作り直す |
| 検索のたびにファイルの実在を確かめる | ネットワークのフォルダや抜かれたドライブで検索が止まる |
| 根に到達できないときも、見つからないものに印を付ける | 取り外しと削除を区別できない |

## 結果

- 移動・復元・ドライブの再接続のあと、作り直さずにすぐ検索できる。
- 消えた画像の記録は、利用者が消すまで DB に残る。「インデックスの状態」の窓で、枚数と、消すと失われるもの(処理結果と手動タグ)を見てから消せる。
- 同じ更新日時・同じサイズで内容だけが違う変更は、見逃す。更新日時とサイズで差分を取る選択の、既知の限界である。
- 検索結果に出た画像のファイルが、検索のあとで消えていることはありうる。ドラッグやコピーの時点で分かり、そのフォルダを走査し直す。

## 見直す合図

同じ更新日時・サイズで内容だけが違う変更が、実際の使い方で起きると分かったとき(ハッシュを取る条件を広げる)。
