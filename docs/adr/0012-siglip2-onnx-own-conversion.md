# 0012. SigLIP2 のモデルは、元の重みから ONNX 形式に自前で変換する

状態: 採用

## 背景

特徴ベクトル検索(0011)には、SigLIP2 の画像側とテキスト側のモデルが、ONNX(機械学習モデルの共通のファイル形式)の形で要る。入手できる完成品として、Immich が配布している ONNX(`immich-app/ViT-SO400M-16-SigLIP2-384__webli`。評価に使ったのはリビジョン `19baa26af70b`)を、試験的に使って評価した。入出力の形、出力の L2 正規化、前処理の仕様が揃っていて、torch なしで参照を動かせる。

ただし、その配布にはライセンスの記載が無い。このアプリを他の人に配るとき、同梱するモデルのファイルが「誰が、どの条件で、使ってよいと言っているか」を示せないと、配る側も受け取る側も、使ってよいかを判断できない。そのまま配布物に入れると、配布物の系譜に、ライセンスの分からない 1 者が入る。

元の重みは `timm/ViT-SO400M-16-SigLIP2-384`(Hugging Face のメタデータで Apache-2.0)にあり、Google の SigLIP2 を open_clip の形式にしたものである。big_vision の README は「コードベースは Apache 2」と書く。SigLIP 2 の README は「ソフトウェアは Apache 2.0、それ以外の資料は CC BY 4.0」と書く。チェックポイントにどちらが当たるかは、資料からは決められない。

## 決定

製品が使う ONNX は、元の重みから open_clip(SigLIP2 を読み書きするライブラリ)で自前に変換したものにする。変換の道具は `tools/convert-siglip2/`、出力は `models/ViT-SO400M-16-SigLIP2-384__ohanami/`(各ファイルの SHA-256 は `models/MANIFEST.tsv`)。

- 入力は固定する: `timm/ViT-SO400M-16-SigLIP2-384` のリビジョン `fec784dabb3081a5f101fc74eefaf9d1ed08237b` の `open_clip_model.safetensors`・`open_clip_config.json`・`tokenizer.json`・`tokenizer_config.json`・`special_tokens_map.json`。変換はネットワークから取らず(`HF_HUB_OFFLINE=1`)、この固定したファイルだけを読む。SHA-256 が MANIFEST と違えば止まる。
- 書き出しの仕様: fp32、opset 19、TorchScript の経路(`dynamo=False` を明示)、固定形状(バッチ 1)、入力名 `image` / `text`、出力名 `embedding`。`encode_image` と `encode_text` を `normalize=True` で書き出し、L2 正規化をグラフに含める。後処理は無い。テキスト側の外部データは 1 ファイルにまとめる。
- 出力の隣に `CONVERSION.json` を書く。入力の SHA-256、全パッケージの版、スクリプトの SHA-256 などを記録する。
- 変換は、リポジトリの外の venv(Python 3.10.11)で行う。製品とそのテストは Python に依存しない。変換は一度きりである。
- 製品のコード・DB に、比較に使った配布元の名前を入れない(製品の系譜は、上の自前変換だけである)。`SourceIdentifierTests` が、`src/` の識別子・文字列リテラル・ファイル名(DB に入る model_id や前処理の版は文字列リテラルなので、同時に守られる)を検査する。コメントは検査しない。比較に使った事実を説明するのは禁じない。
- 環境は固定する。`requirements.txt` は `pip freeze` の全件(推移的な依存を含む)で、`torch==2.6.0`(PyPI の Windows 版 = CPU 版)、`open_clip_torch==2.31.0`、`timm==1.0.15`、`onnx==1.17.0` などを含む。`transformers` は使わない。

## 検討した案

- **比較用の ONNX をそのまま配布する**: ライセンスの記載が無いので採らない。
- **配布元にライセンスを問い合わせて、返答を待つ**: 返答の有無と内容に依存し、配布の時期を相手に預けることになる。自前変換で必要なものは Apache-2.0 の重みと公開 API だけで済む。
- **自前変換(採用)**: 配布物の系譜が「Google → timm / open_clip → Ohanami」になり、間にライセンス不明の 1 者が入らない。同じ open_clip の経路なので、入出力の形・前処理・テキストの整理は、評価したものをそのまま使える。

## 根拠

受け入れ条件は、比較用の ONNX と数値的に等価なこと(すべての比較で 1 − cos ≤ 1e-5)とした。1 − cos は、2 つのベクトルの違いの指標で、0 なら同じ向き(同じ結果)である。変換した結果は、次のとおり一致した。

| 比べたもの | 結果 |
|---|---|
| 画像側の ONNX ファイル | SHA-256 まで一致(バイト同一) |
| テキスト側のグラフ(2448 ノード)と全 330 個の初期値 | バイト列が同一(外部データを 1 ファイルにまとめた分だけ、ファイルが違う) |
| 出力(合成画像 34 枚、テキスト 821 件、手元の画像 1030 枚。GPU) | すべてビット単位で一致(1 − cos の最大 2.2e-16、最大の差 0) |
| 検索の評価の出力(探したい 1 枚が決まっている検索の順位、上位 10 枚のうち当たりの割合、上位 10 件。0014・0037) | バイト同一 |
| GPU の測定(全ノードが CUDA EP、cuDNN が必要、破棄後 +127MiB、1 枚の Run 中央値 65ms) | 比較用の ONNX と同じ水準(0011 の破棄後 +136MiB は比較用の ONNX での測定、この +127MiB は自前変換の ONNX での測定) |

手元の画像 1030 枚は、開発者の手元の約 1,000 枚である。データは公開していない。

画像側の ONNX が SHA-256 まで一致したことは、2 つの事実の証拠になる。この変換が決定的であること(別のマシンでも、固定した環境で同じバイト列になる)と、比較用の ONNX の重みの出どころが timm の重みであること。

環境の固定: 比較用の ONNX が公開された日より前(2025-03-14 より前)の版に、パッケージを `pip install --uploaded-prior-to` で固定した。`requirements.txt` だけで新しい venv に導入すると、`pip check` が通り、`pip freeze` が `requirements.txt` と一致した。

実時間(開発機): 重みの取得(4.54GB)約 2 分、環境の導入約 3 分、変換約 1 分(変換の記録 CONVERSION.json では 63.9 秒。ワーキングセットのピークは約 9.4GiB)、受け入れの検証まで含めて約 45 分。ディスクは入力・出力・venv で約 10GiB。

## 結果

- 配布物の系譜が、Apache-2.0 の重みから Ohanami の変換までたどれる。
- 変換したモデルは、テスト用の正解の埋め込み(`tests/Ohanami.Core.Tests/TestData/`)を作り直しても、同じバイト列になった。
- `tools/convert-siglip2/convert.py` と `requirements.txt` のバイトは変えない。`CONVERSION.json` が、この 2 つの SHA-256 を記録しているため。変えるなら、変換をやり直す。
- venv のパスが長いと、onnx のテストデータのパスが Windows の MAX_PATH を超えて、導入が失敗する(`WinError 206`)。短いパスに置く。
- 変換したモデルの配布には、LICENSE と NOTICE(系譜)を付ける。チェックポイントのライセンスが Apache-2.0 か CC BY 4.0 かは、資料から決められない(未確認)。どちらでも再配布できるよう、帰属(作者・ライセンス名・リンク)と「ONNX に変換した」旨の明記を付ける。

## 見直す合図

- 元の重みのライセンスが明確になったとき、または変わったとき(LICENSE と NOTICE を直す)。
- 変換の道具・環境・入力の重みを替えるとき。受け入れ条件(1 − cos ≤ 1e-5)で比べ直し、`CONVERSION.json` を作り直す。
- 別のモデル(0011)に替えるとき。新しい model_id として扱う(0006)。
