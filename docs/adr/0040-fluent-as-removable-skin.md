# 0040. Windows 11 の見た目(Fluent)は、外せる皮として入れる

状態: 採用

## 背景

WPF の標準の見た目は、昔からのもの(Aero2)で、利用者が使っている Windows 11 のほかのアプリと並べると、古い画面に見える。Windows 11 の見た目(Fluent テーマ)は、.NET 9 から WPF に入ったが、.NET 9・10・11 のどれでも試験的な機能(コンパイラの警告 WPF0001)である。確かめた外部の事実を示す。

- テーマを指定する `ThemeMode` は `[Experimental("WPF0001")]` で、API の文書は「将来の版で削除されうる」と書く。チームの手引きは、見た目・読み込み方・リソースのキーの参照にも、壊れる変更がありうると書く。外す予定の公式の記載は無い。
- dotnet/wpf の既知の問題の追跡(#10393)に、このアプリが使う部品(ScrollBar・ListBox・ToolTip・ContextMenu・ProgressBar など)が、未完了として並ぶ。
- 標準の部品は自動で変わるが、自前で描いた一覧と、色の直書き(約 35 か所)は変わらない。暗い配色では、白地に白になる恐れがある。
- Fluent は、寸法を変える(ListBoxItem 21px → 43px、TextBox 19px → 32px、スクロールバーの幅 17px → 12px など)。画面を出さずに寸法を測るテストは、テーマを読まなければ、この変化に気づかず、最小のウィンドウの約束が、黙って検証されなくなる。
- 配布後に見た目が勝手に変わる範囲は、`.NET 10.0.x` の中だけである(このアプリは .NET 10 で動き、.NET 11 しか無い PC では起動しない)。10.0.11 と 10.0.14 で、Fluent の中身は全部同じだった(比べたのはこの 2 つだけ)。

## 決定

Fluent(ライト)を、いつでも外せる皮として入れる。守る決まりは 3 つ。

1. **テーマを読み込む入口は 1 か所にする。** `src/Ohanami.App/AppTheme.cs` が、Fluent のリソース辞書(`PresentationFramework.Fluent` の `Themes/Fluent.Light.xaml`)をコードで足す。アプリとテストが、同じ入口を通る。`Application.ThemeMode` は呼ばず、csproj 全体で WPF0001 を黙らせない。
2. **自前の色は直書きのまま、`src/Ohanami.App/AppColors.cs` の 1 か所に集める。** Fluent のリソースのキー(文字列)は、どこからも参照しない(キーは版で変わりうる。消えると、黙って既定値になる)。面の色(窓・一覧・詳細)と意味の色(エラーの赤・補助の灰)だけを自分で決め、Fluent の部品の色は Fluent に任せる。値は、Fluent の上でも、元の見た目の上でも読める値にしてある。
3. **窓の背景の Mica は切り、色を自分で決める。** Mica は、窓の背景に壁紙の色が混ざる素材で、壁紙で窓の色が変わると、面の色をそろえられない。AppContext の switch `Switch.System.Windows.Appearance.DisableFluentThemeWindowBackdrop` で切る(WPF が読む)。Mica を切っても、タイトルバーは壁紙の色のまま残るので、DWM の `DWMWA_CAPTION_COLOR` で、こちらの側から色を明示する。古い OS では効かない(戻り値は無視する。見た目だけの違い)。

外すときは、`AppTheme.Install` の 2 行とテスト用の `ApplyTo` の 1 行を消せば、元の見た目に戻る。3 つの決まりは、ソースを読むテストが見張る(`tests/Ohanami.App.Tests/ThemeGuardTests.cs`)。見張れない範囲(文字列でキーを組み立てる参照、リフレクション、別のアセンブリ経由)は、テストの冒頭に書いてある。

## 検討した案

| 案 | 採らなかった理由 |
|---|---|
| 元の見た目(Aero2)のまま出す | Windows 11 の標準の見た目と違う。下の条件を満たせば入れる方向で試した |
| 試験的でなくなるまで入れない | 外す予定が公式に無く、試験的でなくなる見込みが無い |
| 自前で Windows 11 風の見た目を作り込む | 下の条件を満たせず、それでもモダンな見た目が要るときは、自前で作るより先に、サードパーティの部品(WPF-UI など)を同じ条件で比べる(依存の追加には、AGENTS.md のとおり、理由の説明と承認が要る) |

## 根拠

次の条件を満たすときだけ入れる。Microsoft 側の修正を待つしかない不具合が 1 つでもあれば、入れない。見つかった不具合は、こちらの側の明示の指定で直せるものだけを許す。

| 条件 | 確かめる内容 | 結果 |
|---|---|---|
| 寸法 | テストをテーマつきで測るように直し、最小の窓の約束(1042×560 でフォルダ一覧が 2 行以上、詳細の画像が 256px 以上、「インデックス」欄は固定の 7 行で高さが動かない)が保てるか | テーマつきで測ると、最小の窓でフォルダ一覧が 2 行に足りなかった(テーマなしのテストは、黙って通っていた)。一覧の行の余白と区切り線の高さを明示して、約束を保った。詳細画面の右の欄の幅を 440 から 424 にした(内側の余白 8px の分)。最小の窓の大きさは変えていない |
| 実機での確認 | 日本語入力、入力欄の右クリック(Fluent で固まる報告がある) | どちらも問題なし。入力欄の右クリックは、アニメーションして出る |
| 見た目 | 直した形を見る | 見た目に問題は無かった。詳細画面の上のボタンの周りに余白が無いが、背景色がそろっていれば、あってもなくてもよいので、そのままにした |

細いスクロールバーのつかみやすさ、スクロールの滑らかさ、起動の時間は、測っていない。

## 結果

- Windows 11 の見た目で出る。
- .NET の版を上げるときは、見た目の確かめ直しが要る(寸法のテストが、テーマつきで測るので、約束の崩れは落ちるテストで気づける)。
- Microsoft 側で直せないものが残る。確認のダイアログ(`MessageBox`)は Fluent が当たらず、昔の見た目のままである。進み具合のバーは、0% のとき、太い灰色の帯に見える。どちらも、作り込まず、対応しない。
- 実際の見た目(テーマ)は、画面の外の描画のテストでは確かめられない(テストは `Application` を持たないので、根の要素に同じ辞書を足して測る)。実機でしか確かめられない部分がある。

## 見直す合図

Microsoft が `ThemeMode` を削除する、または見た目を壊す変更を入れたとき。.NET の版を上げるとき(寸法と見た目の確かめ直し)。
