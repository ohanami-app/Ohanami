# 0019. llama-server は、VRAM を 6.5GiB 以内に収める引数で起動し、VRAM はプロセスごとに測る

状態: 採用

## 背景

VLM(画像と文章を扱える AI モデル。ここでは、画像から、写っている文字・説明文・タグを作る。0018)を動かす llama-server(0017)は、起動の引数しだいで、使う GPU のメモリ(VRAM)・メインメモリ(RAM)・速度・出力が大きく変わる。使う人から見た問題は、VRAM が足りないと VLM が起動せず、画像の説明が作られないことである。対象環境は VRAM 8GB・RAM 16GB である。llama-server プロセスの VRAM のピークは 6,656MiB(6.5GiB)以下、ワーキングセットは 6GB 以下に収める必要がある。

測り方にも罠がある。GPU 全体の使用量から起動前の値を引く方法は、ほかのプロセス(ブラウザの動画再生など)の変動が混ざる。起動前のベースライン(測定を始める前の GPU 全体の使用量)も 128〜1016MiB とぶれる。

## 決定

llama-server は、次の引数で起動する(`src/Ohanami.Core/Vlm/LlamaServer.cs`、定数は `src/Ohanami.Core/Models/VlmCatalog.cs`)。

```
-m <gguf> --mmproj <mmproj> --host 127.0.0.1 --port <N>
-lm none -ngl 99 -c 8192 -np 1 -cram 0 --no-mmproj-offload
--image-max-tokens 3584 --no-webui
```

| 引数 | 決めた理由 |
|---|---|
| `--no-mmproj-offload` | 画像エンコーダ(mmproj)を CPU に置く。GPU に置くと VRAM が足切りを超える(下の表) |
| `-cram 0` | ホスト側のプロンプトキャッシュを無効にする。1 枚ずつ独立に処理するので役に立たず、ワーキングセットが増え続ける |
| `-lm none` | モデルを mmap(ファイルをメモリに割り当てて読む方式)でなく、メモリへ読み込む。mmap だと、ワーキングセットがページキャッシュの分だけ多く見える |
| `-ngl 99 -c 8192 -np 1` | 全層を GPU に載せる。文脈長は、文章(536 トークン)+ 画像の最大(3584)+ 出力(2048)= 6,168 が収まる大きさ。スロットは 1 |
| `--image-max-tokens 3584` | 画像トークンの上限(0025) |
| `--image-min-tokens` | 指定しない(既定のまま)。実際の画面で測った下の表と、合成の画像で測った後ろの節 |
| `--no-webui` | 画面(Web UI)を立てない。出力には影響しない(下の確認) |

リクエストは `temperature` 0、`response_format` に json_schema(0022)、`max_tokens` 2048(0023)で送る。

VRAM は、llama-server プロセスごとの専用 VRAM(性能カウンタ `GPU Process Memory\Dedicated Usage`)で測り、判定する。GPU 全体 − 起動前の値は、参考として併記するだけにする。足切りの判定は、一部の画像の測定でなく、評価の実行全体のピークで行う。

## 検討した案

- **mmproj を GPU に置く**(`--no-mmproj-offload` なし): 画像のエンコードが速い(プロンプトの処理が約 3 倍)が、VRAM が足切りを超える。採らない。
- **`--image-min-tokens 1024`**: 手書き/縦書きは良くなるが(再現率 81% → 88%)、小さい UI が大きく悪くなる(95% → 76%)。採らない(下の表)。
- **画像を上限いっぱいに拡大する**(`--image-min-tokens 3584`): 小さい字の濁点・半濁点の読み違いは減る(合成の画像で、c1(製品の起動のまま)の 0.39〜0.59 倍)が、測る前に決めた線(c1 が 5% 以上で、c2(c1 に `--image-min-tokens 3584` を足したもの)が c1 の 1/3 以下)をどの高さでも満たさない。1 枚の時間は 5.7 倍(15.6 秒 → 89.3 秒)になる。拡大した字は、元から大きい字に追いつかない(同じ高さで 16.7% 対 9.9%)。採らない。中間の設定(たとえば 1536・2048)は測っていない(下の節)。
- **flash attention を切る**(`-fa off`): CUDA の flash attention(注意機構の計算を速くする方式)で、Qwen3-VL・Qwen3.5 の画像の埋め込みがずれる、という llama.cpp の未解決の報告がある(SM86(RTX 30 系の GPU の世代)で最悪のトークンの cos が 0.638。大きい画像ほどずれ、CPU で動かすと flash attention なしと 0.2% 以内で一致する)。mmproj を CPU に置く構成は、この経路を通らない。mmproj を GPU に置いた run と CPU に置いた run で、OCR の精度の差はノイズの範囲だったので、flash attention の設定は比べず、切る必要も無い。
- **VRAM を GPU 全体の使用量 − 起動前で測る**: ほかのプロセスが混ざる(下の通しの例)。プロセス別の値を使う。
- **足切りを 大判の層の画像だけで判定する**: 候補によっては、大判の層だけでは通り、実行全体では超えた(4B Q8_0 は 大判の層で 6,602MiB、33 枚の実行全体で 6,828MiB)。実行全体のピークで判定する。

## 根拠

評価の画像は、開発者の手元の約 1,000 枚から選んだ 33 枚(0018)。足切りは VRAM 6,656MiB。測定は、起動前のベースラインがぶれるので、「ピーク − ベースライン」には ±数百 MiB の誤差を見る。

### mmproj の置き場所(8B Q4_K_M。大判の層の画像で測定)

| 構成 | VRAM(プロセス分のピーク) | 備考 |
|---|---|---|
| mmproj を GPU | 6,952MiB(足切り超) | ロード直後の待機時点で 6,901MiB |
| mmproj を CPU | 6,199MiB(合格) | ワーキングセットのピーク 3.2〜3.8GB。大判で 1 枚 35〜64 秒 |

スリープ明けに、mmproj を CPU に置く構成を測り直すと、ピークは 6,427MiB だった(起動前のベースラインのぶれの範囲)。

### `-cram 0`(34 枚を連続で流したとき)

| 設定 | ワーキングセット |
|---|---|
| 既定(`-cram` 8192MiB) | 2.3GB から 7.1GB へ増え続ける。`--image-min-tokens 1024` では 9.3GB |
| `-cram 0` | 約 2.3〜2.6GB で横ばい |

`-cram 0` の出力は、20 枚で完全に一致した(残りの 14 枚は確かめていない)。

### `--image-min-tokens`(8B Q4_K_M。難しい画像の層)

画像トークンは、VLM が画像を読むために、画像を区切った単位の数である。表の「素直な層」「難しい層」は、評価の画像の分け方である(0018。素直なセリフの画面 12 枚と、手書き/縦書き・小さい UI・装飾・大判の 14 枚)。再現率は、正解の隣り合う 2 文字の組のうち、出力に出てきた割合である(0018)。

| 設定 | 画像トークン(中央値) | 素直な層 再現率 | 難しい層 再現率 | 手書き/縦書き 再現率 | 小さい UI 再現率 | 1 枚の中央値 |
|---|---|---|---|---|---|---|
| 既定 | 823 | 96.88% | 91.50% | 81.25% | 95.38% | 12.9 秒 |
| 1024 | 約 1,150〜1,183 | 97.01% | 84.19% | 87.50% | 75.66% | 19.9 秒 |

1024 は、1024 トークン未満の画像をすべて拡大する(主流の約 1148×652 の画像も対象になる)。素直な層は同じ(ノイズの範囲)で、難しい層の全体が 92% から 84% に下がる。

### `--image-min-tokens 3584`(画像を上限いっぱいに拡大する。合成の 90 枚)

上の表は、実際の画面の難しい層で測った。ここでは、濁点・半濁点(゛゜)の読み違いが、字の大きさとどう関わるかを、合成の画像で測る。使う人から見た問題は、たとえば、画面に出た「ぼたん」が書き起こしでは「ほたん」になり、「ぼたん」で探しても当たらないことである。実際のスクリーンショットでは、文の意味から字を補えるので、字の形の読み違いが見えにくい。そこで、意味のない仮名の並びを描いた画像で測った。

- **画像**: 濁点・半濁点の付く字 25 種と、付かない字 44 種を、意味のない並びにした文(ひらがなの行とカタカナの行を交互に置く)を、背景 3 種(暗い・明るい・にぎやかな絵の上の半透明の窓)× 字の高さ 5 種(12・16・20・24・32 px)で描いた 90 枚。1 枚に約 120 字で、合計 10,800 字、うち濁点・半濁点の付く字が 6,478 字。画面の大きさは 1280×720 と 1024×576 が半々。正解は作った文なので、どのモデルの出力にも寄っていない。
- **再現**: 画像と正解は、`tools/Ohanami.KanaYardstick` が乱数の種から作る(同じ種なら同じバイト列)。手元の画像ではないので、画像も数字も公開してよい。
- **モデル・要求**: 8B Q4_K_M(0018)。同じ画像・同じ要求(`temperature` 0)を、c1 と c2 で流した。c1 は製品の起動のまま(`--image-min-tokens` なし)、c2 は c1 に `--image-min-tokens 3584` を足した。
- **数え方**: 正解と出力を 1 字ずつ並べ(編集距離)、濁点・半濁点を外した字が同じ置換を「濁点・半濁点だけの読み違い」とする。このうち、正解が濁点・半濁点の付く字(以下、濁字)のものが「濁誤」で、正解の「が」を「か」に(落)、「ば」を「ぱ」に(取違)、のように読み違えたもの。率は、濁字のうち濁誤になった字の割合。正解が付かない字なのに濁点・半濁点が付いた読み違い(付加。「か」を「が」に、のように)は濁誤に入れず、清音の字の誤りとして「清誤」に数える。清誤は、濁点・半濁点の付かない字の誤り(別の字への置換・読み落とし・付加)の率。[ ] は Wilson の 95% 区間。CER は 0018 の意味(正解と出力を 1 字ずつ並べて、置換・挿入・削除を数える)。
- **実倍率**: 元の画像に対する、画像の線形の拡大率。画像トークンは (幅 / 32) × (高さ / 32) に比例する(0025)ので、画像トークン(`prompt_tokens` − 536)から逆算した。c1 では 0.99〜1.00、c2 では 1280×720 の画像で 2.00、1024×576 の画像で 2.50。c2 の画像トークンは、90 枚すべてが 3,600(指定の上限 3,584 と 16 違う。理由は調べていない)。

**測る前に決めた線**: ある字の高さで、c1 の濁誤が 5% 以上、かつ c2 の濁誤が c1 の 1/3 以下なら「合」とし、拡大を採る方向で、中間の設定を測りに進む。満たさなければ「否」で、拡大の線は閉じる(中間の設定は測らない)。

下の表は、元の字の高さごとの、濁誤の率(%)と CER(%)。1 つの行は 18 枚で、濁字は約 1,295 字(背景 3 種と画面の大きさ 2 種を含む)。比は、c2 の濁誤 ÷ c1 の濁誤。「c1 の濁誤 ÷ 清誤」は、濁点・半濁点の付く字の濁点・半濁点だけの誤りが、付かない字の誤りの何倍か(率どうしの比。意味のない並びでの数字である)。

| 元の字の高さ | c1 の濁誤 | c2 の濁誤 | 比 | 線 | c1 の清誤 | c1 の濁誤 ÷ 清誤 | c1 の CER | c2 の CER |
|---|---|---|---|---|---|---|---|---|
| 12 px | 32.85 [30.3–35.4] | 19.20 [17.1–21.4] | 0.58 | 否 | 9.27 | 3.5 倍 | 29.77 | 14.40 |
| 16 px | 27.31 [25.0–29.8] | 10.57 [9.0–12.4] | 0.39 | 否 | 5.67 | 4.8 倍 | 24.68 | 8.98 |
| 20 px | 16.22 [14.3–18.3] | 7.18 [5.9–8.7] | 0.44 | 否 | 3.93 | 4.1 倍 | 16.11 | 6.06 |
| 24 px | 9.71 [8.2–11.4] | 5.47 [4.4–6.8] | 0.56 | 否 | 3.60 | 2.7 倍 | 11.44 | 4.49 |
| 32 px | 9.91 [8.4–11.7] | 5.65 [4.5–7.0] | 0.57 | 否 | 2.30 | 4.3 倍 | 8.43 | 4.63 |
| 全体(90 枚) | 19.20 [18.3–20.2] | 9.62 [8.9–10.4] | 0.50 | — | 4.95 | 3.9 倍 | 18.08 | 7.71 |

比は 0.39〜0.58 で、1/3(0.33)に届く高さは無い。背景と組み合わせた 15 の升(1 つの升は 6 枚)でも、すべて「否」。c1 の濁誤が 5% を下回る升は無く、c2 の濁誤が 5% を下回る升は、24 px・明るい背景(4.82%)の 1 つだけ。

濁誤の内訳(全体)は、c1 が落 685・取違 559、c2 が落 396・取違 227。付加(付かない字に濁点・半濁点が付いた)は、c1・c2 とも 2 字で、清誤に入っている。余計な字(画像に無い字を足す誤り)は、c1 で正解の字数の 0.10%(記号は 0 個)、c2 で 0.04%(記号は 0 個)だった(0021)。

下の表は、1 枚の処理時間(1 枚の平均、秒)。c2 は、画像の大きさに依らず、常に約 3,600 の画像トークンになるので、小さい画像ほど増え方が大きい。

| 画面の大きさ | c1 | c2 | 倍率 |
|---|---|---|---|
| 1024×576 | 12.6 | 89.9 | 7.1 倍 |
| 1280×720 | 18.6 | 88.8 | 4.8 倍 |
| 全体 | 15.6 | 89.3 | 5.7 倍 |

下の表は、「拡大したあとの字の高さ」(元の字の高さ × 実倍率)が同じ範囲の画像を、c1 と c2 で並べた濁誤の率(%)。拡大した字が、元から大きい字と同じに読めるかを見る。

| 拡大後の字の高さ | c1(元から大きい字。実倍率 0.99) | c2(元は 12〜16 px の字を拡大) |
|---|---|---|
| 22〜36 px | 9.81 [8.7–11.0](36 枚) | 16.63 [15.0–18.4](27 枚) |
| 36 px より大きい | (該当なし) | 6.61 [5.9–7.4](63 枚) |

同じ 22〜36 px でも、拡大した字(16.63%)は、元から大きい字(9.81%)より、区間が重ならないほど読み違えが多い。2 つの群は、画面の大きさと元の字の高さが違うので、字の高さだけを揃えた比較ではない。なぜ追いつかないかは調べていない。

読み取れること:
- 拡大は、濁誤をどの高さでも約 4〜6 割に減らすが、1/3 には届かない。減らしきれない分が、24 px・32 px でも 5〜6% 残る。
- 時間の代償が大きい(5.7 倍)。mmproj が CPU にあり(上の表)、画像のエンコードが画像トークンの数に比例して遅くなるため、と考えられるが、その内訳は測っていない。
- c1 の誤りは、字が小さいほど多い(12 px で 32.85%、32 px で 9.91%)。拡大しない今の設定では、元の高さが 12〜16 px の字は、意味のない並びでは、濁点・半濁点の付く字の 3 割前後が、濁点・半濁点を読み違えられる(合算 30.08%)。実際のゲームの画面で、この誤りがどのくらい出るかは測っていない(0021)。
- 合成の画像の 90 枚は、きれいな字を描いたものである。実際の画面の、装飾・縮小の影響は入っていない。

### `--no-webui` と `--image-max-tokens` の出力への影響

評価で使った構成に、製品が `--no-webui` と `--image-max-tokens 3584` を足した。33 枚と無作為の 40 枚(計 73 枚)を、製品の起動(0017)とクライアントで流したところ、書き起こし・説明文・タグが 73 枚すべて、評価のときの出力と完全に一致した(差 0)。

### VRAM の測り方

実際のライブラリ 1030 枚の通し(約 3.3 時間)の途中で、利用者がブラウザで動画を見た。GPU 全体の 200ms ごとのピークは 7,436MiB で、起動前の 653MiB を引くと 6,783MiB となり、足切り(6,656MiB)を超えて見えた。外部の使用が混ざった結果であり、この値を合格とは呼ばない。

そこで、プロセス別の測定を行った。

| 測定 | llama-server の専用 VRAM |
|---|---|
| 通しの後半(5 秒ごとの記録、654 標本) | 6,058MiB で一定(ブラウザは別に 310〜530MiB) |
| 別の起動での実験(1 秒ごと、469 標本。プロンプト全体のトークン数(画像 + 文章 536)が最大の 5 枚(2,252〜3,256。画像だけなら 1,716〜2,720)・4K の合成画像(プロンプト全体で 4,012。画像だけなら 3,476)・起動し直した直後の 1 枚) | 最小 5,944MiB、最大 6,058MiB(起動直後 5,952MiB、最初の 1 枚の途中で 6,058MiB になり、以後変わらない) |
| 評価時のピーク(GPU 全体 − 起動前) | 6,096MiB |
| 4K の合成画像(画像トークン 3,476) | 6,102〜6,122MiB |
| ベンチの新しい測り方(プロセス別) | 6,059MiB |

専用 VRAM は、起動時の確保(重み + `-c 8192` の KV(文脈の計算結果を覚えておく領域)+ 計算バッファ)でほぼ決まり、画像の大きさにも処理した枚数にも依らない。足切りの内側で、余裕は約 600MiB である。

## 結果

- llama-server は、プロセス単位で約 6,060MiB(約 5.9GiB)の VRAM と、約 2.6〜3.2GB のワーキングセット(プロセスが実際に使っているメインメモリ)で動く。VRAM 8GB の機械で、画像エンコーダ(約 2.2GiB。0011)とは同時に載らない(0027)。
- mmproj が CPU なので、画像のエンコードが遅い。大きい画像(大判の層)で 1 枚 35〜64 秒、4K 級の画像で 1 枚約 100 秒かかる(0025)。
- `-cram 0` なので、同じ画像を続けて処理するときのキャッシュの恩恵は無い。
- `--image-min-tokens` を指定しないので、画像を拡大しない。小さい字の濁点・半濁点の読み違いが出る(上の合成の画像の測定。0021)。
- どの値が model_id に入るかは 0006 に従う。出力に影響する `--image-max-tokens`・`--image-min-tokens` は入り、起動のほかの引数は入らない。

## 見直す合図

- 画像によって専用 VRAM が変わる測定(たとえば 4K で 6,200MiB を超える)が出たとき。上の「画像に依らない」という読みが崩れるので、通しからやり直す。
- llama.cpp・モデルを替えたとき(0017・0018)。VRAM と出力を測り直す。
- 対象環境の VRAM を増やすとき。mmproj を GPU に置いて速くできるか、測り直す。そのとき、画像の拡大(`--image-min-tokens 3584`)の時間の代償(1 枚 15.6 秒 → 89.3 秒)も測り直す。mmproj が GPU なら、画像のエンコードは約 3 倍速い(上の表)ので、代償が小さくなりうる。
- 起動のコールドスタート(電源を入れた直後)が問題になったとき。起動待ちの時間切れ(300 秒)の根拠は、モデルが OS のキャッシュにある状態の測定なので、見直す。
