# 0043. モデルのファイルは、利用者が「ダウンロード」を押したときだけ、Hugging Face から取る

状態: 採用

## 背景

Ohanami が動くには、2 組のモデルのファイルが要る。特徴ベクトル検索の SigLIP2(自前で変換した 4 ファイル、約 4.58GB。0012)と、VLM の Qwen3-VL(GGUF と mmproj の 2 ファイル、約 6.19GB。0018)で、合わせて約 10.8GB ある。zip には入れられない(1 ファイル 2GiB 未満。0042)ので、Hugging Face に置き、利用者の PC に取ってきてもらう。

使う人から見た問題は、次の 2 つである。

- たとえば、初めてアプリを開いた人が、何も押していないのに、数 GB の通信が始まったら困る。スクリーンショットを検索するアプリが、PC の外に何かを送っているのではないか、と疑われる。逆に、回線が途中で切れるたびに 4GB を最初から取り直すことになるのも困る。
- ファイルが壊れたまま置かれると、検索の結果が静かにおかしくなる(0020)。

このアプリは、次の約束をする。README・画面・ADR で、この文のまま使う。

> 画像・検索語・インデックスは、PC の外に出ません。ネットワークに出るのは、モデルのファイルを取るときだけです。「ダウンロード」を押すと、Hugging Face にファイルを要求します (相手には、IP アドレスと、取ったファイルが伝わります)。モデルを手で置けば、一度も接続しません。

この約束を、コードの作りで守る。

## 決定

**モデルのファイルは、利用者が「ダウンロード」を押したときだけ取る。押す前には接続しない。モデルがそろっていれば、通信は 0 回である。**

ダウンローダーは Core の部品(`ModelDownloader`。`src/Ohanami.Core/Models/`)で、`OhanamiCore` を開かずに使える(Core を開くには、モデルが要るため)。画面が使う口は、取る前の見積もり(`ModelDownloader.Plan`。ネットワークに出ない)、ダウンロード(`DownloadAsync`)、進み具合(`ModelDownloadProgress`)、失敗(`ModelDownloadException`)の 4 つである。

取り方は次のとおり。

- **URL**: `https://huggingface.co/<リポジトリ>/resolve/<コミット>/<ファイル>`。コミットを指すので、あとから上書きされても同じ中身が取れる(0020)。続きを取るときも、毎回この URL から始める(配信元の署名つきの URL は、有効期限があるので、覚えない)。取得元のリポジトリとコミットは、カタログの定数である(`ModelCatalog`・`VlmCatalog`)。`EmbeddingModelSpec` には入れない(入れると、今ある DB の `models` の行が、キーの過不足で読めなくなる)。
- **ホスト名**: `huggingface.co` の文字があってよいのは、`ModelCatalog` だけである。ファイルの実体は、`huggingface.co` ではない別のホスト(配信元の CDN)から来る。失敗したときは、最後に接続したホスト名を、例外に持たせる(ファイアウォールで許可するのに要る)。
- **送るもの**: GET だけ。Cookie・認証・Referer・利用者や PC を表す値は付けない。`User-Agent` は、固定の文字列(`Ohanami`)である。
- **途中から再開する**: `<ファイル>.part` に書き、続きは `Range: bytes=N-` で頼む。206 のときは、`Content-Range` の開始が N で、全体のサイズが定義と同じことを確かめる。200 のときは、`Content-Length` が定義と違えば、本文を読む前に止める。Range を無視して 200 が来たら、足さずに 0 から書き直す。416 は、`.part` を消して 0 から 1 回だけやり直す。HF だけの `X-Linked-ETag`・`X-Linked-Size` は、判定に使わない(判定は、標準のヘッダのサイズと、最後の SHA-256)。
- **検証**: 取り終わったら、`.part` を、モデルの検証と同じ関数(`ModelVerifier.VerifyPathAsync`)で検証し、同じフォルダの中で改名する(同じフォルダなので、改名は一瞬で、途中の状態が残らない)。サイズか SHA-256 が違えば、`.part` を消して止める。**自動では取り直さない**。取りながらのハッシュはしない(中断と再開で、ハッシュの状態を持ち越さないため。数 GB の読み直しは数秒で済む)。
- **止まりの検出**: 本文の読み取りごとに、一定の時間(既定 30 秒)1 バイトも来なければ、接続を切って、続きから再開する(`ResponseHeadersRead` で読むとき、`HttpClient.Timeout` は本文に効かない)。切れた・止まったときは、続きから自動で再開し、進みが無いまま 3 回続けて切れたら、止める(進んだら数え直す)。
- **取る前の確認**: 置き場の空きと残りのサイズを比べる(余裕 64MiB を足す)。足りなければ、何も取らずに止める。
- **スリープの抑止**: ダウンロードの間は、ジョブと同じ `SleepGuard` で、スリープを抑える。
- **置き場**: 検証が読む場所と同じ 1 つ(`AppPaths` が決める `ModelDirectory`・`VlmModelDirectory`)。
- **失敗**: 状態コード(404・403・429・5xx など)・サイズの食い違い・SHA-256 の食い違い・止まり・接続の失敗・空き不足・ファイルの書き込みの失敗を、種類つきの例外(`ModelDownloadException`)で返す。画面が、手で置く方法(置き場とファイル名)と一緒に出す。

**約束を、テストで守る**(`NetworkBoundaryGuardTests`)。製品のコード(`src/` のすべて。コメントは除く)を読んで、「式・許すファイル・理由」の表と照らす。

- ネットワークの API(`HttpClient`・`System.Net`・ソケットなど)を使ってよいのは、127.0.0.1 の llama-server とやり取りする `LlamaServer.cs`・`VlmClient.cs` と、`ModelDownloader.cs` だけ。
- `huggingface.co` の文字があってよいのは、`ModelCatalog.cs` だけ。URL のリテラルは、`ModelCatalog.cs` と、127.0.0.1 の `LlamaServer.cs` だけ。
- GET 以外の送信は、127.0.0.1 の VLM への依頼(`VlmClient.cs`)だけ。Cookie・認証は、どこにも無い。
- ダウンロードを始める呼び出し(`ModelDownloader` を作る・`DownloadAsync` を呼ぶ)は、画面の 1 か所だけ。画面ができたら、その 1 か所のファイル名を、表に足す。

## 検討した案

| 案 | 採らなかった理由 |
|---|---|
| 初回の起動で、自動でダウンロードを始める | 約束(押したときだけ)と、利用者の予想に反する |
| 取りながら SHA-256 を計算する | 中断と再開で、計算の途中の状態を持ち越す必要がある。取り終わったあとの検証(数秒)で足りる |
| `HEAD` で、サイズと SHA-256(`X-Linked-*`)を先に取る | HF だけのヘッダに頼る。送るのが GET だけ、という約束も単純でなくなる。サイズは、取り始めの応答のヘッダで確かめられる |
| 配信元の署名つきの URL を覚えて、再開に使う | 有効期限がある。毎回 `resolve` の URL から始めれば、覚えなくてよい |
| ハッシュが違ったとき、自動で取り直す | 同じ誤りを繰り返して、数 GB の通信を無駄にしうる。原因(取得元・回線・ディスク)を、利用者が見て決める |
| NuGet のダウンロード用のライブラリ | 依存を増やさない方針。.NET の `HttpClient` で足りる |

## 根拠

- ダウンローダーは、`HttpMessageHandler` を渡せる作りで、テストは偽のサーバーの応答だけで動かす。**ネットワークに出るテストは無い**。確かめたこと: 200・206・Range の無視・416・途中で切れる・本文が途中で終わる・止まる(再開・諦め)・進みが無いまま続く失敗・サイズ違い(`Content-Length`・`Content-Range`・本文が多い)・SHA-256 違い・空き不足・各種の状態コード・リダイレクトの先のホスト名・キャンセルのあとの再開・`.part` からの再開。送ったリクエストが GET だけで、`User-Agent` 以外のヘッダが無いことも確かめた。
- 見張りのテストは、ネットワークの API や `huggingface.co` を、許可の外のファイルに足すと、落ちることを確かめた。
- Plan の見積もりは、カタログの定義(4 ファイルと 2 ファイル、合計 10.8GB)と一致する。

## 結果

- モデルがそろっていれば、通信は 0 回。押す前には接続しない。
- 回線が切れても、続きから取れる。壊れたファイルは置き場に出ない(検証が通ってから、同じフォルダの中で改名する)。
- SigLIP2 は、Hugging Face のリポジトリ(`ModelCatalog.HfRepository`。`ohanami-app/siglip2-so400m-patch16-384-onnx`)のコミット `32f87634e7700a4267cef3ffe700b10fe077112f`(`ModelCatalog.HfRevision`)から取る。置いたファイルは、カタログと同じ相対パス・同じ大きさ・同じ SHA-256(リポジトリの公開の情報で、4 ファイルの大きさと SHA-256 が定義と一致することを確かめた)。コミットの定数が本物であることは、テストでは確かめていない(ネットワークに出るテストは作らない)。
- 実際の Hugging Face と配信元への接続(`User-Agent` が無くても通るか、リダイレクトに `Range` が付いたまま 206 が返るか、など)は、テストでは確かめていない。
- ダウンロードの画面は、別に作る。画面は、上の 4 つの口を使い、失敗のときに、手で置く方法を案内する。

## 見直す合図

- Hugging Face が、固定の `User-Agent`・`Range` を受け付けなくなったとき。
- 取得元をほかのサービスに替えるとき(`huggingface.co` の見張りの表を、ホスト名ごと見直す)。
- ダウンロードを始める場所が、画面の 1 か所で足りなくなったとき(表に足す前に、約束(押したときだけ)を破らないかを確かめる)。
