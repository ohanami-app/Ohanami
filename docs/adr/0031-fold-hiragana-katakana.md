# 0031. テキスト検索は、ひらがなとカタカナを同じ文字として探す

状態: 採用

## 背景

画面の文字は、同じ語がひらがな・カタカナのどちらでも書かれうる。たとえば画面に「ネコ」とあるとき、利用者は「ねこ」と打つかもしれない。検索の側は、どちらで書かれているかを知らない。実際に、画面でカタカナで書かれた名前を、ひらがなで打つと 0 件になった。対象は、テキスト検索(VLM が作った OCR・説明文・タグと、手動タグの文字を、全文検索で探す検索)である(0029)。

## 決定

全文検索の正規化に、1 文字から 1 文字への写像を足す。NFKC と小文字化のあとに、カタカナをひらがなへ写す(`src/Ohanami.Core/FullText/KanaFold.cs`)。

- `U+30A1`〜`U+30F6`(`ァ`〜`ヶ`。`ヴ`・`ヵ`・`ヶ` を含む)を `U+3041`〜`U+3096` に、`ヽ` を `ゝ` に、`ヾ` を `ゞ` に写す(どれも差は 0x60)。
- 長音符 `ー` と、対応するひらがなが無い文字(`ヷ`〜`ヺ`)は写さない。半角カナは NFKC で全角のカタカナになってから写る。
- 濁点・半濁点の有無は区別したままにする(「か」と「が」は別の文字)。
- 写像は `NormalizedText.Create` の中の 1 か所に置く。索引・検索語・強調表示の 3 つが同じ `Create` を通るので、片側だけに入る事故が起きない。
- 正規化の版を `nfkc-lower-kana1` に上げる。次に開くとき、索引が作り直される(0030)。VLM の再処理は要らない。
- 特徴ベクトル検索(SigLIP2。検索語をベクトルにするテキスト側)には入れない。モデルの入力を変えないため。手動タグの名前の正規化(`ManualTagName.Normalize`)も別で、ひらがなとカタカナだけが違うタグが、勝手に 1 つにまとまることは無い。

## 検討した案

| 案 | 採らなかった理由 |
|---|---|
| 設定で切り替えられるようにする | 同一視によって困る例が見つかっていない。切り替えの設定を持つと、索引の規約が 2 通りになる |

## 根拠

1 文字から 1 文字への写像なので、正規化後の位置と元のテキストの位置の対応(強調表示が使う)が保たれる。写す前と後で、どちらも「日本語の文字」と判定され、分割の種類が変わらないことを、写像の範囲全体でテストする。

具体例を作って確かめた。カタカナで書かれた語の文書があるとき、変更前は、その語をひらがなで打つと 0 件だった。変更後は、ひらがな・カタカナ・半角カナのどれで打っても同じ件数に当たる。濁点を落とした綴りは、0 件のままである(区別を残したため)。

検索の回帰ベンチ(0037。変更で検索の質が下がっていないかを確かめる道具)で、変更の前後を比べた(開発者の手元の約 1,000 枚で測った。データは公開していない)。known-item は、「探したい 1 枚と、そのとき打つ検索語」の組で、目的の画像が上位 20 位以内に入るかを数える。precision@10 は、検索語ごとの上位 10 枚のうち、当たりの割合である。

| 項目 | 結果 |
|---|---|
| 索引の作り直し(1,030 枚) | 304ms。VLM の再処理なし |
| 上位 20 位以内だった known-item が、外へ落ちた | 0 件 |
| known-item が上がった | 0 件 |
| 順位が 1 つ後ろへずれただけの行 | 4 行(見た目で探す known-item 3 件。まとめた結果とテキスト検索) |
| precision@10 の当たりの数 | 特徴ベクトル検索・テキスト検索・まとめた結果の 3 つとも同じ(基準線の推移は 0037 の表) |
| テキスト検索のみの、返した件数 | 152 → 153 |
| テキスト検索のみの「返した分の当たり率」(当たり ÷ 返した件数) | 76.3%(116/152)→ 75.8%(下限。116/153) |

当たり率の 0.5 ポイントの低下は、新しく当たった 1 枚が、判定済みの組に無く、未判定のまま外れとして数えたためで、判定すれば決まる。1〜2 件の差は採否の根拠にしない、という決まりに従い、採った。

## 結果

- ひらがな・カタカナ・半角カナの書き分けで、引けなくなることが無い。
- `ヷ`〜`ヺ` と、ひらがなのある文字の濁点・半濁点の違いは、同一視しない。

## 見直す合図

同一視によって、別の語が同じ語として当たる偽陽性が、実際の使い方で目立ったとき。
