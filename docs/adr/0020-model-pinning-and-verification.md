# 0020. モデルのファイルは、配布元のコミットと SHA-256 で固定し、使う前にすべて検証する

状態: 採用

## 背景

製品が使うモデルは 2 つある。画像と検索語を特徴ベクトルにするモデル(SigLIP2。0011・0012)と、VLM(画像と文章を扱える AI モデル。ここでは、画像から、写っている文字・説明文・タグを作る。0018)。合計で約 10.8GB のファイルで、結果(ベクトル・書き起こし・説明文)はモデルのファイルで決まる(0006)。使う人から見た問題は、ファイルが壊れていたり、別のものに入れ替わっていたりしても、アプリが気づかずに動き続けると、検索の結果が静かにおかしくなることである。

- Hugging Face(HF。モデルの配布サイト)のリポジトリは、公式のものも第三者のものも、同じ名前のファイルを上書きすることがある。ファイル名だけでは固定にならない。
- 同じモデル名でも、アップロード元が違えば、チャットテンプレートやトークナイザのメタデータが違うことがある。評価したファイルと違うファイルを使うと、評価が成り立たない。
- 配布の途中や、利用者が手で置いたときに、ファイルが壊れる・取り違えられることがある。黙って誤った結果を作るのが最悪である。
- 起動のたびに数 GB を読む検証は、時間がかかる。

## 決定

モデルは、Hugging Face のコミットリビジョンを指した場所と、ファイルの SHA-256 の組で固定する。製品は、使う前にすべてのファイルをストリームで SHA-256 検証し、不一致なら止める。

- 固定する値は、リポジトリ・リビジョン(コミット)・ファイル名・サイズ・SHA-256 である。コードの定数に持つ(埋め込みは `src/Ohanami.Core/Models/ModelCatalog.cs`、VLM は `src/Ohanami.Core/Models/VlmCatalog.cs`)。`models/MANIFEST.tsv` は開発用の記録で、製品は読まない。テストが定数と MANIFEST を突き合わせる。
- 公式か、第三者か、利用者自身がホストしたものかで、製品のコードは変えない。違うのは、誰がホストしているかだけである。リポジトリが消えたときの保険として、SHA-256 が一致するファイルを所定の場所に手で置けば動く経路を持つ。
- 採用するファイルは、その 1 ファイルで評価し直してから固定する。品質が同点なら、公式のファイルを採る。
- 取得の URL は、`https://huggingface.co/<repo>/resolve/<リビジョンのコミット>/<ファイル名>` の形にする。コミットを指すので、あとから上書きされても同じ中身が取れる。
- ファイルの探し方は、環境変数 `OHANAMI_MODELS_DIR` → アプリのディレクトリから親へたどって最初に見つかる `models/<名前>` → データのディレクトリの `models\<名前>` の順である(`src/Ohanami.App/AppPaths.cs`)。
- 検証の時機は次のとおり。
  - **埋め込み**: 起動時に、テキスト側(約 2.87GB)をストリームで SHA-256 検証し、終わったら検索が使える状態になる。画像側(1.71GB)も起動時に裏で検証するが、結果は待たない。画像エンコーダを作る時点で参照し、検証が終わっていなければ待つ。不一致なら、エンコーダは `Failed` になる。起動のたびに検証し直す(検証済みの記録を持たない)。
  - **VLM**: 最初の VLM のジョブの頭で、GGUF と mmproj を SHA-256 検証し、`llama-server.exe` の SHA-256 と `--version` の出力(ビルド番号とコミット)を定数と比べる(0017)。同じプロセスの中では、(パス・サイズ・更新日時・期待する SHA-256)が同じなら再検証しない。一時停止からの再開のたびに約 8 秒を払わないためである。
- 不一致やファイルが無いときは、`ModelMismatchException` で止める。埋め込み側は起動で `Failed` になり、足りないファイル名が画面に出る。VLM 側はジョブの開始時の検証で失敗し、理由が画面に出る。

## 検討した案

- **ファイル名だけで固定する**: 上書きされると、中身が変わっても気づけない。
- **コミットを指さない URL で取得する**: 上と同じ。リポジトリの最新を取ることになり、結果が再現しない。
- **ハッシュだけで固定し、取得の場所を固定しない**: 取得元が消えたときの手がかりが無い。場所とハッシュの組にして、手で置く経路も持つ。
- **サイズと更新日時で、検証済みとみなす**(埋め込み側): 検証が速くなるが、ディスク上の改変や取り違えを見逃す。起動のたびに検証する。約 4.58GB を 800MB/秒で読むと、約 5.7 秒である(算術)。
- **VLM も起動のたびに、再開のたびに、検証し直す**: 一時停止と再開を繰り返すたびに約 8 秒かかる。同じプロセスの中では省略する。ディスクの改変は、プロセスを起動し直すと検出できる。
- **モデルを同名の別のファイルに黙って差し替える**: 評価したファイルと、使うファイルが食い違う。

## 根拠

- ファイルの読み込みは、ストリームのまま SHA-256 を計算する。実測では約 805MB/秒(1 万枚の画像を約 10 秒で処理する速さ。0003)。埋め込みの合計 4.58GB で約 5.7 秒、VLM の GGUF(5.0GB)と mmproj(1.16GB)で約 8 秒(どちらも算術)。
- Hugging Face の配布は、コミットを指した `resolve` の URL で、次のように返る(公開ファイルに、Range つきで 1KB だけ取って確かめた)。認証は不要。302 で CDN の署名つき URL に移る。ヘッダに `X-Repo-Commit`・`X-Linked-Size`(サイズ)・`X-Linked-ETag`(SHA-256。`MANIFEST.tsv` の値と一致した)・`Accept-Ranges: bytes` がある。ダウンロードの前に、HEAD でサイズと SHA-256 を突き合わせられる。Range つきの GET は 206 で返る。
- 実体は `huggingface.co` 以外のホスト(CDN)から来る。`huggingface.co` だけを許可するファイアウォールでは足りない。
- 起動の検証は、実物のファイルで、定数と一致した(GGUF・mmproj・`llama-server.exe` の SHA-256 とビルド番号)。

## 結果

- 評価したファイルと、使うファイルが、必ず一致する。モデルを替えるときは、定数を意図して書き換える(新しい model_id になり、全件が要再作成になる。0006)。
- 起動のたびに、埋め込みのモデルの読み込みに数秒かかる。
- ダウンロードの経路は、まだ持たない。モデルが無いときは、足りないファイル名を画面に出す。取得の機能は別の決定で扱う。
- 公式のファイルが上書きされても、リビジョンを指しているので、元のファイルを取れる。
- `ggml-cuda.dll` などのビルドの同梱物は、個別にはハッシュしない(0017)。

## 見直す合図

- モデルの取得(ダウンロード)を実装するとき。HF の無認証のレート制限・10GB を超える配布・レジューム・取得元のホスト(CDN)の扱いを確かめる。
- ディスクの改変の検出が、再開のたびに必要になったとき(同じプロセスの中での省略をやめる)。
- 検証の時間が起動の待ち時間として問題になったとき。
