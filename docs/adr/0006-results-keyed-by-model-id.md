# 0006. 画像ごとの結果は、作ったモデルごとに別々に残し、モデルが替わっても自動では作り直さない

状態: 採用

## 背景

画像ごとの結果(特徴ベクトル、VLM の OCR・説明文・タグ)は、どのモデルで作ったかで中身が変わる。利用者がモデルを入れ替えたとき、これまでの結果を失いたくない。モデルやプロンプトを替えたとき、古い結果を上書きして失うと、VLM の数十時間分の結果が消える。一方、替えるたびに自動で作り直すと、1 万枚の VLM が約 36 時間、画像ごとの特徴ベクトルの作成が約 14 分かかる。ゲームをしている間に GPU を取られることにもなる。

## 決定

**結果を、画像の識別子(0003)と、どのモデル・設定で作ったかを表す識別子 `model_id` の組で持つ。** `image_vectors` と `captions` は `UNIQUE (model_id, hash)` で、モデルを替えても古い結果は消えず、新しい結果と混在してよい。`stage_status` は「その画像のその段階を、今の `model_id` で処理したか」を指すだけの記録で、結果そのものは持たない。

**`model_id` は、結果の中身を決めるものだけから作る。** 値は、モデルの種類を表す名前に、正準な文字列(UTF-8、改行は LF)の SHA-256 の先頭 12 桁をつなぐ。

| 入れるもの | 特徴ベクトルのモデル(`EmbeddingModelSpec`) | VLM(`VlmSpec`) |
|---|---|---|
| ファイル | 4 つのファイルの SHA-256: 画像側の ONNX(モデルのファイル形式)、テキスト側の ONNX、テキスト側の ONNX の外部データ(`textual/model.onnx_data`。重みの本体)、文字の区切り方の定義(トークナイザ) | 2 つのファイルの SHA-256: GGUF(VLM のモデルファイル)と mmproj(画像を読む部分のファイル) |
| 仕様の版 | 画像の前処理の版 `siglip2-squash384-bicubic-pillow-v1`・テキスト整理の版 `siglip2-textclean-v1`(中身は 0013) | プロンプトと JSON スキーマの SHA-256 |
| 設定 | 次元(1152)・正規化(L2) | 温度(0)・チャットテンプレートの追加引数・画像トークンの下限(既定)と上限(3584。0025) |

入れないものは、ファイルのパスとサイズ、ONNX Runtime の版、llama-server のビルド、`max_tokens`、再試行の設定、`-ngl` などのメモリの設定である。これらは、結果を作った実行の記録として、実行の単位ごとの `runs` 表(アプリのビルド、実行環境の JSON)と、結果ごとの設定(`captions.settings_json`、失敗は `stage_status.settings_json`)に残す。成功した結果の設定は `captions` だけが持ち、`stage_status` と二重に持たない。

**今の `model_id` と違うモデルで作った結果は「要再作成」として数える。** 自動では作り直さない。利用者が、段階(特徴ベクトルの作成、VLM の処理)ごとに手動で始める(0039)。作り直すまで、特徴ベクトル検索(絵の近さで探す検索)は今のモデルの行だけを読むので、その画像は出ない。テキスト検索(VLM が作った OCR・説明文・タグと、手動タグの文字を、全文検索で探す検索)は、画像の最新の結果から索引の文書を作る(0030)ので、古い結果のまま引ける。

## 検討した案

| 案 | 採らなかった理由 |
|---|---|
| 画像ごとに最新の結果だけを持つ(hash を主キーにして上書きする) | モデルを替えたとき、旧モデルの数十時間分の結果が消える |
| ONNX Runtime や llama-server のビルドも `model_id` に入れる | 部品を 1 つ上げるだけで全件が要再作成になる(特徴ベクトル約 14 分・VLM 約 36 時間)。ビルドが違うと結果が変わるかは別に確かめる事柄で、変わらない限り同じモデルとして扱う。どのビルドで作ったかは `runs` から辿れる |
| 画像側とテキスト側を別々の `model_id` にする | 1 つにまとめた場合は、テキスト側だけ替えても全件の特徴ベクトルの作り直しになる。作り直しは 1 万枚で約 14 分なので、この単純さを取った。数値が等価(1 − cos ≤ 1e-5)なら既存のベクトルを引き継ぐ手もあるが、入れていない |
| モデルが替わったら自動で作り直す | GPU を占有し、VLM は日単位かかる。ゲーム中に勝手に動かない取り決め(0027)に反する |

## 結果

- モデルを替えても過去の結果は残り、検索から消えない(テキスト検索)。古い結果の画像は、作り直しを始めるまで特徴ベクトル検索には出ない。
- プロンプトや JSON スキーマを変えると新しい `model_id` になり、全件が要再作成になる。変更の費用が大きい(VLM は約 36 時間)ことを、画面で伝える必要がある。
- ONNX Runtime や llama-server のビルドを上げても、全件の再処理にはならない。ビルドの違いで結果が変わりうるが、それは `runs` を見て調べる。結果が変わることが分かったときは、その差を理由に `model_id` に入れるかを決める。
- 起動時に `models` 表の行を読むたび、構成から `model_id` を再計算して照合する。不一致・壊れた構成の記録・知らない種類・同じ ID で中身が違う行は `ModelMismatchException` で止まる。
