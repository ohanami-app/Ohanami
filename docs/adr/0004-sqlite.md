# 0004. DB は SQLite にする

状態: 採用

## 背景

利用者のスクリーンショットについて、画像の管理情報・OCR と説明文・検索用の索引・特徴ベクトル(画像の特徴を表す数値の並び)・手動タグを、1 つのローカルなストアに持つ。クラウドなどの外部のサービスは使わず、利用者が別途データベースをインストールすることも無い。設計上の上限は 10 万枚で、読み書きは 1 台の PC の中で完結する。

## 決定

DB は SQLite(`Microsoft.Data.Sqlite`)にする。ファイルは `%LOCALAPPDATA%\Ohanami\ohanami.db` である。

- 全文検索は SQLite の FTS5 で作る(0029)。
- 特徴ベクトルは普通の表に入れる(0008)。
- ジャーナルは WAL(書き込みを別ファイルに溜めて、読み取りを妨げない SQLite のモード)。書き込みの接続は 1 本にして、アプリ側のセマフォ(同時に 1 つだけ通す仕組み)で直列にする。読み取りは用途ごとの短命の接続で行い、WAL なので書き込みを妨げない。接続のたびに `foreign_keys`・`synchronous`・`busy_timeout` を明示的に設定し、既定値に頼らない。接続プールは使わない(Dispose でファイルが確実に閉じるように)。
- スキーマの版と移行の守りは 0005 に書く。

## 検討した案

| 案 | 採らなかった理由 |
|---|---|
| Turso(SQLite を作り直した新しいデータベース) | ベータ版で、リスクが利点に見合わない |
| LanceDB(ベクトル検索向けの組み込みデータベース) | 実験的な機能と、コミュニティ製の SDK に頼ることになる |

## 結果

- 追加のインストールが要らず、1 ファイルで完結する。バックアップも複製もファイルのコピーで済む。
- 同時に書ける接続が 1 本なので、書き込みが重なるときは待つ。1 枚の結果を 1 トランザクションで確定する作り(0028)は、この直列化を前提にしている。
- 組み込みの SQLite の機能(FTS5 の分割方式 `unicode61`、列の型を厳密に検査する `STRICT` テーブル)の範囲で作る。日本語の全文検索は、SQLite の機能だけでは足りず、C# 側で分割して補う(0029)。

## 見直す合図

件数が設計上の上限(10 万枚)を超えて、書き込みの直列化や総当たりのベクトル検索(0008)が待ち時間として問題になったとき。
