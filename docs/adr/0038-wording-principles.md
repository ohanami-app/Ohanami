# 0038. 画面の語は、使う人の目的の言葉で書き、正確な技術名をヒントに添える

状態: 採用

## 背景

このアプリは、SigLIP2(画像と検索語をベクトルにして近さで探すモデル)・VLM(画像と文章を扱える AI モデル。ここでは、画像から、写っている文字・説明文・タグを作る)・OCR(画面の文字の読み取り)・CUDA(GPU で計算する仕組み)・FTS5(SQLite の全文検索機能)といった技術でできている。画面の文字を、どの層の言葉で書くかが決まっていないと、同じものが場面ごとに違う名前で呼ばれ、同じ語が別のものを指す。語を決めないと、たとえば次のような問題が起きる(どれも、画面を点検して見つかった実例である)。

- 同じ数が「ベクトル n 件」「埋め込み済み n / n 枚」「埋め込み: n / n 枚」の 3 通りで書かれていた。
- 「見つからない」が 4 通りの文型で、しかも「元のファイルが無い」と「記録が無い」という別のものを、同じ語で指していた。
- 開発者向けの語(`visual`・`fulltext`・`cosine`・`Core:`・`llama-server`・例外の型名・`HRESULT`)が画面に出ていた。
- 検索の見出しの「n 枚」が、どの検索語でも 300 と出た(特徴ベクトル検索が全画像に順位を付けるため、上限に必ず達する)。読み手は「300 枚が見つかった」と読む。
- 「全文検索の対象 n 枚」は、実は検索語に一致した枚数だった。「対象にできる枚数」と読まれる。
- 「準備完了」が、インデックス作成が済んだようにも読めた(まだ続いている)。
- 手動タグのヒントが「Shift で複数を選べる」と書いていたが、Shift で選ぶ処理は無かった。

## 決定

**本文は、使う人の目的の言葉で書く(何ができるようになるか)。括弧とツールチップに、正確な技術の名前(SigLIP2・VLM・OCR・CUDA・コサイン類似度など)をヒントとして添える。** なじみがあっても不正確な語より、一見「わからない」でも正確な語を選ぶ。出さないのは、コードの綴り(識別子・変数名・例外の型名・列挙名・ハッシュの値)である。調べる手がかりになる名前(`llama-server`・`HRESULT`・SHA-256)は、括弧で残す。

**規則。**

- **段階の名前は、その段階で使えるようになる検索の名前で呼ぶ。** 画像ごとの特徴ベクトルを作る段階と、それで探す検索は「特徴ベクトル検索」(検索の名前は「特徴ベクトル検索 (SigLIP2)」)、VLM が文字・説明文・タグを作る段階と、それで探す検索は「テキスト検索」。技術の名前はヒントに書く。
- **作る側と探す側を言い分ける。** 段階(インデックスを作る工程)の話は「…のインデックス作成」「…のインデックスが無い」と書き、検索の名前だけを書かない。「特徴ベクトル検索の準備中」は、検索が使えない話に読めるため。順位・類似度・一致は探す側の語である。
- **1 つの語は 1 つの意味にだけ使う。** 語と意味と使う場所の表を持つ(下)。「出た」は一覧に入ったこと(どちらの検索でも)、「一致」はテキスト検索で語が合った(文字に含まれていた)こと(特徴ベクトル検索には使わない)。
- **言い切れないことは言わない。** ヒントも言い切りにする。コードで確かめていない仕組みは書かない。数や割合に見える語は、何の中の数かと、上限で切ったかを言う。
- **本文は、読み違えると次の行動が変わること。** 仕組み・内部の名前・理由の詳細はヒントに置く。ヒントを付けられない所(通知・確認の窓)は、括弧で添える。
- **説明の文は「です・ます」調。** ボタン・見出し・状態の名前は名詞のままにする。失敗は「〜できませんでした: 理由」(左パネルの補足の 1 行だけは、頭を外して理由から始める。0047)。画面に出す文で、半角の「(」の前には、半角の空白を 1 つ入れる(前が日本語でも英数字でも。画面のフォントでは、空白が無いと括弧が前の字に詰まって見えるため。括弧は半角のまま)。例外は、行や文の頭・空白の直後・開きの括弧とかぎ括弧(「(」「「」「『」「[」)の直後だけ。書式の差し込みは、差し込んだあとの文で数える(`{0}(…)` でなく `{0} (…)` と書く)。
- 手動タグは、必ず「手動タグ」と書く。窓や確認が出るボタンには「…」を付ける。数え方は「枚」、日時は分まで。ショートカットは、メニューとツールチップに書く。
- **ふだんは静かにする。** 新しく足す通知は、失敗、一部できなかったこと、見て分からない結果だけにする。成功しただけの操作の通知は足さない。
- モデル名は、モデルの定義(Core の公開の表示名 `OhanamiCore.ModelLabels`)から取り、画面の文字列に書き写さない。モデルを替えても嘘にならないように。

**規則はコードで守る。** 語は 1 か所の関数から作り(段階の名前は `ProcessingWords.StageName` だけ)、引退させた語とコードの綴りは、画面の文を作る関数の出力にテストを掛けて見張る(`tests/Ohanami.App.Tests/WordRulesGuardTests.cs`)。ソースの文字列は、組み立てで割れていて grep では見つからないので、文を作る関数を実際に呼んで、出てきた文を調べる。モデル名の書き写しは `ModelNamesGuardTests` が見張る。

**引退させた語、今の語、理由。**

| 引退させた語 | 今の語 | 理由 |
|---|---|---|
| 埋め込み(本文) | 特徴ベクトル検索(段階と検索の名前)。ヒントでは「特徴ベクトル化」 | 日本語では「何かを埋め込む」に読め、不正確 |
| 画像検索(検索の名前) | 特徴ベクトル検索 (SigLIP2) | 「画像検索」は「画像で探す」(逆画像検索)に読まれうる。「特徴ベクトル検索」は、どんなベクトル検索にも当たるので、モデル名の添えを必ず付ける |
| 全文検索(画面の語) | テキスト検索 | 「全文」は、もともと文章でできたものに使う語。この検索は OCR・説明文・タグ・手動タグを探す。対象は VLM が作った文字で、画面の元の文字そのものではない。これをヒントで言う |
| 走査・再走査 | スキャン・今すぐフォルダを再スキャン | 1 語 1 義。画面の文だけ。コードとログの「走査」は変えない |
| 未処理 | 未作成 | 「処理」は何でも指す。作るのはインデックスである |
| 要再処理 | 要再作成 | 「要」で、自分で始める必要があることが伝わる。作り直しは開始のボタンでは始まらず、窓の「再作成を始める…」で始める |
| 準備完了 | 検索準備完了 | 「完了」は、作業が済んだように読める。検索の両方(特徴ベクトル検索とテキスト検索)が答えられるときだけ使う |
| 見た目が近い(理由の行) | 特徴ベクトル検索で出ました (SigLIP2 の類似度。文字の一致なし) | 特徴ベクトル検索は全画像に順位を付けるので、「近い」とは限らない。近さを言い切らない |
| 「1 に近いほど近い」(類似度の説明) | 「割合ではない。同じ検索の中だけで比べられる」。値の水準の目安(「0.1 前後」など)は書かない。補正をかけた検索では、「どの言葉にも近い画像の分を引いた値」と書く(0051) | 当たりと外れの値は重なり、1 に近い値は出ない(0034・0051)。値の水準は、補正をかけた検索とかけない検索で違う。誤った期待を与えない |
| 元のファイルが無い画像(一覧の名前) | フォルダに無い画像 | フォルダを外した画像も対象で、ファイルは在る。「元のファイルが無い」は、特定のパスのファイルが見つからない場面(タイル・コピーの失敗・パスの注記)だけに残す |
| 失敗の一覧(窓の名前) | インデックスの状態 | 失敗だけでなく、作り直し・飛ばした画像・フォルダに無い画像も扱う。詳細画面の 1 枚ごとの「処理状態」とは別の名前にする |
| 「…検索の失敗」 | 「{段階}のインデックス作成に失敗」 | 失敗したのは検索ではなく、インデックス作成である |
| 全文検索の対象 n 枚 | 一致した画像: n 枚 | n は検索語に一致した枚数である |
| 検索の見出しの「n 枚」 | 上限で切ったときだけ「上位 300 枚」 | どの検索語でも 300 と出て、見つかった数に読めるため |
| 「ジョブ」・「索引」・`Core:` など | 「インデックス作成」「インデックス」。コードの綴りは出さない | 利用者に定義の無い語 |
| 手動タグのヒントの「Shift で複数を選べる」 | Shift+クリックの範囲選択を実装して、ヒントを合わせた | 実装に無いことを書かない |

## 検討した案

| 案 | 採らなかった理由 |
|---|---|
| 内部の語を一切画面に出さない(規則を厳しく守る) | モデルや段階の名前は、利用者が選び・替え・置く対象で、見える名前が要る。技術の名前を出さないと、調べる手がかりが無い |
| 「埋め込み」を画面の呼び名に統一する | 日本語では不正確(上の表)。なじみがあっても不正確な語を避ける |
| 「画像検索(SigLIP2)」と括弧で補う | 「画像検索」が逆画像検索に読まれるのは、括弧では直らない。名前そのものを替えた |
| 状態の語を「未処理 / 要再処理」のまま使う | 「処理」は広すぎて、何をするか言っていない |

## 根拠

語の正確さを、次の 2 つの点検で確かめた。

- 画面に出る文字列を、場面ごとに全部集め、語の対応表(今の語・本文の語・ヒント・正確さの印)を作った。決まった語にも例外なく、正確さの印(正確・ずれる所がある・誤解を招く)を付けた。誤解を招くと印を付けたのは、検索の見出しの「n 枚」、「全文検索の対象」の数、「準備完了」の 3 つで、いずれもコードを読んで事実と食い違うことを確かめ、直した。
- 画面が言う仕組みを、コードで確かめた。例えば、フォルダを「取り込み停止」にしても、取り込み済みの画像は検索に出続け、インデックス作成も続く(有効かどうかを見るのは、走査と監視の 2 か所だけ)。要再作成の画像は、特徴ベクトル検索では出なくなり(今のモデルの行だけを読む)、全文検索では古い結果のまま引ける。この違いは、ヒントと確認の文で段階ごとに書き分ける。

## 結果

- 画面の語を変えるときは、1 か所の関数を直す。見張りのテストが、引退させた語が戻ることを防ぐ。
- ヒントの手法の語(「特徴ベクトル化」「OCR・説明文・タグ」)は、モデルが替わって手法が変わると嘘になりうる(今は SigLIP2 と Qwen3-VL に結びついている)。
- Core の文・ログ・コードには、「索引」「走査」が残る。画面に出る Core の文は、`UiText.Plain` が言い換える(型名・列挙名・ハッシュの値を消し、`llama-server` を「VLM の処理プログラム」に替える。手がかりになる名前は括弧で残す)。

## 見直す合図

モデルを替えて、ヒントに書いた手法が変わったとき。語が別のものを指す場面が見つかったとき(語と意味の表に足す)。

## 付録: 語と意味と使う場所

| 語 | 意味(1 つだけ) | 使う場所 |
|---|---|---|
| インデックス | 検索のために画像ごとに作った情報(特徴ベクトル検索の分とテキスト検索の分) | 区画の見出し・開始のボタン・作る側の文 |
| インデックス作成 | 2 つの段階を作る工程(GPU を使う) | 開始・一時停止・再開のボタン、実行中の行 |
| 特徴ベクトル検索 | SigLIP2 で画像と検索語をベクトルにして、近さで探す方法 | 探す側(検索の名前・類似度・順位)。作る側は「…のインデックス」 |
| テキスト検索 | VLM が作った文字(OCR・説明文・タグ)と手動タグを、文字で探す方法 | 探す側。作る側は「…のインデックス」 |
| 出た | 結果の一覧に入った(どちらの検索でも) | 理由の行 |
| 一致 | テキスト検索で、検索語が文字に合った | テキスト検索の理由・順位(特徴ベクトル検索には使わない) |
| 類似度 | 特徴ベクトル検索の、検索語と画像の近さ(コサイン類似度)。短い日本語の検索語では、そこから、どの言葉にも近い画像の分を引いた値(0051)。同じ検索の中だけで比べる | 一覧のツールチップ・詳細の順位 |
| 取り込み | 監視とスキャンで、新しい画像・変更・削除に気づくこと | フォルダの行(止める・再開) |
| スキャン | フォルダの中の画像を調べ直すこと(GPU を使わない) | 「今すぐフォルダを再スキャン」・進捗・通知 |
| 飛ばした | 今回の実行で読めず、作らなかった(記録していない。次に始めたとき、もう一度試す) | 窓・件数。「失敗」と混ぜない |
| 要再作成 | いまのモデルと違うモデルで作ったインデックス | 件数・窓・確認 |
| 未作成 | まだインデックスが無い画像 | 件数・通知 |
| 未取得 | モデルのファイルが、まだ手元に無い(画像の状態の語ではない。「未作成」とは別) | 件数の内訳・補足の行・窓の上の 1 行 |
| 準備完了 | モデル 1 組のファイルが、そろって使える(検索全体の「検索準備完了」とは別) | セットアップの画面の区画の状態(緑) |
| フォルダに無い画像 | どのフォルダにも現存するパスが無い画像の記録 | 窓・件数・通知・確認 |
