# 0039. インデックス作成は 1 つのボタンで始め、まれな操作は窓に置く

状態: 採用

## 背景

利用者がほとんど押さない操作のボタンが常に並んでいると、本当によく使う「始める」「一時停止」が見つけにくい。左パネルには、フォルダの操作、インデックス作成の開始・一時停止、失敗のやり直し、要再作成の作り直し、見つからない画像の記録を消す操作が並び、ボタンが 14 個あった。そのうち 5 つが、インデックス作成(画像ごとの特徴ベクトルと、VLM(画像から文字・説明文・タグを作る AI モデル。0018) による OCR・説明文・タグの作成)を始めるボタンで、始まる処理の指定は 2 通りだけだった(特徴ベクトルだけ、特徴ベクトルと VLM)。ほとんど押されないボタンが、常に画面を占めていた。

画面を読むだけでは見えない罠もあった。インデクサー(インデックス作成を進める部品)は、始めたときの指定(どの処理を続けるか。ジョブ)を覚えたまま、新しい画像が来るまで待つ状態(待機)に入る。待機中に、失敗のやり直しや要再作成の開始のボタンを押すと、画面が「特徴ベクトルの作成だけ」の指定で開始を呼び、覚えている指定が置き換わる。以後、待機からの自動の再開では、新しい画像に VLM がかからなくなる。画面には、覚えている指定が出ないので、気づけない。

## 決定

**開始の指定を、いつも「特徴ベクトルの作成と VLM」の 1 通りにする。** 画面が `Indexer.StartAsync` を呼ぶ場所を 1 か所(`src/Ohanami.App/IndexPanel.cs`)にし、引数はいつも `AllJobs`(特徴ベクトル → VLM)にする。指定が 1 通りなら、見えない状態は無い。罠は作りで消える。Core の変更も、`IndexState` への指定の追加も要らない。呼び出しが 1 か所であることは、ソースを読むテストが見張る(`tests/Ohanami.App.Tests/StartAsyncSingleCallSiteTests.cs`)。

**左パネルの形。** 左は、フォルダの一覧、状態、開始・一時停止・再開の 1 つのボタン、「インデックスの状態…」の窓を開くボタンだけにする。ボタンは 14 個から 4 個(「追加…」「外す…」「インデックス作成を開始」「インデックスの状態…」)になった。

- 開始・一時停止・再開は、同時に押せる時が無いので、1 つのボタンで文字を替える(止まっているときと失敗のあとは「インデックス作成を開始」、実行中と待機中は「一時停止」、一時停止中は「再開」)。二度押しで「開始してすぐ一時停止」にならないよう、押したら次の状態が届くまで押せなくする。起動時は止まったままである(0027)。
- 状態の文で、「停止中・待機中・一時停止の途中・一時停止中」を言い分け、新しい画像が来たときにどうなるかを括弧で添える。
- まれな操作(失敗のやり直し、要再作成の作り直し、飛ばした画像のやり直し、フォルダに無い画像の記録を消す)は、「インデックスの状態」の窓に移す。窓は種類を 5 つ持ち(特徴ベクトルの作成の失敗・VLM の失敗・飛ばした画像・要再作成・フォルダに無い画像)、対象の一覧を見ながら操作する。操作できないときは、窓の中に理由を 1 行で書く(ツールチップは、押せないボタンには出ない見込みなので頼らない)。
- フォルダの有効・無効のボタンは外し、フォルダの行の右クリックにある「取り込みを止める」「取り込みを再開する」に下げた。「今すぐフォルダを再スキャン」も同じ右クリックに置く。
- ウィンドウの最小の大きさは 1042×560 にする。高さ 560 は、固定の 7 行にしたうえで、フォルダの一覧が 2 行以上見える高さである。幅 1042 は、詳細画面を開いたときに、画像に使える幅が一覧のサムネイルの幅(256px)以上になる大きさである(枠 16 + 左の列 300 + 右パネルの余白 18 + 詳細の右の欄 440(内側の余白を含む。0040) + 画像の余白 12 + 256)。
- 「インデックス」の欄は、固定の 7 行にし、どの状態でも高さを動かさない。入りきらない文は末尾を切り、ヒントに全文を出す。上のフォルダの一覧が、状態によって伸び縮みしないため。

**ゲーム中の GPU 解放は、一時停止だけで満たす。** 一時停止は、llama-server を止め(0026)、ORT(ONNX Runtime。特徴ベクトルを計算する部品)のセッションを破棄する(0011)ので、GPU が空く。止めている間に撮ったスクリーンショットも、走査は GPU を使わないので拾われ、新しい順の一覧の一番上に出る。

## 検討した案

| 案 | 採らなかった理由 |
|---|---|
| 「特徴ベクトルの作成だけ」を始めるボタンを残す | 指定が 2 通りになり、上の罠が残る。ゲーム中の軽い動かし方として安全だという確認が、もともと無い(ゲーム中は一時停止で足りる) |
| ウィンドウの最小の大きさを、ボタンが 14 個あったときの 760×480 のままにする | 左パネルが収まらない(必要な高さ 614〜821px に対し、使える高さが 419px)。詳細画面を最小の幅で開くと、画像の欄の幅が 0 になった |
| 左パネルに全部のボタンを残す | まれな操作が、常に画面を占める。最小のウィンドウで、フォルダの一覧が見えなくなる(上の表) |

## 根拠

最小のウィンドウで、左パネルが収まるかを測った(画面を出さずに、パネルを描画して寸法を測るテスト)。

| 状態 | 必要な高さ | 備考 |
|---|---|---|
| 止まっているとき | 614px | |
| 通常の VLM 実行中 | 665px | |
| 最も長い形 | 821px | |
| 使える高さ(既定のウィンドウ 1180×760) | 699px | 最も長い形ではフォルダ一覧の高さが 0 になる |
| 使える高さ(ウィンドウの最小を 480 にした場合) | 419px | どの状態でも一覧が 0 で、ボタンも切れる |

ボタンを減らし、固定の 7 行にして、最小のウィンドウの高さを 560 にした。この大きさで、どの状態でも、フォルダの一覧が 2 行以上見える(1 行 56px のとき 131px)。「インデックス」欄の高さが、状態によらず 1px も動かないことを、テストが固定している(`IndexSectionHeightTests`)。

## 結果

- 「開始」の意味が 1 つに揃う。止まっているときに特徴ベクトルの作成の失敗だけをやり直しても、VLM の未作成が溜まっていれば、VLM も始まる。
- 「特徴ベクトルの作成だけ」は、VLM を使えない環境での逃げ道でもあった。VLM のモデルのファイルが無いときは、Core がそのジョブを「未取得」として動かさず、特徴ベクトルの作成だけを進めて待機に入る。左パネルと「インデックスの状態…」の窓に、未取得であることと足りないファイルを出す。ファイルをそろえたあとの「インデックス作成を開始」で、VLM が始まる。ファイルは在るのに起動できないとき(VRAM が足りないなど)は、従来どおり、埋め込みが済んだあとに実行全体が失敗で止まり、待機に入らない。画面の指定には戻さない。
- 要再作成の作り直しは、開始のボタンでは始まらず、窓の「再作成を始める…」で始める。
- 「インデックスの状態」の窓は、押すたびに増えない(1 つだけ持つ)。モーダル(開いている間、元の画面を操作できなくする形)にはしない(一時停止をいつでも押せるように)。

## 見直す合図

VLM を起動できない環境(VRAM が足りないなど)で、実行が止まることが実際に起きたとき。ボタンを減らしたことで、まれな操作が見つけにくいと分かったとき。
