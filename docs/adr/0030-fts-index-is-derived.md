# 0030. テキスト検索の索引は、いつでも作り直せる形にして、DB の移行の外に置く

状態: 採用

## 背景

利用者から見ると、検索の仕組み(たとえば、ひらがなとカタカナを同じ文字として探す変更。0031)を変えたときに、数十時間かけて作った VLM(画像から文字・説明文・タグを作る AI モデル。0018) の結果を作り直さずに、新しい仕組みで引けてほしい。

テキスト検索(VLM が作った OCR・説明文・タグと、手動タグの文字を、全文検索で探す検索。0029)の索引(`fts_docs`。検索用に作った表)は、VLM の結果(`captions`)と手動タグから作る。つまり、元のデータから作り直せる派生データである。索引の中身は、正規化・分割・区切り・文書の選び方の規則で決まる(0029・0031)。この規則を変えると、索引と検索の分割がずれて、例外が出ないまま検索が壊れる。規則を変えるたびに、DB の移行(0005)を書き、VLM の再処理(約 36 時間)を強いるわけにはいかない。

## 決定

**`fts_docs` は派生データで、スキーマの移行(0005)の外に置く。** 規約文字列で作る・作り直す(`src/Ohanami.Core/FullText/FtsIndexSpec.cs`、`FtsIndex.cs`)。

- 規約文字列は、索引の中身を決める規則をすべて含む。LF 区切りの正準文字列で、`fts-spec/1`・`tokenize`・列の構成(`layout=single`)・正規化の版・分割の版・欄の区切り・タグの区切り・文書の選び方の版・制御文字の置換の版である。`index_meta['fts_spec']` に保存する。
- 開くとき(`OhanamiCore.OpenAsync` の裏の起動の中。`OpenAsync` を待たせない)に、保存された規約と現行の規約を比べる。違う、または `fts_docs` が無ければ、1 つの書き込みトランザクションで、`fts_docs` と `search_text` を `captions` から作り直す。この間、テキスト検索は「準備中」を返す(特徴ベクトル検索の結果は返る)。作り直しに失敗したら、テキスト検索だけが失敗を返し、アプリ全体は止めない。
- 規則(`Tokenizer`・`NormalizedText`・`CharClassifier`、文書の選び方、置換、区切り、列の数)のどれかを変えたら、対応する版を上げる。上げ忘れると、索引は古い規則のままで、検索だけが新しい規則になる。
- 1 枚の結果の保存(`CaptionStore.SaveAsync`)は、`captions` の upsert・段階の状態の 2 行・`search_text` の upsert・`fts_docs` の delete と insert を、同じトランザクションで行う。索引は、保存のたびに `captions` と食い違わない。
- 索引文書の元は、画像ごとに最新の結果(作成時刻が最新のもの)で、モデルは問わない。モデルを替えた直後も、再処理が済むまで、古いモデルの文書で引ける(要再作成の画像、つまり今のモデルと違うモデルで作った結果の画像が、検索から消えない。0006)。
- `fts_docs` と FTS5 の影の表(`fts_docs_data` など)は、スキーマの移行が作らないので、「あるはずの表」の検査(`DatabaseSchema.ExpectedTables`)に入れず、新規の DB と移行した DB の `sqlite_master` の比較からも外す。`fts_docs` 自身の形は、`FtsIndex` のテストが持つ。

## 検討した案

列の構成は、1 列(OCR・説明文・タグを連結)と 3 列(OCR・説明文・タグ)を、結果を見る前に採否の線を決めて比べた。線に使う known-item は、探したい 1 枚が決まっている検索の問題で、目的の画像が上位 20 位以内に入るかを数える(0037)。

| 案 | 線 |
|---|---|
| 1 列(基準): OCR・説明文・タグを 1 つの文章にして、索引に入れる | |
| 3 列: OCR・説明文・タグを別々の欄に入れる(順位を付ける式 BM25 の、欄ごとの重みは既定の 1.0 のまま。重みは調整しない。評価の標本への過適合の入口になるため) | 次の 3 つをすべて満たすときだけ採る: 2 つの検索をまとめた結果の precision@10 の下限が +0.02 以上上がる。見た目で探す known-item が減らない。セリフで探す known-item が減らない。判定は 1 回きりで、後から線を動かさない |

## 根拠

実データの結果(開発者の手元の約 1,000 枚で測った。データは公開していない)で、1 列と 3 列を同じ DB で測った。

| 指標 | 1 列 | 3 列 |
|---|---|---|
| precision@10(検索語ごとの上位 10 枚のうち、当たりの割合。2 つの検索をまとめた結果) | 同じ | 同じ(差は +0.000。線は +0.02) |
| known-item(探したい 1 枚が上位 20 位以内に入った件数)・セリフで探す known-item | 同じ | 同じ |

3 列は、1 列と完全に同じ結果だった。FTS5 の BM25 は、列の重みが既定のままなら、文書全体のトークン数で正規化するので、列を分けても順位は変わらない。線(+0.02)を満たさないので、1 列にして、3 列のコードは消した。規約文字列の `layout=single` の行は残してある(実験のビルドで作った DB を開いたときに、作り直しが起きるように)。

索引の作り直しにかかる時間は、1,014 件で 250ms、1,030 件で 262〜304ms だった(開発者の手元の実データ)。

## 結果

- 正規化や分割の規則を変えても、VLM の再処理は要らない。次に開くとき、索引が自動で作り直される。
- 作り直しの間は、全文検索が使えない。DB が大きいと長くなる(1 万件で数秒の見込み。線形と仮定した見積り)。その間、書き込みは待つ。
- 索引の中身を決める規則を変えたら、版を上げるのを忘れない、という規律が要る。テストが、規約を変えると作り直されることを確かめている。
