# 0022. VLM には、書き起こし・説明文・タグを 1 回の JSON で出させ、タグは固定の語彙にしない

状態: 採用

## 背景

VLM(画像と文章を扱える AI モデル。ここでは、画像から、写っている文字・説明文・タグを作る。0018)の 1 回の呼び出しで、画面の書き起こし(OCR。0021)・説明文・検索用のタグ(「黒髪」「水着」のような短い属性の語)を出させる。出力は、テキスト検索(0029。全文検索)の索引にそのまま入る。次の問題があった。

- 書き起こしと説明文は、見た目を言う検索語に当たりにくい。利用者が打つ語は、「黒髪」「ピンク髪」のような 1 つの属性を言う一般語が多い。画面に文字として写っていなければ OCR に出ず、説明文にも主題でなければ書かれない。手元の 45 件の検索語が、書き起こし・説明文のどちらかに含まれるのは、13 件(29%)だけだった(この割合を、含有率という。測り方は「根拠」)。
- 出力が壊れる(JSON でない・想定外の項目・途中で打ち切り)と、黙って誤った結果が検索に入る。
- タグを別の呼び出しにすると、1 枚あたりの時間が約 2 倍になる。

## 決定

出力は、1 回の呼び出しで、次の 3 項目の JSON オブジェクトとして出させる。

```json
{"type":"object",
 "properties":{"ocr":{"type":"string"},"description":{"type":"string"},"tags":{"type":"array","items":{"type":"string"}}},
 "required":["ocr","description","tags"],
 "additionalProperties":false}
```

- 項目の順は `ocr` → `description` → `tags` に固定する。書き起こしてから要約させるためである。スキーマは `response_format` の `json_schema` として送る(`src/Ohanami.Core/Models/VlmCatalog.cs` の `VlmSchema`)。
- `ocr`: 画面に写っている文字を、見えるとおりにすべて書き起こす(セリフ・名前・見出し・UI の文言)。読めない文字を推測で補わない。文字がなければ空文字列。
- `description`: どんな場面かを、日本語で 120 字以内で説明する。
- `tags`: 画像を検索するときに打たれそうな、短い属性語の配列。画像に実際に写っているものだけを書き、推測や創作をしない。同じ語を 2 回書かない。多くても 15 語まで。分類は、髪の色・髪型・服装・場面(場所)・画面の種類・絵柄・人数。髪の色は「黒髪」「ピンク髪」のように「○髪」の形で書く。ほかの分類は、例を挙げる。
- プロンプトは `src/Ohanami.Core/Models/VlmPrompt.cs` にある。1 文字でも変えると、新しい model_id になり、全件が要再作成になる(0006)。
- 応答は厳格にパースする。
  - 成功にするのは、`finish_reason` が `stop` のときだけである(`length` で、たまたま JSON が壊れていなくても失敗にする)。
  - `choices[0].message.content` は、JSON のオブジェクトで、プロパティは `ocr`・`description`・`tags` だけ。想定外のプロパティは失敗にする。`ocr`・`description` は必須の文字列、`tags` は必須の文字列の配列(空配列は許す)。型違いや欠落は、理由つきで失敗にする。
  - 思考の痕跡(`reasoning_content`、または `content` の `<think>`)があれば、その画像を失敗にする。構成の誤りの兆候だからである。
  - 孤立したサロゲートを含む文字列で、応答を読めないときは、その画像を失敗にする。
- 文字列は加工せずに保存する(trim も正規化もしない)。説明文が 120 字を超える・tags が 15 個を超えるのは、失敗にせず、記録だけする。
- tags は、全文検索の索引に、区切り「、」でつないで入れる(0029)。

## 検討した案

- **tags を作らない(書き起こしと説明文だけ)**: 属性語が拾えない(上の 29%)。
- **tags を別の呼び出しで作る**: 1 枚あたりの時間が約 2 倍になる。OCR が悪化するなら諦める、という線を先に決めて、1 回の呼び出しで試した。
- **tags を閉じた語彙(固定の一覧から選ばせる)にする**: 画面に合う語が一覧になければ、最寄りの語に無理に寄せる。1 万枚で、全文検索の誤ヒットを増やす。分類ごとに例を挙げるが、一覧に無い語を自分で書く余地を残す(下の v2 の試み)。
- **プロンプトの v2(例にない語は自分で書く、と明記する)**: OCR が悪化したので採らない(下の表)。

## 根拠

評価は、開発者の手元の約 1,000 枚から選んだ 33 枚で行った。データは公開していない。この 33 枚の画像に、利用者が見た目で探すときに打つ語(45 件の検索語)を書き、含有率(検索語が、書き起こし・説明文・タグのどれかに含まれる件数。タグの境目はまたがない数え方)を測った。OCR の指標の CER(文字誤り率)と再現率は、0018 で説明している。

採否の線(測る前に決めた)は次のとおり。

- OCR: 素直な層で、再現率 ≥ 95%・CER ≤ 3% を保つ。tags なしとの差が、再現率 2pt・CER 1pt 以内ならノイズ。それより悪くなったら、tags は諦める。
- 含有率: 45 件の検索語のうち 27 件以上(60%)なら、この形で採用する。20 件未満なら、プロンプトを 1 回だけ直して再試行する。20〜26 件のときの扱いは、規則に無かったので、検索語を見ずに特定できる欠陥に限って 1 回だけ直し、33 枚で試し、良いほうで進める、と決めた。表記の揺れは直さない。
- v2 の判定: (1) OCR が線を保つ、(2) 含有率が 20 件を下回らない、(3) 画像と矛盾するタグ(画面の種類・服装・髪の色などの誤付与)の数が v1 より減る。3 つとも通れば v2、1 つでも落ちれば v1 を採る。2 回目の修正はしない。

| 項目 | tags なし | v1(採用) | v2 |
|---|---|---|---|
| 素直な層の CER / 再現率 | 2.80% / 96.88% | 2.80% / 96.88% | 4.54% / 94.98%(線を割った) |
| 難しい層の再現率 | 91.50% | 93.81% | — |
| 含有率(45 件の検索語) | 13(29%) | 20(44%) | 22 |
| 矛盾するタグの数 | — | 8 | 8(減らなかった) |
| 異なり語数 | — | 58 | 70 |
| 1 枚の時間(中央値) | 12.9 秒 | 12.5 秒 | — |
| パース失敗・ループ | 0 | 0 | 1 枚が「…」の繰り返しのループ |

- v1: 33 枚すべてパースでき、ループなし。含有率の内訳は、説明文 14 件・tags 16 件。髪の色を言う語は、測った 4 つともすべて当たった。外れの多くは、表記の揺れ(かな・カタカナ・漢字の書き分け、同じ意味の別の言い方)。ほかに、分類にないもの(体型・肌の色・表情・構図など)と、VLM の誤認(動物の種類の取り違え)。
- v1 のタグの問題は 2 つ。(a) 露出の多い絵に、写っていない服装のタグが付く(人物でないものに髪の色のタグが付く例もある)。プロンプトでは直らず、少数なので放置した。(b) 閉じた語彙への寄せ(例の一覧を「この中から選べ」と扱い、合わない画面を最寄りの語に寄せる)。ある画面の種類のタグが、実際にその画面である画像より、多くの画像に付いた。
- v2: プロンプトを変えると、温度 0 でも、OCR の出力が画像ごとに揺れ、悪いほうに出た(素直な層の CER は tags なしとの差が +1.74pt で、ノイズの範囲 1pt を超える)。含有率は 22 件で足りたが、矛盾するタグは減らなかった(ある語の誤付与は減ったが、別の語の誤付与が別の画像に新しく出た)。3 つの条件のうち 2 つ(OCR、矛盾の減少)で落ちたので、v1 を採った。
- 1030 枚の通しでは、tags の個数は中央値 6・最大 19(「15 語まで」を超えたものが 3 枚)。空は 0。

## 結果

- テキスト検索(0029)が、属性語を、含有率 44% まで拾う。髪の色の語はほぼ全部、タグで当たる。
- 表記の揺れや、分類にない語は、テキスト検索では拾えない。特徴ベクトル検索(0011)と、融合(0033)が補う。
- 閉じた語彙への寄せは、Qwen3-VL の癖として残る。タグを根拠にした検索には、少数の誤ヒットが混じる。
- 厳格なパースなので、想定外の出力は失敗として記録される(再試行や失敗の扱いは 0023)。
- 出力の順序や項目を変えると、全件が要再作成になる(約 36 時間。0018)。

## 見直す合図

- モデルを替えたとき(0018)。タグの癖や OCR への影響は、モデルごとに違う。
- 属性語の含有率や、タグの誤ヒットが、検索の精度の問題になったとき。語彙の整理や、検索語側の同義語の展開を検討する。
- スキーマに項目を足すとき。OCR が悪化しないか、同じ線で確かめる。
