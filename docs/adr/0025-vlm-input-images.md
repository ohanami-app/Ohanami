# 0025. VLM には画像のファイルをそのまま渡し、画像トークンの上限は 3584 にする

状態: 採用

## 背景

VLM(画像と文章を扱える AI モデル。ここでは、画像から、写っている文字・説明文・タグを作る。0018)には、画像を HTTP のリクエスト(base64 の data URI)で渡す。使う人から見た問題は、大きな画像(4K のスクリーンショットなど)だと、処理が極端に長くなったり、GPU のメモリが足りなくなったりすることである。次の点を決める必要があった。

- 対象の形式(PNG・JPEG・WebP)を、そのまま送れるか、変換が要るか。
- アルファ(透明)つきの画像、EXIF の向きつきの JPEG の扱い。
- 画像トークンの上限(`--image-max-tokens`)。画像トークンは、VLM が画像を読むために、画像を区切った単位で、大きい画像ほど増え、VRAM と時間が増える。上限は、VRAM の足切り(0019)に収まり、かつ手元の画像のどれにも効かない大きさにしたい。

## 決定

- PNG・JPEG・WebP とも、ファイルのバイト列を、そのまま送る。MIME は `image/png`・`image/jpeg`・`image/webp`。変換はしない。
- 読んだバイト列の SHA-256 が、DB のハッシュ(0003)と同じ場合だけ使う。違えば、次のパスを試す。ファイルを開けない(共有違反など)ときは記録せず、その実行では飛ばして、次の実行で再試行する。デコードできないバイト列は、先に `SKCodec` で確かめて、失敗として記録する。
- アルファ・EXIF の向きは、扱わない。アルファは llama.cpp が捨てて RGB をそのまま使う。EXIF の向きは無視する。埋め込み(0013)も向きを見ないので、2 つの経路は揃っている。
- `--image-max-tokens` は 3584 にする。この値は model_id に入る(作り方は 0006)。変えると全件が要再作成になる。

## 検討した案

- **WebP を Skia で PNG にしてから送る**: 実物の確認で、llama-server b12110 は WebP をそのまま読めた(非可逆・可逆とも、書き起こしが正しい)ので、不要である。Skia の変換は、事前乗算でデコードするので、完全に透明な画素の RGB を 0(黒)にする。PNG をそのまま送る場合(アルファを捨てて RGB を使う)と、透明部分の扱いが食い違う。そのまま送れば、PNG と同じ扱いに揃う。
- **EXIF の向きを適用する**: 向きつきの JPEG(向き ≠ 1)では、VLM の説明の位置がずれる(書き起こしは読める)。主な対象はスクリーンショットで、向きのつく JPEG はほぼ無いので、今は直さない。
- **アルファを白や黒で合成してから送る**: 今の対象(スクリーンショット)に、アルファはほぼ無い。直さない。
- **`--image-max-tokens` を小さくする(3072 など)**: 3584 で、手元のどの画像にも効かず、4K の画像も足切りの内側に収まった(下の表)ので、小さい値での測り直しは不要と判断した。

## 根拠

### 画像トークンの上限

文章(プロンプト)のトークン数は 536(テンプレートの印を含む。`/tokenize` でプロンプト本文 526 + 印 10)。画像のトークン数は、(幅 / 32) × (高さ / 32) になる(128×128・256×128・256×256・512×256 の画像で、`prompt_tokens` から逆算して、4 つとも一致した。32×32 と 64×64 は、画像トークンが最小に切り上げられるので、逆算に使えない)。

評価の画像は、開発者の手元の約 1,000 枚である。データは公開していない。

| 項目 | 値 |
|---|---|
| 1030 枚の画像トークンの最大 | 2,720(`usage.prompt_tokens` の最大 3,256 − 536) |
| 上限 3584 | 手元のどの画像にも効かない(3584 ≥ 2720) |
| 文脈長 8192 の内訳(最悪) | 文章 536 + 画像 3584 + 出力 2048 = 6,168 |
| 4K(3840×2160 の合成画像) | 画像トークン 3,476(上限の内側) |
| 4K の 1 枚の時間 | 約 96〜102 秒(手元の大判の画像は 35〜64 秒。画像のエンコードが CPU のため。0019) |
| 4K の VRAM(プロセス分のピーク) | 6,102〜6,122MiB(足切り 6,656MiB の内側。余裕 534〜554MiB) |

4K の画像を流して、描いた文字の書き起こしが正しいことも確かめた。

### 形式とアルファ

合成画像(1024×576。目でも確認)を、実物の llama-server に送った。

| 入力 | 結果 |
|---|---|
| PNG・JPEG・WebP(非可逆・可逆) | どれも書き起こしと説明が正しい |
| アルファつき PNG | llama.cpp がアルファを捨てて RGB をそのまま使う。透明部分の RGB が白なら白背景として読めて、書き起こしが正しい。黒なら黒背景に見えて、黒い文字が消える |
| アルファつき WebP | Skia で PNG にしたものも、そのまま送ったものも、背景は黒だった |

アルファつき WebP の比較は、テストの WebP を Skia で作ったので、透明部分の RGB が 0 になっていた。RGB が残る WebP での比較は、できていない(未確認)。

### 出力の一致

手元の 33 枚と無作為の 40 枚(計 73 枚)を、製品の起動とクライアントで流すと、書き起こし・説明文・タグが 73 枚すべて、評価のときの出力と完全に一致した(0019)。`--image-max-tokens 3584` は、出力に影響しなかった。

## 結果

- 4K 級の画像は、1 枚に約 100 秒かかる(リクエストのタイムアウト 300 秒の内側)。4K 級の画像が多いライブラリでは、VLM の全体の時間が延びる。
- 向きつきの JPEG では、説明の位置がずれる。アルファつきの画像は、形式によって、透明部分の扱いが揃わない(PNG は RGB のまま、WebP は透明部分が黒になりうる)。どちらも、スクリーンショットでは、ほぼ起きない。
- 画像トークンの上限を変えるときは、全件の再処理を伴う。

## 見直す合図

- 写真を対象に加えるとき。VLM と特徴ベクトルの作成の両方で EXIF の向きを適用し、前処理の版(0013)を上げる。
- アルファつきの画像を、対象に加えるとき。透明部分の扱いを、形式で揃える。
- 手元の画像に、画像トークンが 3584 を超えるものが出たとき(8K など)。上限と VRAM を測り直す。
- 対象の形式を増やすとき(JXR など)。llama-server が読めるかを確かめる。
