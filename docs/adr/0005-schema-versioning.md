# 0005. DB の形(スキーマ)の変更は、版の検査と複製で守り、値の一覧(列挙)は DB の制約に持たせない

状態: 採用

## 背景

アプリを更新して DB の形(スキーマ)が変わっても、数十時間かけて作った OCR・説明文の結果が消えてはならない(OCR と説明文は、画像を読む AI モデルの VLM が作り(0018)、1 枚に約 12 秒で、1 万枚なら約 36 時間)。古い DB を、黙って誤って読むことも許されない。「想定外は大声で落とす」が原則である。

## 決定

次のように作る(`src/Ohanami.Core/Data/`)。

**版の検査。** DB に `PRAGMA application_id`(Ohanami の定数 `0x4F484E4D`、文字で 'OHNM')と `PRAGMA user_version`(スキーマの版)を持つ。開くとき、`application_id` が違う、版がコードの知っている最新より新しい、表があるのに版が 0、のどれかなら `UnknownSchemaVersionException` で止まる。

**移行。** 古い版の DB を新しい形に変える処理(移行)は、版ごとの明示的な関数(リフレクションで探さない)を順に適用する。守りは 3 つ。

1. 適用の前に `VACUUM INTO '<DB>.bak-v<移行前の版>'`(DB を別ファイルに複製する SQLite の命令)で複製を取る。既にあれば `-2`、`-3` … と別名にして、上書きしない。新規作成のときは取らない。
2. 適用中は `foreign_keys = OFF` にし、各段(1 段 = 1 トランザクション。途中で失敗したら全部やり直す単位)のあとに `PRAGMA foreign_key_check` を行う。1 行でも返れば例外にして、その段を巻き戻す。
3. 新規作成と移行を 1 つの手順にする。空の DB には「版 1 を作る → 移行を順に全部適用する」。最新の版の DDL(表を作る SQL 文)を別に持たないので、新規の DB と移行した DB で形が食い違うことが構造的に起きない(テストで `sqlite_master` が完全に一致することを確かめる)。

**列挙の値。** `format`・`kind`・`stage`・`status`・`source`・`job_kind` などの、決まった値の一覧から選ぶ列(列挙)には、`CHECK` 制約(列に入れられる値を DB に守らせる仕組み)を付けない。付けるのは、構造の制約(`NOT NULL`・主キー・外部キー・`UNIQUE`)と、形式が変わらない制約(ハッシュが 64 文字で小文字であること、真偽値が 0 か 1 であること)だけである。値の一覧は C# の `enum` との明示的な変換関数(`switch` 式。`Enum.ToString` や `Enum.Parse` に頼らない)が持ち、読むときに知らない値は `UnknownEnumValueException` にする。

**その他の形。**

- 通常の表は `STRICT` にする(FTS5 の仮想表を除く)。時刻は UTC の ISO 8601 文字列(`yyyy-MM-dd'T'HH:mm:ss.fff'Z'`)の 1 つの書式で、文字列として並べて時刻順になる。
- 画像の識別子の列は、BLOB ではなく TEXT(16 進 64 文字)にする(0003)。
- DB を作るとき、最初の表を作る前に `page_size = 8192` にし、そのあとで WAL にする(WAL のままではページの大きさを変えられない)。

## 検討した案

| 案 | 採らなかった理由 |
|---|---|
| 列挙の列に `CHECK (stage IN ('embed','ocr'))` を付ける | SQLite は `CHECK` を `ALTER TABLE` で変えられない。値を 1 つ足すだけで、表を作り直して移すことになり、参照している表の外部キーも絡んで、移行が大きく危うくなる |
| 版を上げるときは DB を作り直す | VLM の結果を失う |
| ハッシュを BLOB(32 バイト)で持つ | 行は小さくなるが、10 万枚で数 MB の差でしかない。`Get-FileHash` の出力と直接比べられず、DB を見て読めなくなる |
| `page_size` 4096(既定) | 1 ベクトルの行(約 4.7KB)が 1 ページに入らず、overflow ページに分かれる |
| `page_size` 16384 | 利点は、1 万件で約 27MB の空きが減ることだけ(下の表) |

## 根拠

`page_size` は、1 ベクトルの行が overflow ページに分かれない大きさにする。1 行は、ベクトル 4608 バイト(1152 次元の float32)に、ハッシュ 64 バイトとモデルの識別子を足して約 4.7KB である。

| `page_size` | 1 ページに入る行 | 空き | 1 万件のファイル |
|---|---|---|---|
| 4096 | 入らない(overflow) | - | - |
| 8192 | 1 行(2 行で約 9.4KB を超える) | ページの 4 割強 | 約 82MB(データは約 47MB。算術) |
| 16384 | 3 行 | 1 割強 | 8192 より約 27MB 少ない(算術) |

8192 を取った。後から変える必要が出たら、WAL を DELETE に戻して `VACUUM` すれば変えられ、移行で対応できる。値は算術で出したもので、16384 との実測の比較はしていない。

## 結果

- 知らない DB・新しすぎる版の DB は、開く前に止まる。黙って読み違えない。
- 移行は、複製が残るので、失敗しても元に戻せる。複製は自動では消さない。
- 列挙に値を足す変更は、表の作り直しにならない。ただし、C# 側の変換関数に足し忘れると、網羅のテストが落ちる。
- 列挙の値が DB の側では守られない。守りは C# の変換とテストが持つ。

## 見直す合図

移行の複製がディスクを圧迫するほど DB が大きくなったとき。`page_size` を変えたい理由(ベクトルの次元の変更など)が出たとき。
