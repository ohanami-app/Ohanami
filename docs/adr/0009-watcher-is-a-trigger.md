# 0009. フォルダの監視(変更の通知)は、走査をやり直す合図にだけ使い、DB への反映は走査に任せる

状態: 採用

## 背景

利用者がスクリーンショットを撮ったら、何も操作しなくても、数秒後に検索に出てほしい。登録したフォルダに新しい画像が入る・消える・移動することを、自動で拾う必要がある。走査は、フォルダの中を調べ直して、画像の追加・変更・消失を DB に反映する処理である。.NET の `FileSystemWatcher`(フォルダの中の変更を、イベント(変更の通知)として知らせる部品)が使えるが、イベントの内容を信じて DB に反映する作りにすると、取りこぼしや来ないイベントで、DB が現実と食い違う。次のことを、実験(.NET 10・Windows 11・NTFS の一時フォルダ)で確かめた。

| 事実 | 内容 |
|---|---|
| バッファがあふれる | `InternalBufferSize` の既定は 8KB、ドキュメント上の上限は 64KB。あふれると、バッファの中身が全部捨てられ、`Error` イベントが 1 回出る。どのファイルが落ちたかは分からない。ハンドラが 1 件 20ms かかると、500 個のコピーで `Created` が 56 件しか来なかった(64KB でも防げない)。ハンドラがすぐ返せば、3,000 個でもあふれなかった |
| フォルダごとの移動 | フォルダごと移して入れると、中身のイベントは来ない(フォルダの `Created` が 1 件だけ) |
| 一時ファイル → 名前の変更 | `x.png.tmp` を書いて `x.png` に変えると、`Created`・`Changed` は `x.png.tmp` に、`Renamed x.png.tmp -> x.png` が来て、`x.png` の `Created` は来ない。上書きの移動は `Deleted` と `Renamed` |
| 書き込みの途中 | 書き手が開いたまま書く間、`Changed` は来ない(12 秒・48MB の書き込みで、閉じた直後の 1 件だけ)。「来たら完了」とも「来ない間は書き込み中」とも言えない |
| 監視フォルダの削除 | 監視しているフォルダ自体を消すと、`Error` のあと、`EnableRaisingEvents` は true のままなのに監視は死んでいる。同じ名前で作り直しても、イベントは来ない |

## 決定

**監視のイベントは「このフォルダを走査し直す」の合図にだけ使う。** イベントの中身(どのファイルか)は DB に反映しない。差分の判定は、走査(更新日時とサイズ → ハッシュ。0003・0007)だけが正である。実装は `src/Ohanami.Core/Folders/FolderWatcher.cs`。

- ハンドラは、フォルダの識別子と時刻を記録して返すだけで、I/O をしない(ハンドラが遅いとあふれるため)。
- `NotifyFilter` は `FileName | DirectoryName | LastWrite | Size`、サブフォルダも見る。`Filter` は付けない。数えるイベントは、`Changed` だけ画像の拡張子(`.png`・`.jpg`・`.jpeg`・`.webp`)のものに絞る(動画の録画などで多発するのは `Changed`)。`Created`・`Deleted`・`Renamed` は拡張子を問わず数える(数が少なく、拡張子の無い名前のフォルダの移動を拾うため)。`Error` は常に数える。`InternalBufferSize` は 64KB にする。
- まとめ方: フォルダごとに、数えるイベントが **3 秒**止まったら走査する。続いても、最初のイベントから **30 秒**で 1 回走査する(連続コピーの途中でも、終わった分から検索に出す)。次の走査は、前の走査の所要時間の 2 倍以上あける(列挙に数十秒かかる大きなフォルダで、走査が背中合わせにならないように)。
- `Error` が来たら、そのフォルダの監視を作り直して走査する。作り直せなければ、フォルダの一覧に「監視できない(定期の走査だけ)」を出し、定期の走査のたびに作り直しを試す。
- **15 分ごと**に、全部の監視を作り直してから、全部の有効なフォルダを走査する。`EnableRaisingEvents` が当てにならない(上の実験)ので、監視が生きているかを判定せず、毎回作り直す。作り直しの瞬間の取りこぼしは、直後の走査が拾う。
- スリープから復帰したら、全部の監視を作り直して、全部を走査する(復帰の前後で監視が生きているかが未確認なので、確かめずに済む形にした)。
- フォルダの登録・解除・有効/無効のあとは、`Refresh` を明示的に呼ぶ。解除した直後に待ちが発火して走査しても、フォルダが無い例外を捕まえてログに出し、落ちない。
- 起動時は、監視を先に作ってから、フルスキャンをする(走査の間のイベントは、もう 1 回の走査になるだけ)。
- 書き込みの途中のファイルの扱いは 0010 に書く。

## 検討した案

| 案 | 採らなかった理由 |
|---|---|
| イベントの中身を DB に反映する | あふれで落ちたファイルが分からない。フォルダごとの移動で中身のイベントが来ない。名前の変更のイベントの組み方が、書き込むアプリごとに違う。どれも「そのフォルダを列挙し直す」なら同じ扱いで済む(公式の対処も、あふれたら列挙して差分を取り直す) |
| `Filter` で拡張子を絞る | `Renamed` での挙動を確かめていない。`Changed` だけを数えるときに絞れば足りる |

## 根拠

走査は軽いので、フォルダを丸ごと列挙し直す方針が成り立つ。1,030 枚のフォルダの差分の走査は 0.1 秒である(開発者の手元の約 1,000 枚で測った。データは公開していない)。実際に使ってみた結果(Snipping Tool で撮ったスクリーンショット。開発者の手元の実データで測った。データは公開していない)を次に示す。

| 項目 | 値 |
|---|---|
| 撮ってから監視が走査で拾うまで | 3.2〜3.7 秒 |
| 見た目の検索に出るまで | 約 5 秒 |
| 文字の検索に出るまで | 13〜22 秒 |
| 15 分ごとの定期の走査 | 起動のちょうど 15 分後に動いた |

数字(3 秒・30 秒・15 分)は、設計の初期値のまま実際の使い方で足りた。

## 結果

- 監視が取りこぼしても、定期の走査(15 分)と復帰の走査が、次に拾う。画面は、遅れることはあっても、DB と食い違ったままにはならない。
- 大きなフォルダで走査が重いときは、前の走査の 2 倍の間隔をあけるので、走査の遅れは増えるが、走査が重なって詰まることはない。
- ネットワークドライブ・リムーバブルでの監視は、動作を確かめていない。監視を作れなければ「監視できない」にして、定期の走査に任せる。
- スリープからの復帰では、通知が 2 種類(`PBT_APMRESUMESUSPEND` と `PBT_APMRESUMEAUTOMATIC`)届くので、復帰の走査が 2 回走ることがある。今の規模では 0.0 秒で害は無い。

## 見直す合図

大きなライブラリで走査の列挙が待ち時間として問題になったとき。.NET が `FileSystemWatcher` の挙動を変えたとき(実験の事実が変わる)。
