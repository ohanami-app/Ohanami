# 0023. VLM の出力が同じ語の繰り返しから止まらなくなったら、設定を変えて再試行する

状態: 採用

## 背景

VLM(画像と文章を扱える AI モデル。ここでは、画像から、写っている文字・説明文・タグを作る。0018)は、まれに、同じ語を繰り返したまま止まらなくなる(ループ)。使う人から見ると、その画像だけ、処理に 1 分以上かかったうえ、結果が壊れて、書き起こしも説明文も検索に出ない。実際のライブラリ 1030 枚を流すと、16 枚(1.6%)がループした。16 枚はすべて `finish_reason=length` で、書き起こし(`ocr`)の途中で同じ語の繰り返しになり、`max_tokens`(評価のときは 4096)まで止まらず、JSON が壊れた。次の画面でループした。

- 価格や状態を示す同じ語が、一覧で何度も並ぶ画面。
- 同じ短い語が並ぶ画面。
- 小さい文字が全面にある、ターミナルのような画面。

どれも、正規の繰り返しがある画面で、繰り返しが止まらなくなる。Qwen3-VL でも、量子化によってはループが起きた(0018)。製品では、どのモデルでも 1 万枚に数枚はループしうる、という前提で設計する。

ループした画像は、4096 トークンまで生成して、1 枚 66〜97 秒かかる(通常は中央値 12 秒)。16 枚の合計は約 20 分で、全体の約 10% を、打ち切りまでの生成に使った。

## 決定

- `max_tokens` は 2048 にする。
- 成功にするのは `finish_reason` が `stop` のときだけである。`length` は、たまたま内容が有効な JSON でも失敗として扱う。黙って途中までの JSON を使わない。
- `length` のときだけ、ペナルティを付けて再試行する。1 回目からは付けない。
  - 試行 1: ペナルティなし。
  - 試行 2: `dry_multiplier=0.8`。
  - 試行 3: `repeat_penalty=1.1`。
  - 2 つのペナルティは、同時には使わない(別々に測った)。
- 3 つの試行がすべて `length` なら、その画像の書き起こし・説明文を失敗(`failed`。error は `finish_reason=length`)として記録して、先へ進む。特徴ベクトル検索(0011)は使える。
- 再試行で成功した結果は、`captions.attempt`(2 または 3)と、使った設定を、`settings_json` に残す。各試行のリクエストの設定・応答の状態・トークン数・時間を、`attempts` の配列に記録する。読みが崩れうるので、区別できるようにする。
- HTTP 400(大きすぎる画像などで文脈を超える)は、再試行しない。その画像の失敗として記録する。
- HTTP 5xx・接続エラー・応答の読み取りの失敗・リクエストのタイムアウト(300 秒)は、llama-server の異常とみなす。プロセスを kill して起動し直し、同じ画像をやり直す。同じ画像で 2 回続けて起きたら、その画像を失敗にして先へ進む(その画像が原因でサーバを落とすときに、無限に再起動しないため)。起動し直しそのものが失敗したら、致命的として、ジョブを止める。
- 200・400・5xx 以外の HTTP の状態(401・404 など)は、設定の誤りの兆候なので、`VlmProtocolException` にして、ジョブを止める(全画像が黙って失敗するのを避ける)。
- `stop` なのに JSON として読めない、または想定外のプロパティがあるときは、失敗として記録する(再試行しない)。
- 実装は `src/Ohanami.Core/Vlm/VlmClient.cs` と `VlmRunner.cs` にある。

## 検討した案

- **最初からペナルティを付ける**: 成功していた画像の書き起こしまで変わる。正規の繰り返しが減るため。
- **`max_tokens` を大きくする(4096 など)**: ループの打ち切りまでの時間が延びるだけである。成功した出力は 2048 に収まる(下の表)。
- **`temperature` を上げる**: ループの画像によっては、止まらない(0.8 に上げても止まらない画像があった)。
- **ループした画像を、評価から除外する**: 失敗したモデルが有利になる(0018 の採点では、「出力が空だった」として含めた)。
- **再試行をしない**: ループした画像の書き起こし・説明文が無くなる。再試行の対象は、元がループで書き起こしが使えない画像だけである。読みが多少崩れても、何も無いよりよいと判断した。
- **2 つのペナルティを同時に使う**: 別々に効果を測っただけで、同時の効果は測っていない。順に試す。

## 根拠

### `max_tokens`

成功した 1014 枚の出力トークン数は、中央値 126・p99 932・最大 1860(1030 枚の通し。評価の画像は開発者の手元の約 1,000 枚で、データは公開していない)。

| `max_tokens` | 打ち切られる画像(成功した 1014 枚のうち) |
|---|---|
| 1024 | 8 枚 |
| 1536 | 5 枚 |
| 2048 | 0 枚 |

長い出力は、小さい文字が全面にある画面である。もっと文字の多い画像が来れば、超えうる。

### 再試行の設定(失敗した 16 枚だけを、設定を変えて再実行)

llama-server b12110 の `/v1/chat/completions` は、リクエストごとの `repeat_penalty` と `dry_multiplier` を受け付け、`temperature` 0 でも効く。既定はどちらも無効である。未知のキーはエラーにならず黙って無視されるので、「エラーが出ない」だけでは、効いている証拠にならない。値を変えると出力が変わり、ループが止まることで確かめた。

| 設定 | パースできた画像(16 枚中) |
|---|---|
| `dry_multiplier=0.8` | 14 |
| `repeat_penalty=1.1` | 12 |
| 順に試す(dry → repeat) | 16(失敗した画像は、2 つの設定で重ならなかった) |

16 枚だけの結果なので、一般化の根拠は弱い。評価のときの設定(`cache_prompt` を使う。0024)では、再試行の 1 枚の時間は 2〜57 秒で、ループの 66〜97 秒より短かった。

### 副作用

- 正規の繰り返しが減る。同じ語が 8〜19 組並ぶ画面で、止まった出力には 1〜4 組しか残らなかった。検索で当たるには足りるが、件数には使えない。
- DRY は、繰り返しを避けるために、似た別の文字に置き換える(数字の桁や字形の似た文字が変わる)。画像と合わない数字を書くので危うい。
- `repeat_penalty` では、別の字に変わって、新しいループになる例があった。
- タグの表記が崩れる画像があった(分類名がタグの先頭に付くなど)。

そのため、再試行の結果は、設定とともに記録して区別する。

## 結果

- ループした画像は、最大 3 回の試行で、ほぼ救える。1030 枚の通しでは、1 回目が `length` だった 16 枚のうち、2 回目で 14 枚、3 回目で 2 枚が救われ、最終的な `length` の失敗は 0 になった。
- 再試行は、ペナルティがかかるぶん、読みが崩れうる。再試行で作った結果に、「再試行で作った」という区別が付く(`captions.attempt`)。
- 3 回の試行までかかる画像があるので、1 枚の時間は延びる(`cache_prompt` を切った製品の設定では、再試行の 16 枚が合計約 1,055 秒、1 枚平均 66 秒。0024)。
- 全部だめな画像は、書き起こし・説明文が無い(特徴ベクトル検索だけで探される)。
- サーバの異常が環境の問題のときの打ち切りと、起動し直しの扱いは 0026。

## 見直す合図

- 別のモデル・量子化に替えるとき(0018)。ループの頻度と、止まる設定を測り直す。
- `max_tokens` を超える出力が、実際のライブラリで観測されたとき(2048 を超える成功の出力が出うる)。
- llama.cpp を更新するとき(0017)。ペナルティの効き方が変わりうる。
- 再試行の副作用(数字の置き換えなど)が、検索の精度の問題になったとき。
