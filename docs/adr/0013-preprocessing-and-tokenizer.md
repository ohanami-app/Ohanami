# 0013. 画像とテキストの前処理は C# で自前実装し、Python の実装との一致をテストで保証する

状態: 採用

## 背景

特徴ベクトル検索(0011)のモデルは、決まった形の入力しか受け付けない。画像は 384×384 の RGB の数値の並び(テンソル)に、テキストは長さ 64 の番号の列(id 列)に、前もって変換する。テキストを番号の列に分ける処理を、トークナイザという。この前処理が、モデルを学習・評価した側の参照実装(Python の Pillow と tokenizers)と少しでもずれると、例外は出ず、検索の精度だけが静かに落ちる。ずれたことに気づけるのは、検索が悪くなってからになる。使う人から見ると、たとえば、画像を縮小する補間の仕方がわずかに違うだけで、特徴ベクトルが少し変わり、「赤い服の女の子」と打って探したときの順位が、気づかないうちに悪くなる。

製品は Python に依存しない。そこで、前処理とトークナイザを C# で実装し、Python の参照と一致することをテストで確かめる必要がある。

## 決定

画像の前処理とテキストのトークナイズを、C# で自前に実装する(`src/Ohanami.Core/Embedding/`)。Python の参照との一致は、正解データを使うテストで保証する。前処理の仕様には版を付ける。版は、結果を作ったモデルを識別する ID(model_id)に入る(作り方は 0006)。

### 画像の前処理

版: `siglip2-squash384-bicubic-pillow-v1`。手順は次のとおり。

1. デコードして RGB 8bit にする。アルファは合成せずに捨てる。パレットは展開する。16bit は上位バイトを取る。ICC・gAMA は無視する(色の管理をしない)。EXIF の向きも無視する。
2. RGB 化はリサイズの前に行う。Pillow はパレット画像をそのままリサイズすると、黙って最近傍に切り替えるため。
3. bicubic で 384×384 に押しつぶす。アスペクト比は無視し、切り抜かない。
4. 255 で割り、(x − 0.5) / 0.5 にして、CHW の並びにする。

デコードとリサイズは分ける。

- デコード: SkiaSharp(libpng・libjpeg-turbo・libwebp そのもの)。「バイト列 → RGB8 の幅と高さ」の 1 メソッドの裏に置き(`IImageDecoder`)、取り替えられるようにする。アルファは Unpremul、色空間なしで要求する。
- リサイズ: 自前で書く。Pillow の `ImagingResample` と同じ手順にする。水平 → 垂直の 2 パス、各パスの後に 8bit に丸める、縮小時はフィルタの幅を縮小率の倍に広げる、bicubic は Keys の a = −0.5、端はクランプ、係数は出力画素ごとに正規化する。

### テキストの整理とトークナイズ

整理の版: `siglip2-textclean-v1`。手順は次のとおり。

1. 空白の連なりを 1 つにまとめ、両端を除く。
2. ASCII の句読点 32 字を削除する(置き換えではなく削除。`don't` → `dont`)。
3. 小文字化する。
4. `tokenizer.json` の merges による BPE でトークナイズする(`tokenizer.model` は使わない)。
5. 末尾に `<eos>`(id 1)を付け、63 トークンで切り詰め、`<pad>`(id 0)で 64 まで埋める。

細部の決まり:

- NFKC はかけない。語彙側の正規化が恒等のため。全文検索の正規化(0029)を流用してはならない。全角の句読点は残る。
- 空白の集合と小文字化の規則は、Python の `str.split()`・`str.lower()` が返す結果から表を作って、C# に持たせる(`src/Ohanami.Core/Embedding/Generated/PythonTextTables.g.cs`。生成は `tools/siglip2-reference/gen_text_tables.py`)。.NET の `ToLowerInvariant` は使わない。Unicode 14 以降で追加された 40 文字を余計に写すため。
- 既知の差を、比較のコーパスから外してテストで明示する。İ(U+0130。Python の `lower()` は 2 文字)、語末のシグマ(U+03A3。Python は語末で ς、それ以外で σ)、不正なサロゲート(Python は例外、C# は別のテストで「例外になる」ことを確かめる)。
- 必ず 64 に埋める。モデルの入力が int32 [1, 64] の固定形状であることのほか、SigLIP のテキスト側は、64 に埋めた系列の最後の位置を使って埋め込みを作る(公式の説明は、`padding=max_length` を必須とする。モデルのコードは確かめていない)ので、埋めずに渡すと結果が変わる見込みである。
- この版の `tokenizer.json` の形(自前の BPE が前提にしている。BPE であること・fuse_unk・byte_fallback・ignore_merges が偽であることは、読み込みのときに検査する): BPE、語彙 256,000、merges 580,604、byte_fallback あり、fuse_unk あり(連続する `<unk>` を 1 つにまとめる)。normalizer は空白 → `▁` の置き換えだけ(NFKC なし)、pre_tokenizer は空白で分けて前の語に付ける(MergedWithPrevious)、post_processor は単独の系列の末尾に `<eos>` を付ける(BOS なし)。added_tokens は 249 個(`<pad>` 0・`<eos>` 1・`<bos>` 2・`<unk>` 3・`<mask>` 4・`<unused0>`〜(99 個)・タブや改行の連続・`<start_of_image>` など)で、すべて normalized=false(生のテキストから先に切り出される)。`tokenizer.model`(SentencePiece。BPE で、normalizer は恒等)は使わない。
- BPE の順序は、Rust の tokenizers と同じにする。normalized=false の added_tokens を生のテキストで先に切り出す → normalizer で空白を `▁` にする → normalized=true の added_tokens → pre_tokenizer → BPE → post_processor で `<eos>`。merge は rank が最小のものから、同じ rank が複数あれば左から。未知の文字は byte_fallback の `<0xNN>` にする。
- 一致しないものを避けるための前段のサニタイズは入れない(Python と C# で挙動が二重になるため)。

### 一致のテスト

一致は 3 段に分けて確かめる。混ぜると、ずれたときに原因が分からない。表の「cos」は、2 つのベクトルの向きの近さ(コサイン類似度)で、1 なら同じ向きである。

| 段 | 比べるもの | 合格線 |
|---|---|---|
| 1. 前処理 | C# の RGB8 384×384 と、Pillow の結果の、画素の最大絶対差 | 1 以下 |
| 2. モデル | Python が前処理したテンソルを C# で Run した出力と、Python の onnxruntime(CPU)の出力の cos | 0.9999 以上 |
| 3. 通し | 形式・サイズを散らした 30 枚以上の画像の cos(テキストは同じ id 列を入れて 0.9999 以上) | 0.999 以上 |

正解データは、Python で一度だけ生成してコミットする(`tests/Ohanami.Core.Tests/TestData/`。生成の道具は `tools/siglip2-reference/`)。トークナイザは、検索語 → id 列の表。前処理は、合成した画像 → Pillow のリサイズ結果(384×384 の可逆 PNG)。埋め込みは、画像 → 参照の埋め込み(1152 個の float)。モデルのファイルは `models/` に置き、テストはハッシュで本物か確かめる。ファイルが無ければ、skip ではなく失敗にする。

## 検討した案

- **Microsoft.ML.Tokenizers を使う**: Gemma 系の扱いが入っていない。BPE の `tokenizer.json` からは作れず(`CreateFromTokenizerJson` は Unigram 専用。2.0.1 で確かめた)、`tokenizer.model` を読む経路は、Python とのトークン列の一致を確かめていない。不一致のときに、ライブラリの中をデバッグすることになる。トークナイザは自前の BPE にして、Python と完全一致を確かめるほうが、原因が追える。
- **テキストの整理を、transformers の `Siglip2Tokenizer`(小文字化だけで、句読点を除かない)に合わせる**: 採らない。基準は open_clip と同じ整理(ASCII の句読点を削除)にした(上)。同じ検索語でも、整理の違いでトークン列が変わる(例: 「ガチャ!」の `!`)。open_clip の元の実装が先にかける ftfy と HTML の unescape は、C# で再現できないので、参照でも、かけていない(`tools/siglip2-reference/README.md`)。
- **前処理やトークナイザを Python で動かす**: 製品が Python に依存する。採らない。
- **画像のリサイズを Skia に任せる**: Skia の補間は Pillow と違い、画素で比べられない。ずれの有無を判断できない。Pillow の手順を写して、画素で比べられるようにした。
- **学習時の前処理(bilinear、アンチエイリアスなし)に合わせる**: Pillow の bicubic とも bilinear とも違う。どちらが「正しい」かは決めない。モデルはこの差に頑健とみなし、完全な参照が用意できる Pillow の手順を基準にした。
- **tokenizer.json をビルド時にバイナリ化する**: 読み込みは 0.5〜1.1 秒(ほぼ merges 58 万件の登録)で、起動時に裏で行う。検索の待ち時間はテキスト側の約 0.2 秒に隠れる(0011)ので、バイナリ化しない。

## 根拠

| 確かめたこと | 結果 |
|---|---|
| トークナイザ(821 件、19 種類のコーパス) | id 列が Python の tokenizers と完全一致。整理の結果(clean_text)も全件一致 |
| 実装をわざと壊す | 同じ rank の merge を右から結合すると 5 件不一致、切り詰めを 63 でなく 64 にすると失敗 |
| 前処理(合成した 34 枚) | 最大絶対差 0(ビット一致) |
| 前処理(開発者の手元の約 1,000 枚で測った。データは公開していない。PNG 1030 枚) | 1030/1030 枚がビット一致 |
| モデルの出力(前処理済みテンソルからも、ファイルからも) | 画像・テキストとも 1 − cos の最大が 1e-10 以下 |
| デコード + リサイズ | 1 枚あたり約 17ms |
| `tokenizer.json`(34MB)の読み込み | 0.5〜1.1 秒 |

コーパスの内容: 実際に打ちそうな日本語の短い検索語、英語、日英混在、数字(`ガチャ10連`・`2023年`・`1000000`)、全角英数と半角カナ(NFKC をかけないことの確認)、絵文字とまれな漢字(byte fallback)、ASCII の句読点(除去で空になるものを含む)、全角の句読点、連続した空白・タブ・改行・U+3000、added_tokens を踏む文字列(`<mask>`・`<table>`・`<unused0>`・`▁▁`)、64 を超える長文、空文字列、空白だけ。

画像のコーパス(合成の 34 枚): PNG(RGB・半透明 RGBA・パレット・グレースケール・ICC 付き・gAMA 付き・16bit)、JPEG(baseline・progressive・4:2:0・4:4:4・グレースケール・EXIF の向き・ICC)、WebP(lossy・lossless)、64×64 の極小、2561×1083、極端なアスペクト比。

16bit PNG は、上位バイトを取る(SkiaSharp と libpng の `strip_16` と同じ)。Pillow の 16bit グレーの変換は壊れるので、合わせない。

## 結果

- 前処理とトークナイザのずれが、テストで見つかる。精度だけが静かに落ちる事故を、構造的に防ぐ。
- 一致の保証が及ぶのは、このコーパスの範囲(トークナイザ 821 件、画像 34 枚)までである。
- JPEG と WebP の一致は、Pillow が符号化したファイルでの結果である。カメラや別のソフトが作った JPEG(CMYK など)は、確かめていない。
- 前処理の仕様を変えるときは、版の文字列を上げる。新しい model_id になり、全件が要再作成(作り直しが要る状態)になる(0006)。
- EXIF の向きを無視するので、向きつきの JPEG でも、特徴ベクトルのための画像は向きを補正されない。VLM(画像と文章を扱える AI モデル。ここでは、画像から、写っている文字・説明文・タグを作る。0018)に渡す画像の扱い(0025)と揃っている。

## 見直す合図

- 写真を対象に加えるとき(EXIF の向きの適用、CMYK の JPEG)。画像の前処理の版を上げる。
- 対象の画像形式を増やすとき(JXR など)。デコードと正解データを足す。
- モデルや tokenizer.json を替えるとき(0011・0012)。トークナイザの一致を、新しいコーパスで確かめ直す。
- Pillow・tokenizers の版が変わったと分かったとき。正解データを作り直して比べる。
