# 0026. llama-server は、アプリが終わったら必ず止まるようにし、スリープから復帰したら応答を確かめて続ける

状態: 採用

## 背景

llama-server(VLM を動かすサーバ。VLM は画像から文字・説明文・タグを作る AI モデル。0017・0018)は、VRAM(GPU のメモリ)を約 6GiB(0019)握る子プロセスである。使う人から見た問題は、アプリを強制終了したあとも GPU のメモリが空かず、ゲームが重くなること、次にアプリを起動しても VLM が動かないことである。アプリが強制終了されたとき、親のいない孤児として残れば、VRAM を握り続け、次の起動で新しいサーバが立てられない。

長時間の処理(0028)の途中で、PC がスリープすることもある。復帰したあとの、サーバとの接続や、アプリの状態の扱いを決める必要がある。

llama-server は、クラッシュしたり、応答しなくなったりすることもある。画像が原因の異常と、環境(ゲームが GPU を取った、復帰後にドライバが戻らない、VRAM 不足)が原因の異常を、見分けたい。

## 決定

### 孤児の防止(2 層)

1. **ジョブオブジェクト**: 起動した直後に、`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` のジョブに子を入れる(`CreateJobObject`・`SetInformationJobObject`・`AssignProcessToJobObject` を、.NET から Windows の関数を直接呼ぶ仕組み(P/Invoke)で呼ぶ。NuGet は要らない)。親が終わると、ハンドルが閉じられ、OS が子を終わらせる。ジョブへの割り当てに失敗したら、警告を出して、pid ファイルだけで続ける(起動は止めない)。
2. **pid ファイル**: 起動の直後に、`llama-server.pid`(pid・プロセスの開始時刻・exe のフルパス・ポートの JSON)を、DB のディレクトリに書く。次の起動で、`OhanamiCore.OpenAsync` が DB を開いたあと(単一インスタンスを通過したあと)に、ファイルがあれば掃除する。pid・開始時刻(UTC の ticks の完全一致)・exe のフルパス(大文字小文字を無視)が、すべて記録と一致するときだけ kill する。pid の使い回しで、別のプロセスを殺さないためである。exe のパスを読めないとき(権限)は殺さない。壊れた pid ファイルは、警告を出して捨てる。
   - 記録する exe のパスは、起動したパス(フルパスにしたもの)にする。起動した直後の `Process.MainModule` は、初期化の途中で、まれに(約 0.3%)先頭のモジュールとして `ntdll.dll` を返す。読んだ名前を記録すると、掃除が別のプロセスと判断して殺さなくなる。
   - 二重起動は、単一インスタンスの Mutex で防ぐ。2 つ目のプロセスが、1 つ目の llama-server を殺さないよう、掃除は DB を開いたあとに行う。

### 停止

- 停止は、プロセスツリーごとの kill で、10 秒まで終了を待つ。kill のあと 10 秒待っても終わらないときは、pid ファイルの記録を消さず、警告だけにする(消すと、次の起動の掃除に記録が無く、VRAM を握ったプロセスの横に新しいサーバを立てて失敗する)。終わったと確かめたときだけ、記録を消す。

### サーバの異常と、環境の問題の打ち切り

- 異常のたびに、kill して起動し直す(0023)。同じ画像で 2 回続けたら、その画像を失敗にして先へ進む。2 回目のあとも、壊れたサーバを次の画像に使わないよう、起動し直す。
- 画像を処理する前にサーバが終わっていたとき(外から kill された、など)は、失敗に数えず、起動し直す。
- サーバの異常で失敗にした画像が 3 枚続いたら、画像のせいでなく環境の問題とみなして、ジョブを止める(`LlamaServerException`。実行は `Failed`、エンジンも `Failed` にして、理由を画面に出す)。3 枚目は失敗を記録してから止め、4 枚目は記録しない(次の実行でやり直せる)。成功、またはサーバが答えた失敗(HTTP 400 など、画像の失敗)で、数え直す。
- 起動のポートのやり直しは、プロセスが `/health` の前に終わったときだけ(最大 3 回)。ほかの失敗(時間切れなど)は、やり直さず失敗にする。

### スリープからの復帰

- スリープ復帰の通知は、`PowerRegisterSuspendResumeNotification`(コールバック。ウィンドウが要らない P/Invoke)で受ける(`src/Ohanami.Core/Power/`)。`PBT_APMRESUMESUSPEND` と `PBT_APMRESUMEAUTOMATIC` の 2 種類を、復帰として扱う。1 回の復帰で、通知が 2 回届くことがある。登録できなくても例外にせず、HTTP の失敗で同じ復旧が働く。購読者の例外は、OS のコールバックに伝えない。
- 復帰を検知したら、llama-server に「疑わしい」の印を付ける。次の画像の前に `/health` を確かめ、答えれば続け、答えなければ kill して起動し直す。復帰のあと、無条件には起動し直さない。
- 実行中は、スリープを抑止する(0028)。

## 検討した案

- **ジョブオブジェクトだけで、孤児を防ぐ**: ジョブへの割り当てに失敗する環境や、入れ子のジョブとの相性が心配である。pid ファイルを保険に持つ。
- **pid だけで kill する**: pid は使い回される。別のプロセスを殺す危険がある。開始時刻と exe のパスも照合する。
- **復帰のたびに、無条件で llama-server を起動し直す**: 復帰後に `/health` に答える場合が多く、起動し直しは無駄である(下の表)。確認して、答えなければ起動し直す。
- **`Microsoft.Win32.SystemEvents` で復帰を受ける**: NuGet の依存が増える。ウィンドウが要らない P/Invoke で足りるので、使わない。
- **穏やかな終了(シグナルなど)で止める**: llama-server は状態を持たない使い捨てなので、要らない。
- **異常があるたびに、いつまでも起動し直す**: 環境の問題(GPU が取られている、ドライバ)で、同じ失敗を無限に繰り返す。3 枚続けたら止める。

## 根拠

実機での確認は、合成した画像のフォルダ(番号つきの文字を描いたもの)と、記録の読み取りの道具(`tools/Ohanami.Bench` の `sleep-fixture`・`sleep-report`、`tools/m2-10-kill-*.ps1`)で行った。ジョブオブジェクトは、実物の llama-server で、親の強制終了のときに消えることを確かめた(入れ子のジョブの下でも)。

| 場面 | 結果 |
|---|---|
| VLM の処理中に 70 秒のスリープ | 復帰の通知が 2 回届いた。次の画像の前に `/health` に答えて、そのまま続けた(起動し直しなし)。スリープ前 10 枚・復帰後 20 枚で、30/30 枚が完了、書き起こしの番号も 30/30 枚が正しい |
| llama-server の読み込み中に 70 秒のスリープ | スリープをまたいで起動できた(8/8 枚が完了)。復帰後に待ち直す形は要らない |
| 埋め込み(ONNX Runtime)の処理中に 88 秒のスリープ | セッションの作り直しは無かった(復帰後の最初の Run が成功)。1500/1500 枚が完了 |
| App の強制終了(`Stop-Process -Force`) | llama-server が一緒に消えた(VRAM 955MiB)。pid ファイルが残り、起動し直すと掃除が `NotRunning` で片づけた。孤児なし |
| llama-server だけを kill | 2.5 秒後に新しい llama-server が起動し、同じ画像をやり直した。24/24 枚が完了、失敗 0 |
| サーバの異常が続く | 3 枚が「同じ画像で 2 回続けた」で失敗になり、ジョブが失敗として止まった。4 枚目以降は記録されず、「失敗をやり直す」で 8/8 枚が完了。理由が画面に出た |

復帰の通知は、どの復帰でも 2 回だった。「`/health` に答えた」の直後に「kill して起動し直す」が並ぶことは無かった。

実際のライブラリでの手動確認でも、スリープからの復帰後に、撮影から VLM の完了まで 16.5 秒で動いた。

## 結果

- アプリが強制終了されても、llama-server は孤児として残らない。残った記録は、次の起動で掃除される。
- 復帰後は、`/health` の確認だけで続けられる。起動し直しは、答えないときだけ起きる。
- 復帰の通知が 2 回届くので、復帰の走査が 2 回走る(1 回あたりの所要は 0.0 秒に丸められるほど短く、害は無い)。
- 環境の問題は、3 枚の失敗で止まり、画面に理由が出る。
- 確かめていない: 300 秒を超えるスリープのあとのタイムアウトの扱い(300 秒のタイムアウトがスリープ中の時間を数えるか)、休止状態(`shutdown /h`)での復帰、リクエストの途中でスリープして成功した場合の復帰後の `/health` の確認(通知を受けるのは VLM のランナーだけ)。
- kill のあと 10 秒待っても終わらない枝は、殺せないプロセスを作れないので、テストが無い(コードの読みだけの確認)。

## 見直す合図

- 300 秒を超えるスリープ・休止状態で、問題が出たとき。
- 復帰後の `/health` の確認で足りない症例が出たとき(無条件の起動し直しに替える)。
- 環境の問題の打ち切り(3 枚)が、誤って止める・止めないとき。
- llama-server を、常駐の別の形に替えるとき(0017)。
