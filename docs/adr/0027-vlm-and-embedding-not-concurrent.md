# 0027. VLM と特徴ベクトルの作成は同時に動かさず、始めたあとは待機して新着を処理し続ける

状態: 採用

## 背景

インデックス(検索のための下準備)の作成には、段階が 2 つある。画像の特徴ベクトル(埋め込み。0011)の作成と、VLM(画像と文章を扱える AI モデル。ここでは、画像から、写っている文字・説明文・タグを作る)による作成(0018)である。使う人から見た問題は、撮ったスクリーンショットが、ボタンを押さなくても、すぐ検索に出てほしいこと、そしてゲーム中は GPU を取らないでほしいことである。

- VRAM 8GB に、llama-server(約 6GiB。0019)と ONNX Runtime の画像エンコーダ(約 2.2GiB。0011)は、同時に載らない。
- 埋め込みは 1 枚約 80ms と速く、1030 枚で約 83 秒。VLM は 1 枚 12〜13 秒と遅く、1 万枚で約 36 時間かかる(0018)。
- 特徴ベクトル検索は、特徴ベクトル(埋め込み)だけで使える。VLM の完了を待たずに、検索を使えるようにしたい。
- ゲームの間は、GPU を取り合いたくない。起動して検索だけを使うときに、GPU を取りたくない。
- 新しい画像は、走査(監視。0009)で、あとから入ってくる。
- VLM と埋め込みを切り替えるたびに、llama-server の起動し直しと、ONNX Runtime のセッションの作り直しが起きる。

## 決定

### 順序

- 安い段階(ハッシュの計算 → 埋め込み)を、全件、先に流す。特徴ベクトル検索が、先に使えるようになる。VLM はその後に流し、新しい画像から順に処理する。ジョブの順序は、`Indexer` が持つ配列(埋め込み、VLM)で明示する。
- 2 つのジョブは、同時に動かさない。切り替えるときは、動いているジョブが資源を解放してから、次を動かす(VLM から埋め込みに切り替えるときは llama-server を止め、埋め込みから VLM に切り替えるときはエンコーダを破棄する)。
- 切り替えは、画像 1 枚の処理の境目で行う。処理中の 1 枚は捨てない。

### 待機

- 利用者がジョブを始めたあと、待ちが無くなっても、ジョブの指定を覚えたまま待つ(状態 `Waiting`。画面は「待機中」)。待機の間は、GPU の資源を解放する(llama-server を止め、エンコーダを破棄する)。走査で待ちが増えたら、同じ指定で自動で動き出す。
- 動き出す条件は、「待ち − 飛ばした画像の集合のうち、今も待ちのもの」が 1 枚以上あること。判定は、走査の完了のときだけ行う。
- 一時停止(`Paused`)では、自動では動かない。ゲームの前に、手動で押す。
- アプリの起動時は `Idle`(指定を覚えない)にする。起動して検索だけを使うときに、GPU を取らない。
- 要再作成(現行のモデルでない結果)は、待ちに数えない。自動では始まらない。失敗した画像も、自動ではやり直さない。
- 待機に入る前に、外れたジョブの「新しく入った待ち」を数え直し、外れた時点より増えていれば、選び直す(VLM の実行中に新着が少数だけ入り、VLM が使い切ると、新着が次の走査まで残るため)。

### 切り替えの条件

- 動いているジョブより優先のジョブ(埋め込み)に、新しい待ちが、**20 枚以上**入った、または最初に入ってから **10 分**たったら、切り替える。どちらかを満たせばよい。
- 「新しく入った待ち」は、待ちから、そのジョブが直近の実行で飛ばした画像(ファイルを開けない・書き換えられたなど)の集合のうち、今も待ちのものを引いた数である。飛ばした集合は、ジョブごとに持ち、ジョブが待ちを使い切って終わったときに置き換え、実行を始めるときに空にする。
- 判定は、走査の完了と、切り替えの合図(`shouldYield`)の評価のときに行う。数え直すのは、動いているジョブより前の順のジョブがあるとき、かつ前回の数え直しから 5 秒以上たったときだけである(`shouldYield` は 1 枚約 80ms ごとに呼ばれる)。
- VLM は、待ちを 8 枚ずつ取る(64 枚ずつではない)。64 枚を使い切るまで待ちを取り直さないと、新着が VLM に入るまで最大 64 × 12 秒 ≈ 13 分かかる。8 枚なら、最大約 1.6 分である。

数字(20 枚・10 分・5 秒・8 枚)は、初期値である。

## 検討した案

- **2 つを同時に載せる**: VRAM 8GB に載らない。
- **画像ごとに切り替える**: 切り替えのたびに、llama-server の起動し直しとエンコーダの作り直しが起きる。バッチ単位で切り替える。
- **VLM が全件を終えるまで、埋め込みを待たせる**: VLM は数十時間かかるので、その間に入った新着が、特徴ベクトル検索に出ない。
- **新着が 1 枚入るたびに、すぐ切り替える**: 起動し直しが続く。読めない画像が 1 枚あるだけで、2 つのジョブを往復する問題も起きる(飛ばした集合で防ぐ)。
- **終わった時点の待ちの数を基準にする**: 走査はジョブと並行して動くので、終わった瞬間に数えると、並行の走査が足した本物の新着が、基準に混ざる。数で持つと、飛ばした画像が消えるのと、新着が入るのが、同じ走査で起きたとき、差し引き 0 になる。集合で持つ。
- **待機をなくし、毎回、手動で始める**: 新しい画像が自動で処理されない。撮影のたびに手動で押すのは負担である。
- **VLM だけ、フォルダが N 分静かになってから始める**: 実際の起動し直しが、設計時の見積りより短かったので入れていない(下の表)。ゲームをしながら重くならないかは、普段の使い方で見る(未確認)。

## 根拠

設計時の見積りでは、llama-server の起動し直しに 20〜40 秒かかるとしていた。実際のライブラリ(開発者の手元の約 1,000 枚。データは公開していない)での手動確認では、次の結果だった。

| 項目 | 結果 |
|---|---|
| 撮影から、走査・埋め込み・VLM の完了まで | 走査 3.7 秒 → 埋め込み済 5.3 秒 → VLM 済 21.5 秒 |
| 待機の間に撮った 1 枚 | ボタンを押さずに処理され、待機に戻った |
| 一時停止の間に撮った 1 枚 | 走査には入るが、ジョブは動かない。再開で処理される |
| 起動直後 | 待機から続けない。画面は「未処理 1」 |
| llama-server の起動 | 2.6〜9 秒 |
| 1 枚の VLM | 7〜25 秒 |
| 撮るたびの起動・停止 | 撮影 3 枚で 3 回起きた |

新着 1 枚で、「待機から続ける」と出たログは、段階ごとの数の足し算だった(判断は段階 1 つずつで、設計のとおり)。

20 枚・10 分で切り替える数字は、VLM が速く、実際の使い方(1 枚ずつ撮る)では VLM の実行中に新しい画像が入る状況にならなかったので、確かめられていない。起きるのは、VLM の待ちが溜まっているとき(初回の処理の途中でスクリーンショットが増えるなど)である。

## 結果

- 特徴ベクトル検索は、特徴ベクトルだけで先に使える。VLM は裏で、新しい画像から順に進む。
- 新着は、テキスト検索(全文検索)には最大約 1.6 分の遅れで入り、特徴ベクトル検索には、VLM の実行中だと最大 10 分遅れて入る。
- ゲーム中は、一時停止で GPU が空く。起動して検索だけを使うときは、GPU を取らない。
- 撮るたびに、llama-server の起動・停止が起きる。ゲームをしながら使って、重くならないかは、確かめていない。
- 切り替えの数字は、推測で決めた初期値で、実際に溜まった状態での挙動は未確認である。

## 見直す合図

- ゲームをしながらの利用で、llama-server の起動し直しが気になるとき。「フォルダが N 分静かになってから VLM を始める」遅延を入れる。
- 特徴ベクトル検索に出るまでの遅れ(最大 10 分)が、許せないとき。切り替えの条件(20 枚・10 分)を見直す。
- 対象の VRAM が増え、2 つが同時に載るとき。
