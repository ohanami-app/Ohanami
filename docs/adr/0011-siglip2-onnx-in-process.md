# 0011. 画像の特徴ベクトルは、SigLIP2 を ONNX Runtime でアプリの中で動かして作る

状態: 採用

## 背景

アプリには、検索の方法が 2 つある。

- **テキスト検索**: VLM(画像と文章を扱える AI モデル。ここでは、画像から、写っている文字・説明文・タグを作る。0018)が作った OCR(画像の文字の書き起こし)・説明文・タグと、利用者が付けた手動タグの文字を、全文検索で探す。
- **特徴ベクトル検索**: 画像と検索語を、SigLIP2 という同じモデルで特徴ベクトル(埋め込みともいう。画像や文を、数百から数千個の数値の並びにしたもの。意味が近いものは、近いベクトルになる)にして、近さで探す。

使う人から見ると、次のような問題がある。青空と白い雲だけが写った風景のスクリーンショットを探すとき、VLM が作った説明文が「晴れた空と雲」だったとする。「青空」と打っても、文字が一致しないので、テキスト検索では見つからない。特徴ベクトル検索なら、絵の近さで見つかる。そのために、画像ごとの特徴ベクトルと、検索語の特徴ベクトルが要る。日本語の検索語が通る、多言語の画像・テキスト両用のモデルを使う。

実行の仕組みには制約がある。

- 対象環境は VRAM 8GB 以上。VLM(0018)の llama-server が約 6GiB(0019)を使うので、画像エンコーダ(約 2.2GiB。下の表)と VLM は同時に VRAM に載らない(0027)。
- ゲームをしている間は GPU を空けたい。埋め込みのエンコーダを破棄したとき、VRAM が戻る必要がある。
- 検索のたびにテキスト側が動く。VLM が VRAM を占めている間も、検索はできてほしい。
- 結果は、モデルとビルドだけで決まってほしい(0006)。配布先の GPU の世代で数値が変わるのは避けたい。

## 決定

SigLIP2 の多言語モデル(ViT-SO400M-16-SigLIP2-384)を、ONNX Runtime 1.31.1(CUDA 13 版。モデルを動かす部品。NVIDIA GPU では CUDA 実行プロバイダ(以下、CUDA EP)を使う)で、アプリのプロセス内で動かす。別のサーバやサービスは使わない。

- 画像側は GPU、テキスト側は CPU に固定する。型で分け、取り違えられなくする(`Siglip2ImageEncoder`・`Siglip2TextEncoder`。`src/Ohanami.Core/Embedding/`)。
- fp32 だけを使う。画像側の入力は `image` float32 [1, 3, 384, 384]、テキスト側の入力は `text` int32 [1, 64]。出力は 1152 次元で、モデルの中で L2 正規化(ベクトルの長さを 1 にそろえる処理)済みである。C# 側でも必ず L2 正規化する(正規化済みなら値は変わらず、出力の検査にもなる)。
- 画像側のセッションには `session.disable_cpu_ep_fallback=1` を常に付ける。CUDA EP で扱えないノードが黙って CPU に落ち、遅くなるのを、例外で止めるためである。
- `cudnn_conv_algo_search` は `HEURISTIC` にする。既定の `EXHAUSTIVE` は、初回に大きな作業領域を一時的に確保し、VRAM のピークと起動時間を膨らませる。
- TF32(NVIDIA GPU の、精度を少し落として速くする計算モード)は切る(`use_tf32=0`)。TF32 は Ampere(RTX 30 系)以降にしか無く、オンのままだと配布先の GPU の世代で数値が 2 通りになる。切れば、どの GPU でも同じ fp32 の計算になる。
- 画像側のセッションは、最初に必要になったときに作る。一時停止と、VLM への切り替え(0027)で破棄し、再開時に作り直す。起動時には作らない。検索だけなら、テキスト側の CPU だけで使える状態になる。
- テキスト側は CPU(4 スレッド)で常駐させる。検索時のテキスト側は常に CPU にする。
- Run(モデルを 1 回動かすこと)が失敗したときの作り直しと再試行は 0028、CUDA の DLL の置き場所と、読み込まれた DLL の自己検査は 0015、cuDNN は 0016 で決める。

## 検討した案

- **Ollama で埋め込みを動かす**: Ollama は画像の埋め込みモデルを扱えない。いずれにせよ自前の実行が要る。
- **テキスト側も GPU で動かす**: GPU を VLM が占めている間は使えない。テキスト側の CPU 実行は 1 回の検索で約 0.2 秒で足りる(下の表)ので、構成を 1 つにするために CPU に固定した。
- **DirectML(DirectX 12 経由で動く ONNX Runtime の版)を使う**: 採らない。ONNX Runtime の公式の説明では、DirectML は保守だけが続く扱いで、新機能の開発は WinML に移っている。対象環境は NVIDIA GPU に決めてあり、CUDA EP で足りる。
- **NaFlex(縦横比を保つ可変解像度)の版を使う**: 採らない。入力が、画像ごとにパッチの数が違う別の形(パッチの列・マスク・各画像の縦横のパッチ数)になり、固定の 384×384 を前提にした前処理の確かめ方(0013)と、固定形状の ONNX(上)に合わない。NaFlex の ONNX は、動かして測っていない。
- **GPU の処理を別プロセスのワーカーにする**: 破棄すれば VRAM が確実に戻り、ネイティブ側のクラッシュも UI から隔離できる。ただし、破棄後の VRAM が戻ることを測って確かめられたので(下の表)、採らない。戻らなくなった場合の逃げ道として残す。
- **TF32 をオンのままにする**: Run が約 20% 速い(82〜85ms が 64ms になる)。ただし数値が GPU の世代で変わる。
- **fp16 化、小さいモデル(B-16)との比較**: していない。fp32 の SO400M で足りる。

## 根拠

環境は、ONNX Runtime 1.31.1(CUDA 13 版)、cuDNN 9.28.0.42、RTX 3070(VRAM 8GB)。PATH から CUDA と cuDNN のディレクトリを外して測った(測り方は 0016)。

プロセス内実行を採る判断の線は、次のとおり(測る前に決めた。「線」は、合格とする基準の値である)。

| 項目 | 線 | 測った値 | 判定 |
|---|---|---|---|
| 破棄後の VRAM(GPU 全体の使用量) | 作成前 + 600MiB 以下 | 作成前 1036MiB → 破棄後 1172MiB(+136MiB) | 合格 |
| 1030 枚の連続処理(100 枚目と 1030 枚目の差) | VRAM・ワーキングセット(プロセスが実際に使っているメインメモリ)とも 100MiB 以内 | VRAM 0MiB、ワーキングセット +8MiB | 合格 |
| 1 万枚の処理時間 | 1 時間以内(1 枚 360ms 以下) | 1 枚 約 82ms(逐次)、1 万枚 約 14 分 | 合格 |
| テキスト側の検索語 1 回(CPU) | 500ms 以下なら CPU を常用 | 中央値 174〜219ms(最大 266ms) | 合格 |

長時間の連続処理で VRAM が増え続ける恐れについて: 同じモデルを CUDA で長時間動かすと、処理した枚数に比例して GPU メモリが増え、やがてメモリ不足で落ちる、という外部の報告がある(原因は確定していない)。ここでは、1030 枚の連続処理で VRAM の増えが 0MiB だったので、アリーナ(確保したメモリの再利用の設定)は変えていない。

破棄後に戻らない 136MiB は、CUDA コンテキストの分である(自前変換の ONNX(0012)で同じ測定をすると、+127MiB だった)。モデルの重み(1.7GB)が残る状態は、明確な不合格として線を引いていた。

そのほかの測定値:

| 項目 | 値 |
|---|---|
| 画像側のセッションの作成 | 1.30〜1.60 秒 |
| 画像側の 1 枚の内訳(中央値) | ファイルの読み込み 0.3ms、デコード+リサイズ+正規化 15.4ms、Run 66.2ms(律速は Run) |
| 画像側のプロセスのメモリ | プライベート 約 3.25GB(ONNX Runtime がホスト側にも重みのコピーを持つ)、ワーキングセット 約 0.88GB |
| 画像側の VRAM(自プロセス) | 作成後 2213MiB、推論中のピーク 2223MiB、破棄後 141MiB |
| テキスト側のセッションの作成 | 1.8〜3.0 秒 |
| テキスト側の常駐メモリ | 約 1.76GiB(重みのファイルは 2.7GiB) |

TF32 を切る判断。表の「1 − cos」は、2 つのベクトルの違いの指標で、0 なら同じ向き(同じ結果)である。ここでは、GPU の結果を、CPU で計算した参照の結果と比べている。

| 設定 | Run | CPU の参照との差(1 − cos の最大。合成画像 34 枚) |
|---|---|---|
| TF32 オン | 64ms | 1.8e-4 |
| TF32 オフ | 82〜85ms | 2e-11 |

オフにすると Run が約 30% 遅い(64ms が 82〜85ms になる)。1 万枚で 3〜4 分の差にしかならず、VLM の数十時間に比べて無視できる。GPU のテストの基準は `1 − cos ≤ 1e-6` に締めた(広い基準 cos ≥ 0.999 では、前処理や転送の本物の不具合が隠れる)。

実際の手元のライブラリ(開発者の手元の約 1,000 枚で測った。データは公開していない)で、走査から検索まで通した結果は次のとおり。

| 項目 | 値 |
|---|---|
| 1030 枚の走査 | 1.0 秒 |
| 1030 枚の埋め込み(製品の経路、TF32 オフ) | 約 83 秒(1 枚 約 80ms) |
| 検索 1 回 | 約 0.2 秒(大半は検索語の埋め込み) |
| ワーキングセットのピーク | 約 4.3GiB |

## 結果

- 画像の埋め込みは GPU の約 80ms/枚、検索語の埋め込みは CPU の約 0.2 秒/検索で動く。VLM が VRAM を占めている間も検索できる。
- ゲーム中は、一時停止でセッションを破棄すれば GPU が空く(約 140MiB の CUDA コンテキストは残る)。再開のたびにセッションの作成(約 1.5 秒)と自己検査(0015)が入る。
- CUDA と cuDNN の DLL の同梱が要る(0015・0016)。cuDNN は約 488MiB(0016)。
- テキスト側が約 1.76GiB を常駐させる。
- TF32 を切ったので、評価の基準線は製品の経路(TF32 オフ)で取る。オンで取った埋め込みと比べると 1 − cos の最大が 1.2e-3 違う。

## 見直す合図

- 破棄後の VRAM が戻らなくなったとき(ONNX Runtime・ドライバの版を替えたとき)。GPU の処理を別プロセスにする。
- 対象の GPU を広げるとき(Turing 以前など)。数値の一致と速度を測り直す。
- モデルを替えるとき(0006)。作り直しの規則に従って、新しい model_id として扱う。
- 検索の待ち時間が気になる量になったとき(テキスト側の CPU 実行が 0.5 秒を超えるなど)。GPU が空いているときだけ GPU を使う方式(経路が 2 つになる)を検討する。
