# 0041. サムネイルの一覧は自前で描き、ファイルは Copy でだけ渡す

状態: 採用

## 背景

検索の結果と、検索していないときの新しい順の一覧は、数千〜数万枚のサムネイルを並べる。スクロールが滑らかで、見えていない画像のために仕事をしないことが要る。結果の画像は、ブラウザのアップロード欄や、エクスプローラー、Discord、ペイントなどに、ドラッグして渡したい。

WPF の標準の部品には、格子状に並べて仮想化(見えている分だけ作って描く仕組み)するパネルが無い。

## 決定

**一覧は、1 つの要素が、見えているセルだけを `OnRender` で描く、自前の部品にする**(`src/Ohanami.App/ThumbnailGridControl.cs`)。子要素・テンプレート・データバインディング・コンテナの使い回しを使わず、配置・当たり判定・選択・ドラッグの開始を、すべてコードで明示的に書く。NuGet の追加は要らない。

**サムネイルの作り方。**

- Core は画素を作り(`src/Ohanami.Core/Thumbnails/`。デコードも縮小も SkiaSharp。WPF の型を含まない)、App が表示する(`ThumbnailLoader.cs`)。App は、Core が返した BGRA の画素から `BitmapSource.Create` で作って `Freeze` する。`BitmapImage` は通さない。
- ディスクのキャッシュの鍵は、**内容ハッシュ × 箱の大きさ × 書式の版**で、場所は `<根>/v<版>/<ハッシュの先頭 2 桁>/<ハッシュ>_<幅>x<高さ>.jpg`、JPEG の品質は 85。鍵がハッシュなので、検索結果の並びが変わっても同じ画像のサムネイルを再利用でき、ファイルを移動・改名しても作り直さない。書式(品質・縮小の方法)を変えるときは、版を上げる。
- メモリ上の保持は、鍵を持つ LRU(最近使っていないものから捨てる方式。1,500 枚まで)にする。UI のスレッドの外で作り、見えているセルを優先し、見えなくなった要求は取り消す。
- 埋め込みの段階で、全画像のデコード済みの画素を作る。このとき、サムネイルも一緒に作る案は取らない。サムネイルは、見たときに作る(オンデマンド)。

**他のアプリへの受け渡しは、`Copy` だけを許す。** ドラッグは `DragDropEffects.Copy` でファイルを渡し(`DataFormats.FileDrop`)、`Move` は許さない。`Move` を許すと、ドロップ先によって、元のファイルが移動・削除されうるため。「エクスプローラーで表示」と「画像をクリップボードにコピー」「ファイルとしてコピー」も持つ。

**画面を更新する仕組み。** 毎フレームの購読(`CompositionTarget.Rendering`)は、必要なときだけつなぐ。常時つないでいると、ウィンドウを開いたまま放置しても UI のスレッドが 165Hz で回り続けた(放置時の CPU: 1 コアの 16.7%。必要なときだけつなぐと 0.10%)。再描画の要求(オフセット・選択・ホバー・項目・大きさの変化)と、ローダーの結果の到着のときにつなぎ、不要になったら外す。`InvalidateVisual` は再配置も起こすので、配置のたびに再描画を要求すると、購読を外せなくなる。再描画を要求するのは、大きさが変わったときだけにする。

## 検討した案

| 案 | 採らなかった理由 |
|---|---|
| `ItemsControl` などの標準の部品と仮想化パネルで格子を作る | 格子状に並べて仮想化するパネルが、標準には無い。テンプレートとデータバインディングに頼ると、設計の原則(すべて明示的に)に反する |
| 埋め込みの段階で作ったデコード済みの画素から、サムネイルも作る | 箱の大きさが表示のスケール(DPI)で変わり、1 つの大きさだけを作ると、別の大きさでは結局オンデマンドで作る。埋め込みを作り直すたびに、サムネイルの作り直しが絡む。段階どうしが結びつく。オンデマンドとディスクのキャッシュで、合格線(下)を満たせた。初回表示の待ちが問題になったら、低優先度の裏の生成を足す |
| `BitmapImage` で縮小デコードする | PNG のデコードのたびに、メモリの自動回収(GC)のうち重い世代(gen2)が約 30 回/秒起きた。`BitmapSource.Create` では約 2〜3 回/秒だった(下) |
| ドラッグで `Move` も許す | 元のファイルが移動・削除されうる |

## 根拠

合格線は、測る前に決めた。WPF の描画は、60fps で止まらず、モニターのリフレッシュレートに追従する(開発機は 165Hz で、フレームの間隔は p50 6.06ms、p99 6.07ms)。そこで、ミリ秒の絶対値でなく、フレーム周期 T(6.06ms)の倍数で決めた。

| シナリオ | 線 |
|---|---|
| ウォーム(LRU に収まる範囲の往復) | p95 ≤ 1.5T、2T 超のフレーム ≤ 1%、6T 超 = 0 個 |
| コールド・高速・ランダムなジャンプ | 2T 超 ≤ 3%、6T 超 ≤ 3 個、コールドで画面に入ってから画像が出るまで p95 ≤ 1 秒 |
| 全シナリオ | ワーキングセットの増分 ≤ 600MiB |

1 万件を、1,030 枚の実ファイルを項目ごとに別の識別子で水増しして測った(セル 256×144、画面あたり約 30 件、LRU 1,500 件、デコードのワーカー 8)。3 回の測定で、ウォームで 6T を超えるフレームが 1 度出たこと(下に書く)を除き、どれも全シナリオが線に収まった(下の表は 3 回の範囲)。

| シナリオ(1 万件) | 2T 超 | 6T 超 | 画像が出るまで p95 | ワーキングセットの増分 |
|---|---|---|---|---|
| デコードなし(描画の下限) | 0.11〜0.77% | 0 | - | 156〜162MiB |
| コールドの通し | 0.2〜0.9% | 0〜2 個 | 75〜275ms | 335〜502MiB |
| ディスクキャッシュあり | 0.14〜0.25% | 0 | 40〜116ms | 432〜483MiB |
| 高速(10000DIP/秒) | 0.16〜0.58% | 0 | - | 328〜365MiB |
| ランダムなジャンプ 200 回 | 0.56〜0.90% | 0〜1 個 | 49〜62ms | 398〜445MiB |
| ウォーム(先頭 1,000 件の往復) | 0.00〜0.79% | 3 回のうち 1 回で 18 フェーズ中 1 フェーズに 1 個、ほかの 2 回は 0 個 | - | 312〜320MiB |

デコードの時間は、PNG を縮小デコードして 1 枚の平均 6.8ms(p95 12.1ms)、ディスクキャッシュ(JPEG 品質 85、平均 12KB、1 万件で 118MB)からだと 0.56ms で、約 13 分の 1 である。キャッシュの作成は 1 万件で 14.2 秒かかった。`BitmapImage` を通さない作りにすると、コールドの gen2 の GC は、約 30 回/秒から約 2〜3 回/秒になった。

ウォームで、6T を超えるフレームが 1 度だけ出た(42.6ms)。そのフレームでは、直前の処理・描画・デコードの取り込み・GC のどれも起きておらず、UI のスレッドが 40〜50ms の間、アプリのコードを動かしていなかった。追加で流した 12 フェーズでは再現しなかった。線は緩めず、アプリの外の原因とみられる単発の停止として記録し、合格扱いにした。

ドラッグの先として、ブラウザの `<input type="file">` とドロップ領域、エクスプローラーのフォルダ、Discord、ペイントで、実際に渡せることを手で確かめた(原本はコピーされ、残る)。ブラウザの `input` への最初のドロップが動かなかったのは、試験用のページがページ全体でドロップの既定の動作を止めていたためで、アプリの問題ではなかった。

## 結果

- 一覧のメモリは、見た分だけ 1,500 枚まで埋まる。上限は、表示のスケール 100% で約 221MB、150% で約 498MB、200% で約 885MB である。
- 新しい順の一覧は、上限なしで全部を出す。全選択(Ctrl+A)で数万枚を選べ、ドラッグ・コピーは選んだ全部のファイルの存在を確かめるので、UI のスレッドが秒単位で止まりうる(5 万枚で 0.5〜1.8 秒の見込み。ディスクが冷えるとさらに長い)。数万枚への手動タグ付けと、数万本のドラッグが OS に渡せるかは、確かめていない。
- サムネイルが作れなかったセルは、「元のファイルが無い」(原本が開けない)か「読み込めない」(デコードできない)と出す。
- ホバーのツールチップは、WPF の `ToolTipService` の探索に頼らず、グリッドが自分で出す。標準の探索では、検索結果のサムネイルで出なかった(本当の原因は追っていない)。
- 開発者の手元の約 1,000 枚(データは公開していない)を水増しした 1 万件で測った。実際に数万枚を並べた測定はしていない。

## 見直す合図

サムネイルの初回表示の待ちが問題になったとき(裏での事前生成を足す)。一覧の件数が数万を超えて、全選択やメモリが問題になったとき。
