# Ohanami.KanaYardstick: 濁点・半濁点の読み取りの尺

VLM が画像の中の文字を読むとき、濁点・半濁点(゛゜)の読み違いがどのくらい出るかを、**合成した画像**で測る道具。ADR 0019(`--image-min-tokens` の測定)と ADR 0021(OCR の精度)の数字は、これで取った。
次の VLM の候補を、今のモデルと同じ尺で測るために置いてある。**手元専用**(GPU と llama-server を使う)。数字を上げるために回すものではなく、「候補が今のモデルより濁点・半濁点を読めるか」を決めるために使う。

## なぜ合成画像か

実際のスクリーンショットの OCR は、セリフの意味から字を補えるので、字の形だけの読み取りの誤りが見えにくい。この道具の文は、濁点・半濁点の付く字(25 字)と付かない字(44 字)を意味のない並びにしたもの。単語の予測が効かないので、字の形を読む力だけが出る。
正解は「作った文」で、どのモデルの出力にも寄っていない(今のモデルの下書きから正解を作ると、今のモデルに有利に偏る)。画像と正解は、乱数の種から、毎回同じものを作り直せる(画像はコミットしない)。私物の画像を使わないので、画像と数字は公開してよい。

画像: 背景 3 種(dark / light / busy = にぎやかな絵の上に半透明の窓) × 字の高さ 5 種(12・16・20・24・32 px) × 6 枚 = 90 枚。1 枚に約 120 字(合計 10,800 字、濁点・半濁点の付く字 6,478)。
画面の大きさは 1280×720 と 1024×576(今の設定で、画像トークンが 880 と 576 になる大きさ)。フォントは游ゴシックとメイリオ。ひらがなの行とカタカナの行を交互に置く。

## なぜ Bench の下に置かないか

`tools/Ohanami.Bench`(検索の回帰ベンチ)のコマンドにはしなかった。

- 画像を WPF(`FormattedText`)で描くから。Bench は `-windows` なしの `net10.0` で、WPF を使えない(Skia で描き直すと、アンチエイリアスが変わって、今のモデルの数字を取った画像と画素が違ってしまう)。この道具の `net10.0-windows` + WPF は、画像を同じ画素で作り直すために要る。
- Bench は検索の回帰を測る道具で、私物の画像と qrels に依存する。これは私物を使わず、モデルの読み取りだけを測る。
- 候補のモデルは製品の `VlmCatalog` に載っていないので、Bench の `vlm-check`(製品の構成の確認)に乗せられない。llama-server のファイルと引数をその場で指して流す。

製品の `Ohanami.Core` は、プロンプトとスキーマの文字列(`VlmPrompt`・`VlmSchema`)、llama-server の引数の組み立て(`LlamaServerArguments.Build`)、画像 1 枚の要求・再試行・応答の解釈(`VlmClient`)を、製品と同じものにするために参照する(`InternalsVisibleTo`)。要求の組み立てなどは写さず、製品のコードを呼ぶ。

## 使い方

作業フォルダ(`--work`)はリポジトリの外にする(中だと拒否する。画像と結果をコミットしないため)。

```
# 1. 画像と正解(manifest.json)を作る。同じ種なら、毎回同じバイト列。画像 1 枚ごとの画素のハッシュを manifest.json に書き、画像の束のハッシュ(bundle_sha256)を表示する
dotnet run --project tools/Ohanami.KanaYardstick -- gen --work D:\work\kana

# 2. 流す。1 回で 1 つの条件。条件の名前は自由(c1 = 製品の起動のまま、c2 = --image-min-tokens 3584 を足す)
dotnet run --project tools/Ohanami.KanaYardstick -- run --work D:\work\kana --cond c1 `
    --llama runtime\llama.cpp\b12110\llama-server.exe `
    --model models\Qwen3-VL-8B-Instruct-GGUF\Qwen3VL-8B-Instruct-Q4_K_M.gguf `
    --mmproj models\Qwen3-VL-8B-Instruct-GGUF\mmproj-Qwen3VL-8B-Instruct-F16.gguf
dotnet run --project tools/Ohanami.KanaYardstick -- run --work D:\work\kana --cond c2 --min-tokens 3584 ...(同じ)

# 3. 採点。report.txt(表)・per-image.tsv・alignments.txt が <work> に出る
#    --text-tokens と --gate は必須(既定は無い)。ADR 0019 の表の再現は、--text-tokens 536 --gate with-zu
dotnet run --project tools/Ohanami.KanaYardstick -- score --work D:\work\kana --text-tokens 536 --gate with-zu --base c1 --variant c2
```

- `run` は、製品と同じ引数(`LlamaServerArguments.Build`)で llama-server を起動し、製品の `VlmClient` を呼んで画像を 1 枚ずつ流す。要求(`messages`・`temperature` 0・`response_format` の json_schema・`max_tokens` 2048・`cache_prompt` false)と、`finish_reason` が `length` のときだけの再試行(`dry_multiplier` 0.8、次に `repeat_penalty` 1.1)と、応答の解釈は、製品のコードそのもの(写しではない)。
  結果は `results.jsonl` に 1 枚 1 行で足す(済みの (条件, id) は流さない。途中から続けられる)。何で流したかは `run-info-<条件>-<時刻>.json`(llama-server・モデル・mmproj の SHA-256、モデルのファイルの大きさ、引数、プロンプトの SHA-256、`manifest.json` から写した画像の束のハッシュ)と、`server-<条件>-<時刻>.log`(と `.cmdline.txt`)に残る。終わると(Ctrl-C でも)llama-server を止める。
  90 枚で、今のモデルは c1 が約 25 分、c2 が約 2.3 時間(GPU は VRAM 約 6〜7GB。ほかの GPU の処理を止めてから)。
- 候補のモデルが別の引数を要るなら、`--extra "<引数>"`(空白区切り。パスに空白を含められない)で製品の引数のあとに足す。`--max-tokens` で `--image-max-tokens` を替えられる。
- `score` の `--text-tokens`(必須)は、プロンプトの文章のトークン数(画像トークン = `prompt_tokens` − この値)。Qwen3-VL-8B と製品のプロンプトでは 536(ADR 0025)。**別のモデルでは、小さい画像の `prompt_tokens` から測り直して指す**(実倍率と「拡大後の字の高さ」の表が、これに依る)。
- 採点の正規化は ADR 0021 と同じ(NFKC・小文字化・空白除去)。正解と出力を 1 字ずつ並べ(編集距離)、濁点・半濁点を外した字が同じ置換を**濁点・半濁点だけの誤り**とする。正解が濁点・半濁点の付く字(濁字)なら**濁誤**(落 = 付く字に付かなかった / 取違 = 濁点と半濁点の取り違え)、付かない字なら**付加**(清音の字の誤りで、清誤に入る)。ほかの誤り(別の字への置換・読み落とし)は、正解の字が濁字か付かない字かで分ける。余計な字(挿入)も数える。区間は Wilson の 95%。
  集計に使うのは、1 回目で `finish_reason` が `stop` で、繰り返しの疑い(余計な字が正解の字数の半分超)でない出力だけ。再試行の出力・失敗・繰り返しの疑いは混ぜずに、最後の節で別に数える。

## 判定の決まり

- **ぢ・づ・ヂ・ヅは別に数える**。濁点・半濁点の誤りは、「ぢ・づ・ヂ・ヅを除いたもの」と「ぢ・づ・ヂ・ヅだけのもの」を別々に出し(`score` の表の「濁誤%(ぢづ除く)」と「ぢづ誤%」の列)、判定でも別々に見る。今のモデルは、ぢ・づ・ヂ・ヅの 6 割が、字の大きさや拡大にほとんど依らず、清音(ち・つ・チ・ツ)に読み違えられる(ADR 0021 の観察)。ほかの字と混ぜると、大きさの効果を測れなくなる。
- **進む線は、結果を見る前に決める**。`score` の「進む線」の表は、ADR 0019 の測定の線(基準の条件の濁誤が 5% 以上、かつ比べる条件がその 1/3 以下)を、`--base`・`--variant` の 2 条件に当てる。この線に使う濁誤の率が、ぢ・づ・ヂ・ヅを含むか除くかは、`--gate with-zu|without-zu` で必ず指す(既定は無い)。報告の先頭の「判定の線」の行に、どちらで判定したかが出る。ADR 0019 の表の再現は `with-zu`。**次に測るときは、流す前に、どちらで判定するかを決めて書く**。別の比べ方をするときは、流す前に線を決めて書き、表の線(`ScoreReport` の `GateBaseMinimum`・`GateRatio`)をそれに合わせる。
- 1 つの升(字の高さ × 背景)に濁点・半濁点の付く字が約 430 ある。2% より小さい差は分けられない(区間で見る)。
- **画像は、数字を取った環境と同じ画素のときだけ、数字を比べる**。フォントや WPF の版で、同じ種でも画素が変わりうる。`gen` が出す束のハッシュ(下の「今のモデルの数字」に記した値)が同じなら、画像は同じ。違うときは、記録の数字と比べない。候補のモデルを測るときは、今のモデルも、同じ画像で一緒に流す(c1 で約 25 分)。

## 今のモデルの数字

Qwen3-VL-8B-Instruct(Q4_K_M)+ mmproj(F16)、llama.cpp b12110、製品の起動の引数のまま(条件 c1)、種 20261119、90 枚。RTX 3070(VRAM 8GB)で測った(画像と正解は上の手順で作り直せる)。
画像の束のハッシュ(`gen` が出す `bundle_sha256`): `3a810b40a7d5a28d22b272279812d022b2716cadfadedabe78fea0a3e627231e`。数字を取った画像と、この環境で作り直した画像は、PNG のバイト列まで同じだった。これと違う束で測ったら、下の数字とは比べない(上の「判定の決まり」)。
c1 と c2(`--image-min-tokens 3584`)の比較と、その判断は ADR 0019。ここには、次の候補を比べる基準になる c1 だけを置く。

下の表は、字の高さごとの誤りの率(%)。「濁誤」は、濁点・半濁点の付く字のうち、濁点・半濁点だけを読み違えた(落・取違)字の割合。「ぢづ除く」は、ぢ・づ・ヂ・ヅを除いた濁字での「濁誤」。「ぢづ」は、ぢ・づ・ヂ・ヅ(各行 94〜104 字)での割合。
「濁他」は濁字の、濁点・半濁点以外の誤り(別の字への置換・読み落とし)の割合。「清誤」は、濁点・半濁点の付かない字の誤り(別の字への置換・読み落とし・濁点・半濁点の付加)の割合。CER は、全部の誤り(置換・挿入・削除)÷正解の字数。1 つの行は 18 枚(濁字は約 1,295)。
